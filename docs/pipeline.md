# How the triage pipeline works

The pipeline sorts the craft apps' open issues and PRs (about 21,000) and works the ones maintainers pick, plus small bug fixes that pass the merge rule: it reviews, fixes up and merges PRs and implements issues. Models read, sort and review. People start items and answer one recommendation per item, on GitHub, Discord, the dashboard or their own agent.

## The flow

Every new issue and PR gets the cheap classification (type, size, duplicates, priority) and nothing more. A maintainer then starts an item at the step it needs: review, fix-up, implement (for an issue) or the merge queue. AutoCraft runs the steps from there and comes back with one recommendation, or merges when the maintainer approved the merge. Small and medium bug fixes from whitelisted contributors that pass the merge rule go through without a start. A merge approval works like the merge button on GitHub: AutoCraft makes every fix the merge needs and comes back only where it cannot get there (a step failing twice, a fix it cannot make) or where new commits by someone else go beyond what was approved. See Starting and answering.

The security deep scan is not part of this path: an operator, or a maintainer with write access who sets a spend cap, starts each scan, and it runs outside the daily pipeline (see Security deep scan).

The stages, in order:

1. Sync: Mirrors every issue, PR and comment of the tracked repos into the local database, from GitHub App webhooks within seconds and from a backstop poll, reads the CI state of each default branch every 2 minutes, and makes a vector of each item's title and body for similar-item search.
2. Duplicates: Finds items that describe the same bug or request as another open item, or one closed in the last year, and compares each group. A duplicate is a signal on the items; it closes nothing and holds back only a pull request nobody started.
3. Classify: Gives each open item one type label and two flags (security, needs decision). Jev goes first, Haiku gives a second opinion, and a referee settles disagreements outside the scope labels.
4. Priority: Gives each open item a level from P0 to P4, then orders the candidates of later stages by a work rank.
5. Conversations: Answers what a maintainer or operator writes in an item's conversation; a reply may propose commands that a person runs with a button.
6. Label: Writes each settled type label and flag to GitHub. A label a person set is never changed.
7. Review: Opus reviews every wanted PR at its current head, reading the repo, and gives a verdict with the complete fix list. It writes nothing to GitHub until the final review is posted.
8. Implement: Implements an issue a maintainer queued: Opus plans it in a workspace pod and asks the author or a maintainer when the issue leaves facts or choices open, then writes the change and its tests in a workspace session; AutoCraft runs the formatter, clippy and the tests itself, sends findings back to the session and opens the pull request. A review that asks for fixes or red CI on that pull request goes back to the same session, and AutoCraft pushes the checked revision for a new review.
9. Fix-up: For a take-with-fixes review, applies the listed small fixes to the contributor's branch, or posts them as a comment when the branch cannot be pushed to (on a PR approved for merge, its approver is asked instead). For a wanted PR whose gate check fails, runs the formatter, reruns an infrastructure failure once, or has a model patch the code. For a red default branch in an approved repo, reruns a flaky failure once, opens an issue for an infrastructure failure and a fix PR for a code failure.
10. Verify: Records upstream CI as the verification of taken PRs in repos that have it. A repo without CI, and a bugfix that changes a test file, get a model-planned build in a build environment; a model summarises failures. With the Screenshots feature on, a UI pull request is also rendered at the base and at the head, and a model compares the images; a clear regression holds the merge.
11. Merge queue: Merges PRs that pass the rules in integration batches (up to 50 PRs, checked by upstream CI on the batch PR) through safe-merge; a PR outside the rules merges once a maintainer approves it. Before a PR the rule would merge goes into a batch, and before a pre-approved merge is handed over to the queue, Opus reviews its head commit once more, adversarially and independently of the first review; a defect it verifies becomes a fix-up, or brings an approved item back to a maintainer. Approves held CI runs of outside contributors where the repo allows it.
12. Act: Carries out the closes people command, as them, with a short comment from a fixed template, and posts the comment that asks a pull request's author for more work.
13. Post-merge review: Opus reviews what landed with a merge nobody approved, or whose code the pipeline changed after the approval, reading it with the pipeline's own commits and reviews of the PR, and lists defects and minor findings; a PR that merged as a person approved it gets no such review. Each defect that no open item covers becomes one follow-up issue in repos approved for commenting, except on a security fix whose advisory is not published yet (its findings are only shown); minor findings are only shown. Once an hour, while an operator has named an eval repo, the self-evaluation looks for stalls, loops, repeated failures and cost outliers in AutoCraft's own records; Opus investigates each new or grown cause in the eval repo's code, and each real defect becomes one issue there.

Sync, Embed, Duplicates, Classify and Priority cover the whole org. Label, Review, Fix, Fix-up, Verify, Merge, Post-merge review and Act go one or a few repos at a time. The work rank orders the candidates of Review, Verify and Fix-up, highest first.

## Sync

Every issue, PR and comment of the tracked repos is mirrored into the local database: GitHub App webhooks queue a re-read of each item they name, within seconds, and an org-wide search for changes runs as a backstop every 15 minutes, or every minute while webhooks are not set up or miss changes (docs/operations.md, Webhooks). Later stages plan from the mirror. The mirror can be minutes behind GitHub, so every stage that writes to GitHub or spends a model call first reads the item's live state (state, draft flag, head commit) in one batched query and skips what changed; the skipped items come back on a later pass. Automatic; no model.

Each run searches from 10 minutes before the newest `updatedAt` stored, and once an hour it also re-reads the 6 hours before it, because GitHub's search index can show an item late. An item whose stored row already matches GitHub is not written again. A window of one second with more than 1,000 matches cannot be read by search: the run logs a warning and lists every tracked repo for it instead, and no high-water mark moves until the run finishes. Once a day per tracked repo (the repo reconciled longest ago, one at a time) the runner lists the repo's open issues and PRs, giving way to the minute sync. Mirror rows that are open here but not listed as open are read individually: closed or merged ones are updated, and deleted or transferred ones are marked CLOSED and recorded in the audit log as `item-gone`. Tracking a repo again clears its high-water mark, so the next sync reads it in full. Only the last 20 comments and 10 reviews of an item are mirrored.

**Main CI (`main-ci`).** Every 30 seconds during a sync run and once after it, when the last poll is at least 2 minutes old, one GraphQL query reads the default-branch head commit and its checks for every synced repo. The poll belongs to the sync run, so it runs with the pipeline switch on or off, and a failed poll does not fail the sync. `autocraft-server main-ci [--repo R]` prints the table, and the `main-ci` runner step polls on request (read-only). `main_ci` keeps one row per head seen (the latest 50 per repo) with its state, failing checks and checks. The state of a head:

- `red`: a gate check failed. The gate checks are the ones named `gate`, as in CI fix; in a repo whose checks have no such name, any failed check that is not on the repo's optional-check list counts.
- `optional`: only checks outside the gate, or only checks on the repo's optional-check list, failed.
- `running`: something is pending and no gate check failed.
- `green`: every check passed or was skipped.
- `none`: no checks.

A repo whose newest head's checks have not ended after a red head stays red (see **No new failures** below); `main-ci` prints its state as `red/running` (`red/none`). For a red repo, the culprit is the first red head after the last green or optional one (its PR number is read from "Merge pull request #N" or a trailing "(#N)"), and `red_since` is when that head's state became red. `GET /api/main-ci` returns the summary and one entry per repo (red first); `GET /api/main-ci/summary` returns the counts alone, which `GET /api/progress` also carries as `mainCi`. A change of state bumps the `mainci` live topic.

## Embed

Each item gets a vector from its title and body. A new vector is made only when the text changes. Runs locally on this machine; no model quota and no limit.

## Duplicates

Finds open issues and PRs that describe the same bug or request as another open item, or one closed within the last year, in the same repo.

- **Candidates.** Nearest neighbours by vector (similarity 0.75 or more, at most 3 per item, same kind). A pair an operator already ruled on is not asked again. A change of the cut-off scans every item again once. A quiet pull request (a security fix not yet published) is never a candidate, on either side of a pair.
- **Check.** Jev answers first (0.9 or more is a duplicate, 0.1 or less is distinct). Haiku settles the rest. While Jev is unavailable (see Waits), Haiku decides every pair on its own: its answer is the verdict.
- **Groups.** Items joined by duplicate pairs form a group. The members of each kind (PRs, issues) are compared together in one call by the Compare duplicate groups step (`autocraft-server dupe-compare`).
  - PRs: Opus, with read-only tools on a checkout of the default branch, gets each PR's title, body, linked issues and code diff; CI and review state are background, not rules. It picks the PR to keep and, for each other PR, says whether it is a duplicate, what it does better and which parts are worth carrying into the kept one.
  - Issues: Sonnet, without tools, gets all reports in one call. It picks the report to keep and lists what each other report adds (steps, versions, logs).
  - A PR is never closed as a duplicate of an issue; the kept PR is linked to the kept issue.
  - A closed or merged member wins without a call. A set of more than 10 members is compared in rounds of 10 whose winners meet.
  - A set is compared again only when a member's state, head commit or text changes. Live state is checked on GitHub before the calls; a set with a changed member waits for the next sync. `autocraft-server dupe-compare again <repo>#<n>` (operator, audited as `compare-again`) marks the sets that include an item for one more comparison; the group keeps its id and takes the new result.
  - When the model gives no valid answer twice, the rule decides: the closed or merged one, else the one with a merged fix, else the one with 5 or more extra comments, else the older one. The group says it was kept by rule.
- **A signal.** A group's result (which item is best, what each other one does better, which parts are worth carrying over, what each report adds) shows on its items. It closes and asks nothing, and holds nothing a person started. A maintainer closes a duplicate with `close as duplicate of #n`, and ports parts with a `fix-up` command whose text names them.
- **Held.** An open PR nobody started stays off the automatic path while its group holds another open PR or a merged one: it is neither reviewed nor merged, and a merge already queued (or batched) is refused. A model's comparison frees the PR it keeps, unless someone started one of the group's other PRs, and the PRs it found to be no duplicate. A group without a comparison since a member joined, merged or closed, and one settled without a model, frees none. An operator's ruling on a pair (`by_operator`) frees its two items from each other. A PR that only fixes a duplicate issue is in no such group.
- **Priority.** Confirmed duplicates raise the original's priority.

Models: Jev, Haiku (pair checks); Opus and Sonnet (group comparison). Daily limits: 2000 pairs for the check, 200 comparisons for the group comparison. Writes nothing to GitHub.

## Classify

Every open item gets one type label (bugfix, performance, missing feature, small extra, plugin candidate, infra) and two flags (security, needs decision).

- Jev first. Haiku gives a second opinion when Jev is under 90 % sure of the type or unsure of a flag. Items of repos with the pipeline on come first.
- While Jev is unavailable (see Waits), Haiku classifies every due item and its label and flags settle the item (source Haiku). Items Haiku settled stay settled when Jev returns; Jev classifies them again only after their text changes.
- A type is settled when Jev is at 90 % or more, or Haiku agrees with Jev. A disagreement among the scope labels (missing feature, small extra, plugin candidate) stays unsettled: no referee call and no type label.
- Each flag follows the same rule on its own, whatever the type's state. Security: Jev at 0.9 or more sets it, under 0.3 clears it, in between Haiku's flag counts. Needs decision: the same with 0.8. Until Haiku has answered an unsure flag, the flag is not set (no label, no priority bump). A settled bugfix keeps needs decision only when Jev is at 0.7 or more.
- Other disagreements (for example bugfix against missing feature) go to the Sonnet referee, which applies the classification rules and says whether it is sure. A sure label settles the type. When Sonnet is unsure, Opus referees the same item with the same prompt. Opus's label settles the item either way; an unsure Opus also sets the needs-decision flag, so the PR stays off the automatic path. The referee has its own step and daily limit.
- Started by the operator for a full pass; the pipeline classifies new and changed items on its own. Daily limit 2000.
- A classify job works in slices: Jev asks 40 items at a time, and after half its deadline the job starts no new chunk (the first chunk always runs). It ends done, saying how many items are left, and the items still due make the next job due at once. The area questions run only while the job is inside its slice, or when it cleared the last due item. A job whose items got no answer at all fails ("Jev answered none of N items"), so the failure backoff spaces the retries. The job's handled count is the items answered.

### Areas

A repo can have an area list: 10 to 25 parts of the app, each with a name and a one-line description. Repos without a list skip this question. A list is saved in versions; the highest version is current.

- Classify asks Jev one more `choice` question per item, among the repo's areas plus "none of these". The descriptions are the criteria; a pull request's evidence includes its changed file paths (from the cached diff). Jev at 90 % or more settles it. Below that Haiku decides, and Haiku decides alone while Jev is unavailable. "None of these" is a valid answer.
- `item_areas` holds one row per item: area (empty for none of these), source (jev, haiku or operator), Jev's confidence, the list version asked against, and the time. An item asked against the current version is not asked again; operator-set rows are never asked.
- An operator, or a maintainer with GitHub write permission on the repo, edits the list on the repo's page: add, rename, merge two areas, remove, edit a description. Each save is a new version. Renamed and merged areas re-point their items; the items of a removed area become unassigned. Items whose area survives move to the new version.
- Unassigned items (no row, none of these, or removed area) are counted per repo. Re-scan (`areas-rescan`) asks them again against the current list.
- Propose (`areas-propose`): one Opus call per repo, with read-only tools on the default branch and the workspace (docs, `docs/gaps.md`) and a sample of open item titles. It returns a list that waits as a proposal; accepting it (as it is or edited) saves a version.
- Suggest (`areas-suggest`): Sonnet reads a sample of unassigned items and suggests up to 8 new areas. The operator accepts or ignores each one; accepting saves a version and queues a re-scan.
- Propose, suggest and re-scan are started by an operator or a maintainer with write permission on the repo. The assignment itself runs inside `classify-new` and `classify-all` and counts against their limit.
- CLI: `autocraft-server areas list|propose|accept|edit|rescan|suggest --repo R`.

## Priority

Each open item gets a level from P0 to P4.

| Level | Meaning |
|---|---|
| P0 critical | Crash, data loss, security hole, broken build or install, unusable app |
| P1 high | A core feature is broken, or a regression |
| P2 normal | An ordinary bug, feature or change |
| P3 low | Cosmetic, wording, docs, nice-to-have |
| P4 backlog | Kept open but not worked on now: vague or wishlist requests, ideas without a clear ask, very large asks with little reach. Plugin candidates are P4. |

- Jev picks the level; under 90 % sure, Haiku decides. While Jev is unavailable (see Waits), Haiku rates every due item. The security flag raises the level by one, up to P0.
- Reach (0 to 99) breaks ties inside a level: commenters, comments, linked PRs, confirmed duplicates, the security flag and age. No model. It is not shown.
- Models run again only when the item's text changes; reach is recomputed from the mirror on every pass.
- Unrated items count as P2. Daily limit 3000 items sent to Jev; raise it for the first pass over a new org.
- Implement skips P4 issues: no code is written for the backlog. Everywhere else P4 items come last. Review still reviews P4 PRs.

## Work rank

One key per open item decides what the pipeline works on next, for issues and PRs alike. No model; recomputed whenever the items, priorities or fix estimates change. Items are ordered by, in turn:

1. Level, P0 first.
2. Type: bugfix, performance, infra, missing feature, small extra, plugin candidate; not settled last.
3. Size, smaller first: S, M, L, XL.
4. Reach, higher first.

- The key is one integer, `(4 - level) * 10000 + type * 1000 + size * 100 + reach`, so every candidate list sorts by it.
- PR size comes from changed lines: up to 50 S, up to 300 M, up to 1,000 L, more XL. An issue counts as M until the Implement plan estimates its size.
- Review, Implement, Fix-up, Verify and the merge queue all take the heaviest started item first (see Weight), then the highest-ranked item.
- When Review and Implement both have work, the one with the higher-ranked item starts first. Daily limits still cap both.
- Queue position: an item whose next step is a queued stage (Review, Fix, Fix-up, Verify, Merge) has a place among the in-scope items (repo switch on or started, not our own integration PRs) with the same next step, heaviest started items first, then in work-rank order; Merge places follow the Merge tab's order. It shows as a badge such as "Review #3" on Items, Queue and the item page, and links to that stage's Queue tab with the item highlighted (`/queue/review?item=<repo>:<number>`). Items waiting for a person, running, held or done have none.
- The Work queue page lists every open item in rank order with its level, type, size and next step.

## Starting and answering

Nobody's model time goes to an item nobody picked. A maintainer starts an item with a command, and answers one recommendation when AutoCraft comes back.

- **Commands.** `review`, `fix-up`, `implement`, `merge`, `drop <part>`, `ask author [<words>]`, `backlog`, `close` (`as completed`, `as not planned`, `as duplicate of #n`), `hold`, `resume` and `autorepin`, alone or combined (`fix-up and merge`). `ask <question>` is no command: it asks Opus about the item and runs nothing (see `ask <question>` under the item's conversation). `fix` alone is `fix-up`; `fix 1` fixes one part of a plan; `fix <instructions>` ("fix the UV seam normals, then merge", "fix: use the importer's welded normals and merge") has the fix-up do what the words say. The instructions run up to a comma, full stop, `and` or `then` before the next command word or weight. Words after `fix` that match a part's title name that part; only words that match no part are instructions. Negations, hedges and questions in them leave the message unread, as anywhere. The same text works in a GitHub comment that mentions the app, the Discord slash command, the dashboard's text box and an agent's tools (`src/workflow/parse.ts`, no model call). Text that is not fully understood runs nothing; AutoCraft answers with what it read.
- **Who.** Someone with an AutoCraft login as operator or maintainer, write access on the repo, read live, while writes go out as the GitHub App (`access.canAct`). Any of them may answer for any item of the repo, and their name is kept with the answer. The question goes to the person who started the item and the one who approved its merge (`src/workflow/asked.ts`): only they get the Discord alert, see it among their own items, are named under "Asks" in the item's status comment and are pinged once in a reply to it (PR status comment, below). A PR only the merge rule took up asks nobody when it stops: its state line reads "Stopped: <reason>. AutoCraft would: <recommendation>", and a maintainer's `yes` runs that and takes the item over.
- **Entries.** `review` runs the review and comes back; on an issue it reviews the issue against the code (see Reviewing an issue under Review), and `review and implement` goes on to implement when that review recommends it. `fix-up` also makes the review's fixes and is for a PR. `implement` is for an issue. `merge` puts a PR in the merge queue with no model review; the pre-merge review, Verify, CI and GitHub's gates still apply. A command that says `merge` is refused on a PR that is not aimed at the default branch and in a repo without CI, where nothing merges; on a PR that conflicts with its base branch, its confirmation says who settles the conflict. One workflow works on a PR at a time: the PR of a live implementation takes no start and no `backlog` of its own (the reply says how the issue stands), and an issue whose PR was started on its own is not implemented over it. Every other command on that PR acts on the issue's workflow as if written there: answers, `merge`, `drop`, a weight, and `hold`, which ends the work on the issue and its PR from either of them. `close` there closes the PR and ends the issue's workflow; the issue stays open. `merge` again from the person who approved it tries a merge that waits for their sign-in or write access once more.
- **One recommendation.** An item not approved for merge comes back when its steps are done, with one sentence of what AutoCraft would do and its numbered parts. `yes` (also `lgtm`, `go ahead`, `proceed`, `continue`) runs it, and so does `merge`, which then also approves the merge; a command runs that instead; `fix 1 and 2, drop 3` picks parts. `fix <instructions>` has the fix-up do what the person wrote, as their trusted instruction (the operator fix-up: any file a fix-up may touch, the person recorded as its maker), together with the parts the plan still has; the merge approval carries on as for any push of AutoCraft's, through the review, CI and the pre-merge review. On a PR nobody started it starts at Fix-up with that fix first. A bare `fix` where the review lists no fix fixes the finding the question shows; where the review wrote no finding either, nothing runs and the reply asks what to fix. The confirmation quotes the instructions: "Fixing “the UV seam normals”, then merging when CI is green". An answer is for the commits its question was asked about: when someone other than AutoCraft has pushed since, on any surface, nothing runs and the reply says so. The question goes, and a new one that says the author pushed takes its place: at once when the merge is approved (a blocker), else when the steps are done at the new head. AutoCraft's own pushes leave the question as it is. The answer covers what its question could show: a push of AutoCraft's, a review, a failed step or a failed verification that came between the question and the answer was not seen, so the push is reviewed and counted, and what stops an item stops it again. The answer is for the question its surface showed (the item page, the items list, `get_item`, the Discord alert; on GitHub, the one open when the comment was written): when another took its place since, nothing runs and the reply shows the new one.
- **What a PR comes back with.** The review writes the recommendation with what a yes runs: the fixes it names (then merge, or come back), a merge, a close, the author's turn (`author`), or the backlog, only for a hold that waits for other items. A recommendation that runs nothing is dropped. A hold whose PR is incomplete or wrong in a way its author settles (code nothing calls, a regression it brings, pieces it claims that are missing, tests that do not cover what it claims) asks the author at once, with no question first (Waiting for the author, below). A hold that raises a question of scope (beyond the reference app's behaviour, or beyond what was agreed; `scope`, also when both kinds come together) comes back first, asking whether the change is wanted: "Do you want pinned tabs? If yes, ask the author to wire in the group editor; if not, close it.", and a yes asks the author. Without a recommendation, the workflow builds it from the verdict: a close closes; a hold with no planned fix that waits for other items it names goes to the backlog; any other such hold quotes the review's finding and asks the author, at once when its blocking class says it blocks the merge, else with a question first; any other verdict fixes the planned parts and merges, or merges (also an unsure take: the yes is the judgement the review could not make). The review covers its head, so an item never comes back asking for another review of that head. A hold with fixes on a PR that conflicts with its base branch recommends the fixes, with the base merged in first: a person's fix-up queued at the head lets the conflict step merge the base into a PR its review holds, and the fix-up follows at the merged head. Where only the contributor or a person can resolve the conflict, it recommends asking the author to resolve it with the findings. A bare `fix` on a hold fixes what the review found.
- **Merge approval** is a flag of the workflow: once given it carries through every later step, and the merge is made as the person who gave it. It is taken as the person pressing the merge button on GitHub: AutoCraft does everything the merge needs first. A blocking finding of the review is fixed by the review's fix-up; a review that says hold or close (one that waits for other items aside), the pre-merge review's defects left after its own fix-up rounds, a failed verification and screenshots that show a regression are fixed by a fix-up AutoCraft asks for as the approver, with the review's parts and finding, the defects as parts, or what the check found as its instructions (`fixFirst`, `src/workflow/advance.ts`). Its push is reviewed and checked again, and the PR merges on green CI. An approved item comes back only at a blocker (`src/workflow/blockers.ts`): commits by someone else that the review round finds beyond what was approved, a step that failed twice (two failed fix-up or CI fix tries since the approval or the last answer; a job of the PR's own lane that ends without a try is retried after the step's failure backoff and shows in the health checks; four such jobs of one step in a row at one head, past their deadline or in a crash, ask once, and the question closes once a job of that step runs through there or the PR has a new head; a runner stop or restart, a model call no Task Runner took in time, the GitHub write pacing and an outage (an HTTP 5xx answer, a network error) count for nothing), a fix that could not be made (the fix-up failed, grew too large or cannot run, or no fix-up can be asked for: its tries are used up, or the branch takes no push), a hold that waits for other items, or a stop only a person can settle (below). The word `merge` on an open recommendation runs what it recommends, then merges: "fix 1, then merge" fixes 1. Where the recommendation is another review before the merge, `merge` has it made too; only where the pre-merge review or the review failed for good does `merge` go on without it, as the question says. A review that a push of AutoCraft's owes is made either way, and a PR of another entry needs a review at its head.
- **Task Runners in the confirmation.** Model calls run only on people's Task Runners. When no Task Runner can take the work a command starts or approves, its confirmation says why, on every surface: "No Task Runner can take this right now (<reason>). It starts when one is free." The reason is the first of: no ready one that may take the repo offers a model of the work's tier; the others that may take the repo are held by their usage limit (until when); the sender's own Task Runner is not connected, held by its usage limit (until when), cooling off, not ready, or may not take the repo (role rules, write permission); the ready ones do not take the repo (My repos, write permission, or they take only their users' own items); none is ready. An implementation runs only on the sender's own Task Runner or that of someone who took the item's work, so for an implement command only those count, and a sender without a Task Runner reads that the implementation runs only on their own. A sender with no Task Runner of their own also gets "Set up your own Task Runner: `<base>/connect`", whether or not another can take the work. The rules are the claim's: the Task Runners of the sender and of the people whose started work it already is count whatever their Manual only, My repos and tasks; another person's under that person's settings (`src/core/runner-room.ts`). Ends, autorepin and a weight alone get no such line, and neither does work the automatic merge rule starts. When a queued call of started work later cannot run (no Task Runner may take it, which the dashboard's minute check marks and withdraws after 10 minutes; or, past the 10-minute hold for its people, it waits only for their Task Runners and none of them can claim it; or an implementation call that neither its starter's runners nor a taker's can run), the same line goes once per workflow and reason into the item's chat and the Discord threads that follow the item. It is about the person whose runner the call waits for (the one an implementation is bound to, or the first of the people whose runners alone may take it), else the person who approved the work, else the one who started it, named by that role ("the starter's Task Runner is not connected"); it is not posted when the latest command was answered with that line, and never goes to GitHub. Viewers, and Discord threads of items that show only their status, read "Waiting for a Task Runner". A command refused because the item is already approved for merge says where the work stands and the steps still to come.
- **Text the parser cannot read.** An option of an implementation's open question named on its own ("2", "go with one archive") is no such text: it answers the question as typed, also on the implementation's PR. Text that asks, negates, hedges or sets a condition ("one archive?", "not 2") names no option. `ask <question>` is no such text (see `ask <question>` under the item's conversation). Other text, from someone who may send commands on its items, on any surface, is read by a model before the reply: Haiku (`command.read`) on the sender's own Task Runner, outside its slots, else (`interactive.command-read`) on any Task Runner with a free Interactive slot, never on pipeline slots. It gets the text, the command words and each item's kind, state and open question with its numbered parts, and gives one command, `ask` when the text is only a question, or none. A command that the parser cannot read in full, or that names an item the text does not, is dropped. A quiet item's text goes only to the sender's own Task Runner. Jev (`command.read.jev`) scores whether the text asks for exactly that command. The command runs as if typed only with Jev's score at 0.9 or more (`READ_RUN_SCORE`, `src/workflow/read.ts`), with the message's own items (none or only the item it was written on; exactly the items a list names), and with no condition the parser found and no negation, hedge, question or condition word in the text (the parser's guard, the words an unclear reply never reads back, and if, after, when, until, once, before, later, tomorrow), unless the command is `hold`; the confirmation line then says it was read from the sender's words. A reading of `ask` uses Jev's second score, whether the text is only a question, and no hedge rule: at 0.9 or more, on a text about one item, on the dashboard or GitHub, the text is asked as `ask <text>` would ask it, and the reply says it was read as a question; otherwise the reply proposes `ask <text>`. Otherwise, and always without a Jev score, the reply proposes the command to send. With no reading (no Task Runner took the call, it failed, or the model found the text unclear) within 45 seconds, or 90 for a GitHub comment, the reply is the parser's own. A GitHub comment is read off the comment drain and read again from GitHub just before its command runs; deleted or changed meanwhile, nothing runs and nothing is answered. The texts of the calls are deleted when they end; each reading is a `read` event with the text's hash, the command, the score, its source and whether it ran.
- **A wait on a person is a question.** A started item whose plan has nothing due and waits for a person comes back with one (an approved item at a blocker, any other with its recommendation), and a `yes` runs something:

  | The item waits because | A yes |
  |---|---|
  | its approver (or, not approved, everyone it acts for) has no write access any more, or the merge could not be made as its approver for lack of access | goes on in the name of the person who says it, who becomes the approver. Once the approver can act again, the question closes by itself; where the merge itself was refused for their access, once they sign in to AutoCraft again, which has it tried again |
  | it failed alone in a batch, or the merge was refused for good; not approved for merge, its verification failed or its screenshots show a clear regression (an approved item has these fixed first) | merges it: the next hand-over tries again. Once what refused the merge changed (CI, the merge state, a later merge try), the question closes by itself |
  | the review asks for fixes AutoCraft's fix-up could not make and nobody else is asked: they change files AutoCraft may not edit, the branch takes no push from AutoCraft, they are over AutoCraft's size limits, or the fix-up cannot run | the question names each fix and why it could not be made (`withoutFixes`, `src/workflow/ask.ts`). A fix that blocks the merge (major, or of a blocking class) is never dropped: on a PR approved for merge a yes makes it again, then merges; where only the author can make it (files AutoCraft may not edit, a branch it cannot push to), and on a PR not approved, the author is asked, at once when nobody approved it. Fixes that do not block go to a follow-up issue, and a yes merges. Where a hold row of the fix-up stopped it (too large, no push), or the try that ended the merge leg, and that row is superseded, the question closes by itself; on a PR approved for merge the fix-up runs again while its tries last |
  | its review failed for good, the review asks for fixes and lists none, a comment to the contributor could not be posted, CI stays red after the CI fix (it could not repair it, had nothing to fix, or our own push broke it), or the implementation session ended without what its PR needs | reviews it again (a review's fixes the session left are made by a fix-up). Where the review failed for good, the word `merge` starts the PR at the merge queue in the name of the person who says it, as it would on an item nobody started: it takes the place of the work so far and merges that head without the review. Where an earlier review of that head asks for fixes nobody dropped, or says hold or close, the question names them and `merge` has them fixed, or the review made again, before the merge; once AutoCraft pushed more than a checked merge on that head, `merge` approves the merge and the new head is reviewed. Where CI is red, `merge` approves the merge, which waits for green CI; the question closes by itself once CI is green |
  | its base is not the default branch, the repo has no CI, GitHub keeps the merge state unknown, or its CI runs could not be approved | looks again; the question says what to do on GitHub first, and comes back while nothing changed there. Once it is settled there, the question closes by itself |
  | the issue's implementation ended without a pull request | implements it again |
  | the pre-merge review of the head failed for good (after about a day of tries) | gives it one more try there, and if that fails AutoCraft's slow tries of a day again; the merge goes on once it is clean and CI is green. The word `merge` goes on without it |
  | a fix-up AutoCraft asked for to fix what stops an approved merge could not be made | tries the fix-up again, then merges; the question names what was not fixed and the last try's reason. The word `merge` merges it as it is, past the review or check the person was shown and the pre-merge parts it would fix. `drop <n>` of every blocking pre-merge part overrules those findings instead: the drop is recorded with the person's login and the head, and the merge goes on with green CI without a new pre-merge review, nor a pre-merge fix-up of the dropped findings. The drop holds at that head and at the heads AutoCraft's own pushes make from it; once the author's commits are accepted, a finding of the same title stops the merge again |
  | the author pushed again after 10 review rounds that UTC day (`AUTHOR_ROUNDS_PER_DAY`), a runaway backstop that normal work never reaches | reviews the new commits, counting again from the answer. At 00:00 UTC the question closes by itself and the new commits get their review round |
  | a conflict on a PR approved for merge that AutoCraft cannot resolve and would otherwise leave to the contributor | looks again; the question says to resolve the conflict on the branch or ask the contributor to, and is asked once at that head. Once GitHub says it merges, the question closes by itself |
  | the review holds it until other items are settled | reviews it again (not approved for merge: puts it in the backlog). Once none of those items blocks it any more (closed, merged, or an issue nobody is asked about), the question closes by itself and the PR is reviewed again |

  A question that closes by itself leaves the item with the plan and the approval it had, at the head it was asked at or pushes of AutoCraft's on it; the item's history names why. After someone else's push it stays a question. Every question has a cause the workflow pass checks again: its own where the table names one, else the plan's wait that asked it, which goes once the plan, with the question closed, no longer stops there. On a PR approved for merge that holds only for waits the facts say whatever the merge leg does (a conflict a person resolves, a merge state GitHub has not computed): asking stops the leg, so a wait that the leg's hand-over or hold made stays a question until someone answers it. A wait closes so at most once per head: when it comes back there, only an answer closes it. A step that failed twice is counted again, and the stop goes once fewer tries count (a try was superseded). The pass also runs when a timed wait in the item's facts ends. Closing a question posts nothing on GitHub.

  Nothing is asked where the person acts somewhere else: a hold, a missing repo approval, a maintainer's changes-requested review, the approver's sign-in, a conflict a person resolves on a PR nobody approved for merge, an open pull request, a circuit breaker, the switch to the GitHub App, or another item's open question that blocks the review. The state line says who must act there, and where the item waits for the contributor. A contributor is asked before a step that failed twice is a question, once per answer. A PR approved for merge never waits for its contributor without a question: review fixes our fix-up cannot make and conflicts our step cannot resolve go to the approver, as red CI does.
- **The review round.** Commits someone else pushes to a PR approved for merge are no blocker by themselves: the approval stays, and the PR goes back to review at the new head (`src/workflow/advance.ts`; every surface shows the step "review the author's new commits"). The merge leg ends at the push and a new one starts at a head the round accepts, which then needs green CI and a clean pre-merge review as always. A leg that had already stopped at a check of the earlier head (red CI, the pre-merge review's defects, a failed verification) says nothing about the accepted head either: the new leg checks it, and the item goes on without a question. Opus reviews the commits after the head the workflow accepted (`base_head`) in the light of the whole PR: the prompt input carries `author_commits` with the approved head, the new head and the files the new commits touch, and the delta is what the PR's own diff gained and lost since the earlier review (or the approved head when none was made after it), so a merge of the base branch shows only the author's own changes. Each head's own diff is its diff against its merge base with the base branch, computed with git in the shared repository cache (heads a force-push dropped are fetched by id), or read from GitHub's compare when git cannot read it (`src/review/round-diff.ts`); it never depends on a runner's diff cache. With the delta separated, the size cap applies to it, not to the whole PR, which the reviewer reads in its checkout. When the delta cannot be separated the whole diff is reviewed if it fits the cap; otherwise, and when the delta itself is over the cap, the round stops for the approver (blocker `other`) with that reason, and a yes accepts the head. The review says in its `workflow` column whether the commits stay within the approval (`author_commits.in_scope`): fixes, answers to review or CI, a merge of the base branch and small adjustments within the PR's purpose are in scope; new functionality, a large growth of the change, changes to CI workflows, build scripts or agent instruction files the approval did not cover, and anything suspicious are not. In scope (or a review that does not say) accepts the head, and the review's findings count as any review's; out of scope stops the workflow at the `author-commits` blocker, naming the review's public summary, and a yes keeps the commits. A push that leaves the PR's own diff as the latest sure take or take-fix review read it (a merge of the base branch, a rebase) carries that review to the head without a model call or a Task Runner (`roundCarry`, `src/review/opus.ts`, from the same own diffs), and with it the approval. The round's review is not held by CI, the daily cap or the interval, and a merge-queue entry owes it as one a person asked for. A PR gets 3 rounds a UTC day since its person last went on with it; at the fourth push the workflow stops at `author-commits` (round `daily-cap`) and a yes reviews the new commits (`roundsToday`, `src/core/author-round.ts`). A review that failed for good stops the workflow (blocker `other`), and a yes asks for it again. A workflow stopped at the author's commits before the round existed has its question withdrawn on its next pass and goes to the round.
- **What runs while it asks.** An approved item at a blocker (state `blocked`) keeps only its bookkeeping: triage, the post of a finished review, the release of its assignment, the post-merge steps, a close a person commanded, and the end of an implementation whose PR merged or closed. No review, check, push or merge of it runs until a person answers. An item that asks with its recommendation is not approved: its reviews and checks go on (`src/core/gates.ts`).
- **Weight.** `urgent`, `high` and `low` (10, 8 and 2; normal is 5), or `weight <1-10>`, in a command or alone on a started item. Heavier items go first in every stage; items of equal weight go in the order they were started. Started items of weight 3 and up go before items nobody started, those of weight 2 and below after them (`src/core/work-score.ts`).
- **Hold and resume.** `hold` ends all work on an open item, its place in a batch included, and AutoCraft keeps off it, the automatic path included, whether someone started it or not; the item shows who holds it. A message that is only `stop`, `pause`, `wait`, `hold on`, `not yet` or the like (`no, stop`, `hold the merge for now`, `stop. I will look`) means the same; in a longer message that asks for something else they run nothing. `resume`, `continue` or a yes from any maintainer (not `yes, merge`, which could mean either) goes on with what the item had (`blockerParams.held`): its open question again, or its steps, with its merge approval now in the name of whoever resumed it. The resume accepts no commits: those the author pushed meanwhile make a question first, and AutoCraft's own since the approval still count as made after it. Follow-up issues that wait for the merge go on waiting. An item nobody started goes back to how it was, and an issue whose attempt the hold ended before it had a PR starts a new attempt with the same plan and approval; one whose PR was merged or closed meanwhile ends. A start command starts a held item as ever. A start, an approval or a resume written before the hold is refused, however late it runs.
- **Waiting for the author.** `ask author`, `ask the author to …` (on a pull request; the words after it, up to the next command, are the person's own for the author; words that start with a question mark or a hedge make the message ambiguous) and a review recommendation that asks the author post one comment to the PR as the app (the act step, `src/act/index.ts`): a ping to the author, the review's public summary, the titles and files of the fixes nobody dropped (texts that passed the review's reply checks), a line asking them to merge in or rebase on the base branch when the PR conflicts, and the person's words. The review asks by itself only when it was made after the person last started or answered the item and its hold is classed as blocking; otherwise its recommendation comes to the person as a question first. AutoCraft never asks a bot, itself, or the author of a quiet PR: the question then recommends the backlog. A comment that is not posted (it failed three times, or the PR moved under someone else's push) brings the item back to the person as a question with the reason. Everything that runs on the PR ends, and nothing else of AutoCraft's runs on it, no model call included, until the author pushes (state `waiting`; the state line reads "Waiting for <author>: <what was asked>", with "asked after the review" when the review asked; the Items filter `autocraft:author`). A comment of theirs without a push keeps it waiting; there is no timer. Their push ends the wait and their new commits are reviewed: on a PR approved for merge through the review round, which goes on to the merge; otherwise a review of the new head, which comes back with its recommendation. Any command replaces the wait; `ask author` again posts a new comment with the new words. A PR approved for merge never waits for its author because of a review finding: AutoCraft makes the fixes itself, with the base branch merged in first when it conflicts. `merge` beside `ask author` approves the merge too.
- **Backlog** ends the workflow and leaves the item alone until someone starts it, the automatic path included. So does an answer that leaves nothing to run or merge (`drop 1` to "Fix 1, then come back with the result."): neither the automatic path nor the merge rule takes the open PR up. Follow-up work that was running is ended.
- **Automatic path.** A PR nobody started runs by itself when its label is bugfix or infra, its size S or M, its author whitelisted and its label settled without doubt, in a repo whose Pipeline switch is on. Two things leave such a PR to a maintainer, who starts it or not; its status names the reason:
  - It duplicates another open PR, or a merged one (see Duplicates: Held). Closed unmerged PRs do not count.
  - The cached diff of a head no review stands at already keeps it off the merge rule (its size, or content a person looks at). The review step reads the diff before its model call, so such a PR costs none. While the diff waits for what the rule reads beside it, it counts for nothing.
- **A started item** runs through every stage even when its repo's Pipeline switch is off; other work of that repo does not. The command is the approval of the merge and the pushes it asks for, so the repo's Merges and Pushes approvals, which are for work nobody started, are not needed; the global switch, the other per-repo approvals, daily limits and the merge checks still apply. An approved PR is pushed to and merged only at a head a person accepted, or at our own pushes on top of one; its reviews run at any head. Model calls the automatic path queued for the PR before a person started, approved or resumed it are withdrawn then, and its own jobs do that work; a call already running finishes and its result applies. A model call whose items have all merged or closed is withdrawn too, and its result, if one comes back, is discarded.
- **A refused command changes nothing.** What a start or an answer needs (an open PR that is not a draft or an integration PR, the head the sender saw, no merge of another workflow under way) is checked first; then the workflow, its merge leg and the event are written together.

Started work acts for people: its merge for the person who approved it, everything else for whoever last answered, approved or started the item and may act on the repo. It stands while AutoCraft can confirm their access. Once they lose their role, or GitHub answers that they have no write access, the item keeps only the bookkeeping named above and asks for someone to take their place. The GitHub App reads the permission again every 8 minutes for the people whose work is under way (`refreshSettlers` in `src/preapproval/permissions.ts`). While GitHub has not confirmed it for an hour, or not yet at all, and while writes go out as the box account, nothing is pushed or merged on their behalf and no implementation runs; reviews and checks go on, and nothing ends. A failed read is made again after a minute.

The record of every start, answer, hold and resume is `workflow_events`; the item page lists it.

## Label

Writes each settled type label and flag to GitHub. No model.

- Only settled types are labelled. A label a person set is never changed: items with a different type label are skipped and reported.
- Needs the repo's **label approval**. Without it the stage only plans.
- Writes in batches, at most 60 a minute. A re-run skips items already labelled. Each batch first reads the live state of its items; an item that is no longer open is skipped, counted and its mirror row updated.

## Review

Code review of open, non-draft PRs that a person started (any entry but merge), whatever their label, and of the PRs of the automatic path. A PR already reviewed at its current head is skipped; a push brings it back. Reads GitHub, writes nothing.

One Opus pass reviews every wanted PR at a new head, docs-only and translation PRs included. Opus's verdict is the **final** one.

Step `opus-review`, one PR per call, highest work rank first, daily limit 40 PRs. The step `checks` runs before it in the same lane. Opus reads the repo with read-only tools in a sandboxed checkout of the PR head, as the Opus prompt `review.opus` describes; PR text and diffs are quoted as untrusted data. The Opus reviews (`review.opus`, `premerge.opus`, `postmerge.opus`) run at high effort with a task budget (`taskBudget` in the prompt catalogue, passed as `--task-budget`, the API's `output_config.task_budget`): it counts what the model writes, thinking included, and the tool results it reads; the model sees it count down and paces itself to finish within it, and nothing is cut off. A review without tools gets 80,000 tokens and one with tools 120,000 (`sandbox.taskBudget`), about twice what 99 in 100 reviews with tools used. A normal review stays well below it. The flag is added when a Task Runner takes the call, not stored with the queued call; a Task Runner whose Claude Code is older than 2.1.309, or did not report its version, gets the call without it. Before the calls, the candidates' live state and heads are read in one query; a PR that is closed, a draft or at a different head than selected is dropped and returns as a candidate on the next pass.

Step `review-carry`, one repo per call, calls no model, so it runs while Claude is paused. A head with no review whose only new commit since a sure take or take-fix review is our own fix-up of that review's fixes, approved by the patch check, gets the earlier verdict as a `carried` take, with the discussion mark of the earlier review; one whose only new commit is our merge of the base branch that left the PR's own diff the same keeps the earlier verdict and its fixes. On a PR a person approved for merge the earlier review may be unsure (the carried row keeps its `sure`), and any number of our commits carry, each one carriable by itself: a fix-up of the review's fixes, a fix-up of the pre-merge review's defects, or an operator's fix-up of parts of the plan alone whose files are all files of those parts (the parts it made leave the carried fixes; a fix-up of the review's fixes that started after the merge approval made only the blocking ones, so the fixes that do not block stay on the carried review, as take-fix, to be filed as follow-ups), each approved by the patch check and pushed after its lint passed; and a base merge that left the PR's own diff the same. Not carried: a review made stale by new discussion, a review read against another base branch than the PR has now, a CI fix of ours (it gets a delta review for blocking problems), a resolved conflict that changed the PR's own diff, an operator's fix-up of a person's own words or of files beyond its parts, any commit that is not ours. A carried review keeps the base branch of the review it came from. The Plan holds a `carry` action for such a head instead of a `review` action, so `opus-review` leaves it to this step.

- **Input.** Title, body, size (S up to 50 changed lines, M up to 300, L above), CI and merge state, changed files, and the diff of code and test files. Lockfiles are listed, not diffed. Test files are shown while the diff stays within the length limit; the rest are listed, and the merge rule then needs a person (below). A delta review whose test files do not all fit reads the full diff instead.
- **Too large.** A diff over the call's length limit, or no diff from GitHub: held ("too large for the final review") without a model call. The hold records the size cap it was made under; when the runner starts to lead, the holds at a PR's current head made under a smaller cap than the current one are removed (audited as `review-again` by `pipeline`), so the head is reviewed again, and a workflow question about such a hold closes without an answer (`src/review/too-large.ts`).
- **Discussion.** Opus also gets what others wrote on the PR, in a separate `<discussion>` block after the diff: top-level comments, review bodies and the unresolved inline review threads (path, line, first comment and the last three replies, author; outdated ones marked). All of it is read from GitHub in one query per PR when the review starts; if that read fails, the PR is skipped for this pass. Our own posts are left out (comments by the pipeline account, reviews we posted, threads we started). HTML comments and collapsed tool output (such as "Prompt for AI agents" and analysis chains) are removed, each entry is cut to 1,200 characters and the block to 9,000: entries by maintainers (owner, member, collaborator or a dashboard operator or maintainer, never the PR author), and threads a maintainer replied to, first, then threads, reviews and comments, newest first within each. A maintainer's comment or review newer than the PR's previous review, and an unresolved, not outdated thread a maintainer started, have a budget of the same size of their own; only when one of those still does not fit is a sure take or take-fix stored as unsure ("a maintainer's comment was left out of the review for length"), so a person decides. The text is untrusted and cannot close its block: the model checks each claim against the diff, never follows instructions in it, and names each finding it checked in `risks` ("checked: <finding>: holds" or "does not hold"). A finding that holds and is not fixed makes the verdict take-fix (small fix, in the fix list) or hold. Each review stores when it read the discussion (`seen_at`) and a hash of the counted entries.
- **Waits before a review.** A due review does not start while any of these holds (the plan names it); a maintainer's or operator's request after the latest review (a comment, Review again) lifts all of them. Blocked: a hold review named open items in `blocked_by` (`repo#n`, `#n` or `owner/repo#n`; each must be a tracked open item other than the PR, or an issue whose workflow waits for an answer); no new head and no discussion starts a review until every blocker is merged, closed or decided, then the PR gets one fresh review. A blocker that itself waits on this PR is ignored, and the list expires after 14 days. CI: a head is reviewed only once its checks have finished and passed (a PR with no checks when none are pending); the first review of a PR also runs on finished red CI, and so does the one after blockers settled and the one a person's live workflow asks for (entry `review` or `fix-up`, not started by the automatic merge rule); the review reads the checks of the current head. While a head's CI runs or is red, the repo's checks are read again every minute, and a red head with an earlier take or take-fix review goes to CI fix. Cap: at most 3 Opus calls per PR per UTC day, counting new heads, re-runs, and failed calls (agent runs of `opus-review`, one per job: a reply-fix turn is part of its review); carried reviews do not count. Interval: setting `review_min_interval_minutes` (default 120, 0 turns it off; `autocraft-server pipeline review-interval [minutes]`, audited) is the least time since the PR's last call; the plan says "next review after hh:mm" and the planner wakes then. A head made only by our own pushes since the last review skips the cap and the interval. A change of the PR's base branch is no request: its re-review waits like one after a push and counts against the cap. Failures: a call that gives no valid review waits 10 minutes, then 30 minutes, then 2 hours at that head, then 6 hours four times, so the head is tried for about a day; the eighth failure holds the head until a new commit, Review again or a maintainer's comment, and a pre-approved merge or a workflow asks then. A call that ended without a reply (its Task Runner lost it, the runner stopped, an HTTP 5xx or network error) is counted apart: it waits 10 minutes, 30 minutes, 2 hours, then 6 hours, and the call after 4 of them counts as a model failure, so these too end with a person; a person's request goes ahead of that wait, and the daily cap still counts it. The pre-merge review counts such calls the same way: no try until 4 in a row. A carry waits only for CI. Delta reviews, once a review runs, are as before.
- **Stale reviews.** New discussion makes a PR's review stale when a *counted* comment or review is newer than the review's `seen_at` and the hash of the counted entries differs from the one the review read. Counted entries are the PR author's and those of authors with association owner, member, collaborator or contributor, but at a head that already has a review only a maintainer's (owner, member, collaborator or a dashboard operator or maintainer) makes the review stale; the PR author's comments are read by the next review without starting one. On a PR a person approved for merge no comment makes the review stale: a maintainer who wants a new review says `review`, and the next review reads the comment anyway. Others are shown to the model but never trigger. A one-line comment that only addresses a bot (`@coderabbitai resume`, `@dependabot rebase`) is never counted. Bot accounts never trigger (GitHub type Bot, a login ending in `[bot]`, or a login on the review-bot list, default `coderabbitai`, `dependabot` and `renovate`, set with `AUTOCRAFT_REVIEW_BOTS`), even when the bot is the PR author; empty bodies and bare approvals never trigger. A review is also stale when the PR's base branch is not the one its diff was read against (a review stored without one counts as read against the default branch; rows stored before bases were recorded took the PR's base at the upgrade): the PR author retargeted it, which the mirror, the review's own diff read or a live read before a merge records. A stale PR is a candidate again at the same head, subject to the waits below. A re-review at the same head against another base branch deletes the head's pre-merge review and makes its verification stale: both were made for the old diff. A pre-merge review counts only for the base branch the head's Opus review read. Until a PR has an Opus review at its head, it has no final verdict and no queue state, and it cannot merge; an integration batch that contains it is rebuilt without it. Just before a single or batch merge the discussion is read live again; a maintainer's or operator's entry the review did not read stops the merge and marks the PR stale (the PR author's comments do not, and on a PR approved for merge no comment does). A re-review at the same head asks again what its earlier review asked. The posted review is edited when a newer Opus review exists at the same head. Reviews made before snapshots existed count as having read everything up to the migration. `autocraft-server review again <repo>#<n>` (operator, audited as `review-again`) marks a PR's review stale by hand, ignoring the waits.

| Verdict | Meaning |
|---|---|
| take | Wanted, correct, nothing to change |
| take-fix | Wanted and nearly right; small mechanical fixes are listed |
| hold | Needs a person: unclear reference behaviour, design or scope choice, too large |
| close | Wrong or broken beyond a small fix, not wanted, already done, or superseded |

Opus also returns a complete fix list for take-fix, its reasons and `sure`.

- **Final verdict.** The latest Opus verdict at the PR's current head. A PR with no Opus verdict at its head is not reviewed yet.
- **Unsure.** A take or take-fix with `sure` false stays take or take-fix, so Fix-up, Verify and CI proceed. It never merges without a person's approval, and the recommendation says Opus was unsure. A PR approved for merge goes on through an unsure review, also one made after its hand-over (see [Pre-approved merge](#pre-approved-merge)); being in the queue for any other reason does not count. Unsure sticks: every stored review is also appended to `opus_review_history`. The chain of a PR is its current head plus the heads AutoCraft pushed it from (conflict merges of the base, fix-up pushes). If any review in the chain was a take or take-fix with `sure` false, the PR merges only approved for merge and handed over at its current head; a later sure review does not lift it. A head the author pushed starts fresh. A skipped review never merges by rule.
- **Blocking classes.** On the maintainer workflow each fix of a take-fix, and a hold, carries a blocking class with one sentence why, the same four as the pre-merge review's defects (`regression`, `security`, `data-loss`, `off-purpose`) or none (`src/core/review-blocking.ts`). A fix or hold without a valid class, and every review stored before the class existed, counts as blocking; a fix or hold the claims rule makes from a code-wrong claim is `off-purpose`, and a fix it makes from a code-incomplete claim has no class. On a PR a maintainer approved for merge only blocking fixes run as a fix-up, major or not, and only a blocking hold gets a fix-up of its own before the merge (see Merge approval): a take-fix whose fixes all do not block, or a hold that does not block, counts as a take, and the PR goes on to CI, the pre-merge review and the merge. A hold that names items it waits for (`blocked_by`) always stops it and asks. The fixes and hold reason that do not block are filed in the PR's follow-up issue (step `premerge-followups`, table `review_followups`, one row per reviewed head, see Blocking and follow-up defects) before it merges; non-blocking fixes alongside blocking ones are filed, not made. Changed lines the review counts outside the PR's purpose (`outside_purpose`, with a one-line note) stop nothing: on a PR that goes on, a note of at least 20 lines that passed the reply checks is filed with them, once per PR, and listed with the follow-ups in the review's post. The filing is planned at the PR's current head while the reviewed head leads to it through the pipeline's own pushes, so the fix-up of the blocking fixes pushing first loses nothing. A hold's follow-up is known by its reason, so a later, different hold is filed too; a hold that gave no reason files nothing. The review's code-incomplete claims that it did not turn into one of its fixes (a claim that named no fix, or any such claim of a hold that goes on or that a person answered) are filed with them, worded as the pre-merge review words the same claim ("Claim holds only in part: …"), so a gap both reviews raised is listed once. A claim turned into a fix is filed or made as that fix. A carried review files the claims of the review it was carried from, and the fixes that do not block that our fix-up left. Its filing is the row at the nearest head of its carry chain that has one: a head filed before files nothing again, and one whose try sent nothing is tried again there after its backoff, so the order of the carry and the filing loses nothing; no fix-up targets a claim without a fix, so such a claim stays open until a later model review at a newer head no longer raises it. These claims are filed whether or not a pre-merge model call ran: a carried pre-merge review (the review cut) reads no claims. The classes are asked for only on the maintainer workflow, and only there is a missing one a lint problem. A part a person dropped is neither made nor filed. On the automatic path and on a PR not approved for merge every fix and hold counts as before.
- **Re-review after our own commits.** On a PR approved for merge, a delta review whose only new commits are the pipeline's own (`pipeline_commits`, no `author_commits`) looks only at those commits and only for blocking problems, as the review round does for the author's commits; anything else goes in its public points.
- **New push.** Opus reads only the changes from the head it reviewed last to the new head, with its earlier review as context. If GitHub's compare fails or the old head is not an ancestor (force push), it reads the full diff.
- **Duplicates.** Duplicate PRs are handled by the Duplicates stage; the review does not name them.
- **Stored** per PR and head in `opus_reviews` (verdict, sure, reason, fixes, risks, mode full / delta, base head, and `base_ref`: the base branch the PR's diff was read against). A delta review runs only when the earlier review read the PR against the same base branch; after a retarget the whole diff is reviewed. A PR merges only into the default branch, alone or in a batch, and only when `base_ref` is the default branch (checked before a single merge, when a batch is built, and again for each member before it merges). The `final_reviews` view reads it; every later stage reads the view. Integration batches get no Opus review of their combined diff.

### Posting the final review

Step `review-post`, only in repos with **comment approval**; calls no model. For each open PR with an Opus review and a public text at its current head that no review of ours describes yet, it posts one pull request review with event COMMENT (never an approval or a change request). PRs by the pipeline's own account, integration batch PRs and items outside the pipeline's scope are left out. Daily limit 40 posts and edits. A dry run (`autocraft-server review-post --repo R`) lists the bodies without posting.

- **Live check.** Right before posting the PR is read from GitHub. Only an open PR whose head is the reviewed head gets the review; any other is skipped and returns after a new review at its new head.
- **One review per PR.** The review's node id and head are stored in `review_posts`. An Opus review at a later head edits our earlier review (`updatePullRequestReview`) instead of adding another. Each post and edit is audited (`review-post`, `review-edit`).
- **Body.** A fixed template (listed on the Prompts page as `review.post`): an italic first line, `AI-generated review (Opus 5.5). Not a maintainer decision.`, with the model name and version taken from the model id stored on the review; a verdict line in neutral words (take: no blocking problems found; take-fix: small fixes needed; hold: changes needed; close: significant problems found; a note when Opus was not sure); the `public` summary and points that Opus wrote for the PR author (plain statements about the code, with file:line, at most 8 points; no mention of other reviews, models, CI state, mergeability or the pipeline); on a PR approved for merge whose review found fixes or a hold that do not block it, the titles of the fixes made before the merge ("Fixes before the merge:") and of the follow-ups ("Follow-ups, to be filed as an issue:"), with the verdict line "Nothing found that blocks the approved merge:" when no fix is left to make; one `Recommendation: …` line (below); and `Reviewed at <short sha>.` Opus's internal reason, fixes and risks are never posted. A review without a valid `public` field (`opus_reviews.public_review` is null) is not posted; the PR gets its review after a later Opus review at a new head. The model's text is untrusted: mentions, HTML tags, links other than to github.com under the repo's owner, and issue references are removed until nothing more changes (removing one piece can join its neighbours into a new one), then the Markdown link syntax left outside code is escaped (the same cleaning, without kept links, serves the post-merge issue and the Act and fix-up reasons); each item is one line of at most 600 characters, and the body is cut at 6000 characters; the Recommendation line and the `Reviewed at` line are reserved first and never cut.
- **Recommendation.** The last line before `Reviewed at` says what the pipeline does next, derived at posting time from the PR's merge queue entry and whether its merge and our pushes are approved (by a person for this PR, or by the repo), and recomputed when the review is edited at a new head. Take, on a path to merge and the merge approved: `merge after CI and checks pass.`; take otherwise: `merge, after a maintainer's decision.`; take-fix: `merge after the fixes above.`, with `; they may be pushed to this branch.` when our pushes are approved and maintainers can modify the PR; on a PR approved for merge with follow-ups, `merge after CI and checks pass; the follow-ups above will be filed as an issue.` when no fix is left, else `merge after the fixes above; the follow-ups will be filed as an issue.`; where the repo's approvals refuse the filing, the follow-ups are listed as "Follow-ups (not filed: <reason>)" and the line names no issue; hold: `update the pull request; it will be reviewed again.`; close, or anything unclear (no queue entry, declined): `wait for maintainer feedback.` The line names no rule, tier, score or account.

Hand-off, by final verdict: take goes to Verify, take-fix to Fix-up (with Opus's fix list) when the entry or the approval allows fixes. Hold, close, and any verdict of an item not approved for merge, come back as the item's recommendation.

### Reviewing an issue

Steps `issue-review` and `issue-review-post`, for an issue a maintainer started with `review` or `review and implement` (any surface). One job per repo works every due issue of it, up to four at once (`src/issuereview`). `issue-review` makes the model calls; `issue-review-post` calls no model, so its posts never wait for a Task Runner, and it is the only step that posts.

- **Request rows.** The start writes a row in `issue_reviews` with who asked; `review` again on the issue's review writes another, and so does a yes to a question for the reporter. The planner plans `issue-review` while the issue's live review workflow has a queued row, and `issue-review-post` while it has a comment or a question to post (`issueReviewStep` in `src/core/decide-item.ts`).
- **The call.** One Opus call (`review.issue`, effort high) with a read-only checkout of the default branch head. It names the issue, so it is started work of the issue's workflow: the Task Runners of its starter and approver take it first, and any runner after the started-work hold. Input: the issue's title, body, labels and author, its discussion with the same inclusion rules as a PR review's, and the duplicates and open PRs that close or mention it. Reply: what the issue asks, whether it still holds with each claim at `path:line` (a claim without one goes back as one fix turn, then is left out), related items, size and the files a fix touches, approach, risks, and one recommendation: implement, close (completed, not planned, or duplicate of an issue), needs info (with the question for the reporter) or backlog. A call without a valid review is made again after 10, then 30 minutes; after the third the maintainer is asked whether to try again, and a yes reviews it again.
- **The comment.** The review is stored on its row and posted as one comment on the issue as the app, with the model's disclaimer line, ending with `Recommendation: …`. The start of the person who asked is the approval of the comment. A post that sent nothing (no app token, write pacing, GitHub's rate limit) is tried again after 10, then 60 minutes, as other unsent writes are; the question waits for it. After those tries, or a post GitHub refused, the question goes on without the comment and starts with `The review comment could not be posted: <GitHub's answer>`.
- **The question.** The advance pass makes the review's recommendation the issue's open question: a yes implements the issue (the workflow becomes an implement one, with its own rules), closes it as the review said (as the person, through Act), sends it to the backlog, or posts the review's question to the reporter (no model call; the row that posts it keeps the review). A question GitHub refuses, or whose post tries end without sending, comes back as `The question to the reporter could not be posted: <GitHub's answer>`: a yes posts it again, without a model call, and `implement`, `close` and `backlog` still answer it. After the question is posted the issue waits for the reporter (`Waiting for the reporter's answer`); once the issue's author comments after it, the issue is reviewed again on the same row, with the same backoff after a call without a valid review, and comes back with a new recommendation. Any other command answers it as usual: `implement`, `close`, `backlog`, `hold`, `review`. `merge` is refused on an issue's review; `implement and merge` approves the merge with the implementation.
- **`review and implement`.** A review that recommends implement starts the implementation without a question; any other recommendation comes back as the question. A yes to review again after three calls without a valid review keeps the `and implement`.
- **An issue being implemented.** `review` on an issue whose implement workflow runs reviews its implementation pull request again; while the implementation has no pull request yet it is refused (`The implementation of <issue> has no pull request yet.`). `review and implement` there is refused: implement runs already, and `review` alone reviews its pull request.

## Implement

Implements an issue a maintainer queued and opens a pull request for it. Needs the repo's `implement` build feature (Repos page, Build features; an operator, or a maintainer with GitHub write permission on the repo, switches it), and a person who may act on the repo to queue it.

- **Queued.** An issue is queued by the `implement` command of a person who may act on its repo. Nothing is picked up automatically. A queued issue waits while an open PR closes it, and its wait names that PR as the one to answer; a PR that only mentions the issue holds nothing.
- **Task Runner.** Every model call of an implementation runs on the Task Runner of the person who queued the issue, in one of its normal slots. When that runner is not ready, the item shows the wait. Once that person may no longer act on the repo, the work runs for whoever last answered it or approved its merge and may act, on their Task Runner; when nobody may, the issue and its PR show the wait.
- **Plan.** Opus reads the issue, its comments and the repo in a workspace pod and returns a plan with acceptance criteria, the verification it will run and its size. The plan is shown on the item page and goes into the PR body.
- **Questions.** When the issue leaves facts open, the author gets one comment from the bot (reply-linted). When it leaves choices open, the issue's workflow asks a maintainer, as its recommendation with numbered options. The pipeline account is unassigned while the question is open. New issue text or an answer plans again.
- **Session.** Opus writes the change and its tests in a session in the same workspace, with the repo's formatter, linter and tests, and for a UI change the built app. Nothing the session says about its own checks counts.
- **Checks.** AutoCraft runs `cargo fmt --check`, clippy filtered to the changed lines and the tests of the affected crates itself. Findings go back to the same session, at most 3 rounds.
- **Diff.** The diff is checked by code: no trust paths, symlinks, submodules or mode changes, at most 3,000 changed lines and 80 files, binary files at most 1 MiB. Cargo manifest changes are allowed and flagged in the PR body.
- **PR.** Pushed to our fork (or the base repo on the app identity) as `autocraft/impl-<n>-<slug>`, titled "Fix", "Add" or "Change" plus the issue title without URLs, mentions or issue references, opened with "Fixes #N.", and the issue gets one comment. The queuer's merge approval is recorded, so Review, Verify and the merge queue follow as for any PR. A take-with-fixes review or a red CI on the PR goes back to the same session while the issue's work is live; after it ended, a PR started on its own gets the normal fix-up and CI fix.
- **Stuck.** An unparseable plan, a failed session, a `blocked` report, checks that still fail after 3 rounds, a refused diff or repeated push failures stop the workflow at a blocker with its recommendation: try again, open as a draft PR (only when the diff passes the checks), `backlog` or `close`. At most 3 attempts per issue text.
- **Live check.** Right before the push and the comment the issue is read from GitHub. A closed issue gets no PR.
- **Breakers.** Two of the last ten implementation pushes of a repo that turn a required check red stop the stage for that repo; maintainers with write permission resume it.

Models: Opus. No daily limit.

## Fix-up

For a take-fix review, Sonnet applies the listed small fixes to the contributor's branch, so the PR need not wait for them.

- **Needs** the repo's **push approval**, a pushable PR and no conflict. A PR is pushable when its head branch is in the base repository itself (GitHub reports no maintainer edits for those) or maintainers may modify it. A head branch in the base repository is never pushable when it is the repo's default branch, the base of any open PR, or named like a long-lived branch (release, main, master, develop, stable, hotfix, integration). Otherwise the PR is held ("cannot push"), with no write.
- **Stopped pushes.** A fix-up or CI fix whose job stopped at its push is settled by the next read of the PR's checks, which carries the head (the merge lane has them read once no running job holds the PR): pushed when the commit is on the branch, else pushed again from its stored patch or made anew, not counted as a fix-up try.
- **Cannot push.** In a repo with **comment approval**, one comment lists the fixes (at most 6, cleaned of links and mentions), once per head, if the head is still the reviewed one. The PR shows as "asked the contributor"; a new head goes back to Review. Without the approval it stays held. A head recorded as asked becomes a fix candidate again when the PR is now pushable. The same comment is posted when the fix-up cannot be made on a pushable branch: the fixes are too large or name files a fix-up may not edit, or the 2 tries are used. A PR in needs-fix-up always names what it waits on: the contributor's fixes, the contributor's merge of the base branch, the new review of our pushed fix-up, or a repo approval (comment or push).
- **Safety.** The checkout is untrusted: no working tree, hooks or filters run. The diff may touch only the files named in the review, at most 300 lines. Only Rust files and Markdown files (`*.md`, outside hidden directories) may be edited, never a trust path (build scripts, `.cargo`, `.github` and the other tool-configuration directories and files, agent-instruction files; the same list every model-patch lane refuses); a fix list naming any other file holds the PR ("the fixes name files a fix-up may not edit"). Holds of that kind whose files are all editable are tried again. Hunk header line counts are recomputed from the hunk bodies before the checks, since models often miscount; a refusal for a wrong count is not one of the 2 tries. On a quiet pull request (a security fix not yet published) the prompt carries the quiet rule and a patch whose added lines contain a giveaway word is refused like any other refused try; the stored reason names neither the word nor the fix. A quiet pull request is never asked for changes (the ask comment would list the review's fixes): it is held instead. An operator fix-up's comment on it names the files only.
- **Size.** With a sandbox checkout the model reads the files itself: the files the fixes name are listed by path, and no size limit holds the PR. A PR diff over 60,000 characters is shown to the model and to the Opus check as at most 60,000 characters (`src/fixup/diff-view.ts`): a list of the changed files not shown whole, then the diff sections of the files the fixes name and, smallest first, of as many other files as fit. When the named sections alone are over the limit, they are kept whole smallest first while they fit, and the next one keeps its whole hunks in order within the room left, with a note of what it leaves out; the rest are listed by path. A run whose checkout could not be made skips such a PR, and the next run tries again. Without a checkout the files are pasted: a file over 40,000 characters is shown in part, and a PR whose diff is over 60,000 characters or whose shown files are over 120,000 is held ("too large").
- **Opus check.** Before the push, Opus reads the PR, the review's fix list and our patch. A reject pushes nothing, records the try as "rejected" with Opus's reason and counts as one of the 2 tries; the check is recorded with the patch hash.
- **Assignment.** A PR is assigned to the pipeline account when the stage starts work on it (after the cheap checks pass, before the model call; a conflict merge before the base merge), only when nobody is assigned. See Merge queue, "Assignment" for when it is released. No "in progress" comment is posted: the comment after the push covers it.
- **Live check.** The PR is read from GitHub before the model calls and again after the Opus check. If it is no longer open, is a draft or its head moved, nothing is assigned or pushed and the PR is tried again on a later run.
- **Push.** One commit "Apply review fixes", pushed with a lease so a branch that moved is left alone, plus one comment from a fixed template. When the newest comment on the PR, read live, is our own review-fix comment and no review came after it, that comment is edited instead to list the files of both rounds (the first line, then "Pushed further fixes from a later review: ..."); carry and operator comments are always posted new, and if the read fails a new comment is posted.
- **Conflicts.** An open, non-draft PR whose final review at the current head is take or take-fix and that GitHub reports as conflicting gets the default branch merged into its branch (same scope, push approval and pushable rule as above; the PR need not be take-fix). Nothing is checked out. `git merge-tree` computes the merge. A clean merge becomes a commit with two parents (the PR head first), "Merge <base> into <branch>", pushed with a lease; there is no rebase and no force-push. With conflicts, Sonnet (sandboxed, read-only tools) gets each conflicted file as numbered conflict sections, not whole: for each section its id and start line, about 30 lines before and after (shared out where sections are close), the pull request's side and the default branch's side (each with its newlines, so no lines and one blank line differ; the start line is the one in the PR head's file), plus the file's path and line count, quoted as untrusted with the PR title, description and review summary. It returns one resolution text per section id. Our code accepts the reply only when every section is answered exactly once and no other id appears, with no conflict markers. It splices the answers into the merge-tree file, so text outside the sections cannot change. Each answer may use lines from the two sides, each side's own lines in that side's order, plus at most 3 others, none of which adds an import, declaration, attribute, unsafe code or a dependency. A Rust file is read as tokens, so spacing, comments and line position do not matter: a line on neither side may hold no item word, attribute, `unsafe` or `name! {` macro call, and the answer, read in the resolved file, may hold no more of them than its two sides read in their own files (a line uncommented out of a side counts as new). In other files a line taken from a side the answer does not keep whole is tested like a new line. A lockfile section takes exactly one side; a manifest section (`Cargo.toml`, `package.json`) takes only lines of its sides, each in the same table and under the same keys as in its side. Only files a model patch may edit are resolved (the trust paths every model-patch lane refuses: build scripts of either parent, CI and tool configuration, agent-instruction files; manifests and lockfiles under the rules above), and a file whose head or base version has lines shaped like conflict markers is refused; a file with CRLF line endings is resolved as LF text and written back with CRLF; a file with mixed or bare CR line endings, or invalid UTF-8, is refused. A PR whose base is not the default branch is skipped, so only the default branch is ever merged in. Merge-tree and the file reads use the plain two-sided marker style, ignoring user and system git config. Opus then checks the resolution: it gets each section (about 10 lines of context, both sides, our resolution) and the PR's own diff, not the diff of the merge, which also holds everything the default branch changed. A reject pushes nothing and counts as a try; so does a resolution so long that the check's input goes over its limit. A resolution with Rust files is stored and linted before it is pushed (one build task: rustfmt on those files, clippy on the merged tree); the formatter's whitespace changes are folded in by the harness. Clippy findings on lines the resolution changed go back to Sonnet with the earlier resolution's diff, and the new resolution gets the same validation, Opus check and lint; the stored row keeps the state `linting` between rounds, and the next collect picks the re-lint up. After 2 lint rounds with findings left, the try is recorded as rejected with the first finding as its reason. Afterwards one comment from a fixed template ("Merged <base> into this branch to resolve the conflict."). When the newest comment on the PR, read live, is our own earlier conflict note and no comment or review came after it, that comment is edited instead ("Merged <base> into this branch to resolve conflicts (3 times, last at 04:47 UTC)."), with the note line of the latest merge; if the read fails, a new comment is posted. The PR is assigned to the pipeline account only once the checks that need no model pass (conflicted paths, markers, line endings, section sizes). A refusal that the same head always gets again (those checks, the conflict sections over the size limit of 120,000 characters shown to Sonnet or 40,000 for one section, or the conflict sections over the check's 80,000 character limit, measured as the check receives them with the longer side of each section standing in for its resolution; that bound is computed before the claim) is recorded once as held for that head: no second try, and no assignment when it was found before the model call. A model-dependent failure (Sonnet's answer fails our validation, Opus rejects) counts as a try, at most 2 per head; tries count against the daily limit. A PR we can't push to gets, in a repo with comment approval, one comment per head asking the contributor to merge or rebase <base>; without the approval it is held with no write. The new head goes through Review (Opus reads the PR's full diff for a merge commit of ours, not a delta that would include the base branch's changes) and Verify like any new head.
- **Live read.** What the live read shows (conflicting, closed, draft, head moved) is written to the checks table, so a PR that is no longer a candidate is not selected again until the checks sync changes it. A PR that reads as conflicting goes to the conflict merge.
- **Hand-off.** The new head is reviewed again. At most 2 tries per PR. Daily limit 20 PRs, pushes and comments together.

Models: Sonnet (patch, conflict resolution), Opus (patch check).

### CI fix

A PR we want (final review take, or take-fix once its listed fixes are pushed or posted) whose gate check failed at its reviewed head gets a CI fix. Candidates are open, non-draft PRs in the pipeline's scope, not held, not on Backlog, not conflicting and not blocked by a maintainer's changes request, whose checks were read at the reviewed head and fail. The changes-request test is the merge queue's: a live read newer than the PR's last change decides, otherwise the mirrored reviews and the review decision do. When the failed checks include ones with "gate" in their name, only those count; otherwise every failed check does. Limits: at most 2 tries per head, and per PR over all heads at most 2 pushed CI fixes and 4 tries (our own pushes make new heads). A PR at its limit stays `ci-failed`, with a note on the item. Steps `cifix` (no daily limit) and `cifix-rerun` (daily limit 30 PRs).

- **Reading.** Nothing is read while a required check at the head still runs: GitHub serves a run's log only once the whole run has ended, and refuses to rerun the failed jobs of a run in progress. Then the failed check runs of the head and, per failed run, the failed steps' log (`gh run view --log-failed`) are read from GitHub, cut to the last 4,000 characters per step. When `gh` cannot split a job's log into steps (every line names `UNKNOWN STEP`), the job's log is cut to the lines up to its last `##[error]` line before the post-job cleanup, named after the step that line ends. A log that cannot be read yet (GitHub has none to download, or it holds no failed step of the check) is recorded `unread`: not a try, read again after 5, 15 and 60 minutes; one that still cannot be read after that is a failed try. Read-only. The log is untrusted: a prompt quotes it as data. A head whose gate checks all passed (an optional check failed), or with no failed check run (a commit status or a run waiting for approval failed), is recorded `skipped`: final for the head, not a try.
- **Triage**, from the log text and no model. A cancelled run: *skip*, final, not a try. A timed out or startup-failed run, or a network or runner error with no compiler or test error in the log: *infra* (tested before format). Only the formatter failed and the log holds its `Diff in <path>:<line>` lines (a step name alone is not enough): *format*. A failed check that is no GitHub Actions job (no log at all): a failed try. Anything else: *code*. Failed tests that nothing in the log ties to the PR's changed files (no build or lint error, and no failed test's module path or panic or backtrace location in a changed file) look flaky: where the repo's CI approval is on, the failed jobs are rerun once first, as for *infra*, and a code fix follows only when they fail again.
- **Format.** Only files that are in both the PR's diff and the log's `Diff in` lines are formatted. The build task's environment is read from the PR's base commit, never from the PR's own workflow. The task copies the PR head and runs the image's `rustfmt` by absolute path on those files (no glob expansion), offline, from outside the checkout, under an empty environment with the toolchain paths fixed, so the PR's `.cargo/config.toml` aliases, `rust-toolchain.toml` and environment do not apply. The result is accepted only if it is formatting alone: the Rust token streams of each file before and after must be identical (identifiers, literals with their exact contents, comments, punctuation; only whitespace between tokens may differ). A reordered `use`, an added trailing comma, a changed string or comment, or `/ *` turned into `/*` is `refused`. It also passes the same checks as a model patch (Rust files only, at most 300 changed lines, the guard below). No model call.
- **Infra.** The `cifix-rerun` step records the rerun (`rerunning`, then `rerun`) before it calls `gh run rerun --failed`, once per head, when the repo's CI approval is on. After the rerun the failure is read again: an infra failure again is a failed try only when the failed checks completed after the rerun was requested (older results are waited on, for at most 2 hours; waiting does not count against the step's limit); anything else goes on as code.
- **Code.** Sonnet (prompt `cifix.patch`, high effort, sandboxed read-only checkout) writes a diff from the log and the PR's code. A PR diff over 60,000 characters is shown as the fix-up shows it, with the files the log's compiler locations name in place of the files the fixes name; without a checkout the try fails. The editable files are the PR's changed Rust files plus files named on a compiler location line (`--> path:line`) directly after an `error` line. Our code applies the patch to the head with git and judges git's own diff and the files before and after it, not the patch's hunk headers. It refuses a patch that edits a test file or CI config (only `.rs` files outside the trust paths are editable), adds or changes an `#[allow]`, `#[ignore]`, `#[expect]`, `#[warn]`, `#[cfg_attr]`, `#[cfg(...)]` or `#[should_panic]` attribute or a `cfg!` call (read from the patched file's tokens, however the attribute is split over lines or commented), removes a test or an assertion, changes a line inside a `#[cfg(test)]` item (before or after the patch), or adds an early `return;` to a test function. Opus then checks it with the Fix-up check prompt, told the goal is to make the failing check pass without changing what the PR does. On a quiet pull request (a security fix not yet published) the prompt carries the quiet rule and a patch whose added lines contain a giveaway word is refused.
- **Push.** Like a fix-up: needs push approval and maintainer edits, pushes with a lease on the head, and posts one comment. Just before the write the PR's reviews are read live: a changes request, or reviews that can't be read, record `skipped` instead. A branch we can't push to gets the patch as one comment in a repo approved for comments; elsewhere nothing is written. Every try is a row in `ci_fixes` (shown with the fix-ups on the item page). The row is written as `pushing`, with the commit about to be pushed, before the push, and replaced by its outcome after; fix-ups and conflict merges do the same, and the push chain includes `pushing` rows, so a crash between a push and its record keeps the head in the chain and an unsure review earlier in it still needs a person's approval. The post-merge review lists CI fix pushes with the other pipeline commits.
- **Exits.** Every exit records a state. A head that moved or a PR that closed after the work began is a failed try (a moved head is also noted in the checks data); a patch comment that fails is `comment-failed`, final; a formatter task's `formatting` row is closed by whichever state follows.
- **After.** Upstream CI on the new head decides. The Flow page counts the Fix-up node's CI fix states: to read, to rerun, pushed, gave up.
- **Giving up.** A PR a person approved for merge (or started at the merge queue) is never handed to its contributor: when the CI fix gives up or reaches its limit, the merge leg stops and the workflow asks that person, naming the failing checks and the CI fix's last try. A PR nobody approved gets one comment that names its author and the failing checks (`asked`); a PR AutoCraft's own push broke is a person's.

**Red default branch (`main-fix`).** Needs the repo's "Fix red main" approval (off by default; `autocraft-server main-fix-approval` lists it, the Repos page switches it, with the other write switches). The step runs per repo when the pipeline is on and the repo's current default-branch head is `red` (see Main CI), with a daily limit of 20 heads or fix attempts (`main-fix`). For a red head with no rows yet it reads the failed gate checks and log tails with the CI fix reader, and Haiku (prompt `mainfix.classify`, medium effort, no tools) sorts each failed check. The step's model calls are started work of the person who gave the approval (see Started work on its owner's Task Runner): their own Task Runner takes them first, outside its repo choice and in a slot under their Max calls at once, and other Task Runners after the hold or when theirs cannot. One row per (repo, head, check) goes into `main_fixes` with the verdict and a state:

- `flaky` (a timeout, a network error, a cancelled job, a lost runner): the failed jobs are rerun once with `gh run rerun --failed`; the row is `rerun-requested` before the call. When the head turns green the row is `rerun-passed`. When the head is red again after a new reading (or 10 minutes after the rerun), the check counts as `code`.
- `infra` (an HTTP 401 or 403 from a service, a missing secret, a quota, an external service down): nothing in the code is wrong. The step opens one issue per (repo, check, culprit) with the run link and a scrubbed log excerpt, under the repo's main CI fix approval: the row is `issue-opening` before the create and `issue-opened` after it, and later red heads of the same streak reuse the number. A create that was interrupted, or whose answer was lost, is settled by the next run from its audit row and, when that does not tell, by looking for the issue on GitHub; only an issue GitHub does not show is opened again. A refused write ends as `issue-failed`.
- `code` (a compile error, a failing test, a lint or format failure): the row is `needs-fix`. `onCodeVerdict` in `src/mainfix/index.ts` is the one place the fix PR step takes over.

**Fix PR.** Each `needs-fix` row of an approved repo gets one attempt (per repo, head and check; `src/mainfix/pr.ts`), counted against the `main-fix` daily limit each time the model is asked:

0. One attempt covers all the `needs-fix` rows of a head: one patch, one PR (title names the first check and "+N more"), and the rows share the PR number. A head that is still running (a rerun in progress) leaves the rows at `needs-fix`, uncounted. Optional checks of the repo are never read as failures.
1. Skipped as `nothing-to-do` when main is green again or has moved to a newer head ("main is green again", "main moved to a newer head"), or when a fix PR of ours from this red streak is still open, or when an open PR opened or updated after the repo's red-since time names the failing check in its title or body, or changes a file the failure names (read with `gh api .../pulls/N/files`, at most 30 PRs). The reason carries the PR as `#N`.
   The places a failure names are its compiler errors (`--> path:line` within 3 lines of an `error` line) and Rust panics (`panicked at path:line`, with the test's thread name), with a path inside the repository (`src/core/failure-locations.ts`, shared with the batch trace); the file overlap reads only the compiler errors' files.
2. The patch comes from the CI fix path (`patchFromFailure` in `src/cifix/index.ts`, shared with the CI fix step): the failed check's log tail, the files its compiler errors name, then the panics' files, listed by path when a read-only sandbox checkout of the head is available (shown whole or as excerpts only without one), the `cifix.patch` prompt with an empty diff, the same validators and guard, the Opus check (`fixup.check`), `git apply --check` with exact line offsets in excerpted files, and the region check. It is applied to the default-branch head commit, not to a PR head.
   A patch that changes Rust files is linted before the push, asynchronously like the fix-up and CI fix lint: the step stores the patch on the rows (state `linting`, with the lint task, round and files), queues the lint task and ends. The next run of the step for the repo (due once the task ended, or the head moved on) collects it: formatter changes are folded in by the harness (the worker's diff is not trusted: it may hold only `diff --git`, `---`/`+++` and hunk lines for files the patch changes, and the tree with it applied may differ from the patched tree only in those files, with the same modes and identical Rust tokens per file); clippy findings on the patch's lines go back to the model, at most 2 lint rounds. The findings continue the model session that wrote the patch when it was last used within 60 minutes (the prompt cache window): the call is a resume of the sandbox session kept with the stored row (session id, account, session store and checkout path), on the same account, with the findings as the message, and the reply is validated, checked and linted like any patch. Otherwise, or when that account is paused or busy, it is a new call with the earlier patch and the findings. The checkout is the read-only copy of the same commit, rebuilt at the same path if it was pruned. Fix-up, CI fix, conflict resolution (one session per resolved file) and this step work this way; the kept session is removed when the row leaves `linting` (pushed, failed, dropped), at 60 minutes, and by the sweep at the start of each run. Fix issue sends lint findings through its own build rounds and starts a new call, then `fix-failed` ("clippy findings remain after 2 rounds"); a lost lint task is queued once more. A patch without a Rust file skips the lint. Nothing waits on a timer.
3. The clean commit goes to the pipeline account's fork on `autocraft/main-ci-<check-slug>-<sha7>` (`pushBranch`, fork found or created as for Implement). A PR "Fix main CI: <check>" is opened against the default branch with `ghOpenPr`: the body names the failing check with its run link, the culprit commit (and its PR when the message names one) and the patched files, and starts with the AI note (Sonnet). The row becomes `pr-opened` with `pr_number` and `pr_url`. Approval and the red head are read again right before the push.
4. `fix-failed` (reason on the row) records any other end: no patch, a refusal, an Opus rejection, a failed push. The Main CI page shows "needs a person" and nothing retries it.
   A check whose patch could not be made (no patch, a refusal, an Opus rejection) and whose failure is only in test code goes to `issue-opening` instead, because a CI fix never changes tests: every place its own log names is in a test file, inside a `#[test]` or `#[cfg(test)]` item, or in a file or module under `#![cfg(test)]`. A check whose log names no place is never test-only, and each check is judged on its own. The step then opens the red streak's issue in the same run as for an `infra` verdict (one per repo, check, culprit and verdict, settled the same way; an infra issue and a failing-test issue of one check stay apart). The issue, "Main CI fails: <check> (failing test)", names the test and its `file:line` and says no fix outside the test was found (or that the only fix found changes the test), with the run link and the scrubbed log excerpt; it is template text, no model. The row's reason says the same in one line.

The PR is one of our own Fix PRs: the merge queue counts `main_fixes.pr_number` PRs by the pipeline account as whitelisted like Implement PRs while the head is a commit the pipeline pushed (or reached from one only through its own fix-ups, conflict merges and CI fixes), and they still need green CI and the Opus review. Only such a PR (branch prefix `autocraft/main-ci-`, by the pipeline account, in `main_fixes`) is merged singly and not held while main is red; the branch name alone does not count.

A head the reader finds nothing to act on (no failed check run, or only optional checks failed) gets one `nothing-to-do` row. `GET /api/main-ci` carries each repo's row as `autocraft` ("rerunning failed jobs", "asked an operator", "needs a fix", "checking a fix", "opened fix PR #N", "opening an issue", "opened an issue #N", "could not open an issue", each of the three after "a test fails: " when that state's rows are all failing-test issues, "needs a person", "nothing to do: infra", or null). `autocraft-server main-fix --repo R --apply` runs the step by hand.

## Verify

Upstream CI is the verification for `take` PRs in a repo that has CI (the repos' CI runs the full format, lint and test gate). Verify records `ci-enough` for them without a model call or a sandbox task. The merge queue still waits for CI to be green at the head: a PR with `ci-enough` and CI pending is `waiting-ci`, and one with failing CI is `ci-failed`. Only public PRs whose CI does not fail are verified. A private repo is recorded `unavailable` ("not verified"), and the PR waits for a person's approval.

A repo has no CI when none of its latest 20 PRs ever reported a check. Until the checks of a repo were read at least once, Verify records nothing for it. In a repo with CI the language does not matter. In a repo without CI, and for the exception below, Verify builds and tests in the sandbox; that needs a Rust repo (a `Cargo.toml` at the root), and for a non-Rust repo Verify records `unavailable`.

- **Exception in repos with CI.** A bugfix PR whose diff adds or changes a test file gets a Sonnet plan limited to `regression` or `ci-enough`; a `tests` answer counts as `ci-enough`. If the diff cannot be read, CI is the verification.
- **Jobs.** One job per repo, the repos in turn. A job's due items are the repo's PRs it would plan, in its own order, at most as many as one job's limit allows (50); it plans those a Task Runner takes first. The job is proposed only while a call about one of them has a taker (Task Runner for the repo, under Waits). A repo whose only due PRs are `unavailable` needs no call for them and is proposed while a Task Runner takes the repo. A job that planned nothing because GitHub could not be read for its PRs (crate list, diff or base commit) fails, so they are tried again after the failed-job backoff (Failed job, under Waits).
- **Plan.** Sonnet, no tools, picks one kind: `ci-enough` (no task), `tests` (repos without CI only: up to 5 crates, optional test filters) or `regression` (bugfixes only: a test that fails on the base commit and passes on the head). Our code validates the plan; anything invalid is an error.
- **Result.** Pass or fail comes from exit codes only, never from a model.
- **Test name.** The regression test is `<crate dir>/tests/autocraft_regression_<n>.rs`, run as the cargo target `autocraft_regression_<n>`, with n the PR number.
- **Regression.** The test must fail on the base commit and pass on the head. If it also passes on the base, the verification fails with "regression test passes on base" and the PR is held.
- **Failure.** Haiku writes a summary of at most 60 words from the failing step's log (credentials scrubbed, quoted as untrusted). The PR is held.
- **Errors.** An environment error is retried once per head. A verification that still errors (tasks failed past that retry or gone, no plan, a diff too large to plan) is AutoCraft's own: it runs again at the head an hour after the first error, then every 6 hours, 5 times in about a day (`verifyRetryAt`, `src/core/rules.ts`; the count is `verifications.errors`). A run that wrote no result of its own (no planner answer, no crate list, no diff or base) counts as one, and a stale mark of AutoCraft's own (a new base of the diff) starts the count over; Verify again keeps it, so it gives one more run. A person's merge approval made after the error goes past it, and the error is not run again. Meanwhile the PR waits for verification and a pre-approved merge is not handed over. An error after those runs asks a person (`verification-error`), whose yes merges without it; it is no finding, so no fix-up is made for it. An operator can plan a failed or errored verification again from the Item page ("Verify again").
- **Stale.** A verification counts only at the head it was made for (the checks table's head when newer than the mirror's, as in Review); a push or a close cancels its tasks.
- **Approved merges.** A PR a person approved for merge is verified once, at the head that merges: when CI is green there and its pre-merge review has no defect that stops the merge, or its merge leg handed it to the merge queue at that head (a person's `merge` past a failed pre-merge review). Until then it waits for those steps, not for verification. A head a push of ours leaves behind is not verified.

Models: Sonnet (plan, only where the plan is needed), Haiku (failure summary). Daily limit 30 PRs.

## Merge queue

The queue lists every PR whose final review (Review) is take or take-fix at its current head ([Merge queue](/queue), read-only), with one state each: ready, waiting-ci, ci-failed, conflict, needs-fix-up, waiting-verify, verify-failed, verify-error, needs-decision (outside the rule and not approved), decision-answered-merge (approved and handed over), refused, merged, and for PRs in an integration batch batch-checking, in-batch and batch-failed. A PR a maintainer has blocked is in changes-requested (below). A PR whose Actions runs wait for a maintainer's approval shows `ci-approval` (see below).

**Optional checks.** An operator sets a per-repo list of optional checks (exact check names; `autocraft-server optional-checks [--repo R] | add R NAME | remove R NAME`, or the repo page, audited as `optional-check-add` and `optional-check-remove`; setting `optional_checks:<repo>`). A repo starts with `sonarcloud / SonarCloud Scan` and `SonarCloud Code Analysis` on its list (a repo whose list was stored before gained `SonarCloud Code Analysis` once). The queue, single merges and batch PR checks count a failure of only listed checks as success, when nothing else is pending or failing (the stored `overall` and `checks` stay as GitHub reported them; the Opus review input shows the raw state). The merge step passes `--allow-failed NAME` to `safe-merge` for each listed check. CI fix does not treat listed checks as failures to fix, and main CI shows `optional` for a failure of only listed checks.

**No new failures.** A red default branch holds nothing by itself: PRs, batches, single merges and fix-ups go on. While the repo's default branch is red (Main CI page), a PR whose required checks fail only where main fails merges as if they passed. The comparison base is main's newest settled red head, the head the branch's state comes from: the branch counts as red when its newest head is red, and also while that head's checks have not ended (`running`, or `none` in its first 10 minutes, the grace for its checks to register) and the last result is red (the head's own last result when its checks are rerun, else that of the newest head before it with a result; `main_ci.settled_state` keeps it while a rerun runs). The Main CI page shows such a branch as red with "newest head checking". For a PR head whose CI is red, when every failing required check also failed at that main head by name, the checks job reads the failed checks' logs of both heads (the CI fix's reader, every failed check, each failed step whole up to 2,000,000 characters per check and never shown to a model; main's once per red head, kept in `main_ci_failures`) and parses each failed step for its failing tests and locations (every panicking test by name, a failure of no named test by file and line) and each check for its test summary (cargo's `failures:` list before `test result: FAILED`, nextest's failed-test lines). A check's failures are not new when every failed step of it is also a failed step of that check on main (same step name), names at least one failing test or location, all of them among main's for that step, and only test targets main's step reports failed (cargo's `error: test failed, to rerun pass ...` lines and its `targets failed:` list), and its test summary lists only tests main's check fails. Then its CI counts as passing (`ci_vs_main` row `not-new`) and the PR shows "CI fails only where main fails (check)". A failing check that passes on main, a test, location or test target main's step does not name, or a summary test main's check does not fail is new: CI is red as usual. A failed step main's check does not have, a step that names nothing, a test binary that did not exit normally (`process didn't exit successfully`, `fatal runtime error`) where main's step shows none, a log over the limit, a check name two check runs carry, a log GitHub no longer serves, or a day of unread reads is new too (`unparsed`). A check whose workflow run is a rerun (`run_attempt` above 1) or was created before main's head was seen red is new for that head (`early`): a rerun keeps the merge commit it first ran on, and a fresh run comes from a push or a base update. The run is read once per run id. Until the comparison is made its CI counts as pending (a ready PR waits in `waiting-ci`, "a comparison of its CI failures with the red default branch's"), and a head due for it gets the repo's checks job in any queue state; a pre-approved leg in `ci` waits for it too. A log that cannot be read yet, or a read that fails, is read again after 5, 15 and 60 minutes, then hourly; a main log that cannot be read ends that checks job's comparisons. A new main head, or a failing check the row did not judge, means a new comparison. The merge step passes `--allow-failed NAME` for each check found not new, so a check GitHub's branch protection requires is refused there as any red check is; the refusal says so, and so does one from a merge command other than `safe-merge`, which is not given `--allow-failed`. The CI fix and an implementation's revision leave checks found not new out of what they fix, and a PR whose only failures are not new gets no CI fix. A batch PR's red CI is compared the same way in the merge job, with the default branch at the batch's base (only when that head is red with the failing checks; else its failures are new): not new, it merges; new, it is traced, rerun or split as below without the base check. PRs from branches named `autocraft/main-ci-*` (the fix PRs AutoCraft opens for a red main) merge alone and never join a batch.

**Runs waiting for approval.** GitHub holds the workflow runs of an outside contributor's PR (`action_required`) until a maintainer approves them; the check rollup does not list them, and `safe-merge` refuses such a head. The checks job reads the runs of each PR whose latest review is a final take or take-fix at the head the checks describe (one request per PR, again while runs wait) and records them in `ci_run_approvals`. A PR with runs waiting is in state `ci-approval`, never ready, until they ran. The **CI approval** (an operator's per-repo approval, setting `ci_approved:<repo>`, audited as `ci-approve` and `ci-revoke`; `autocraft-server ci-approval` shows it) lets the `ci-approve` step approve those runs (`POST .../actions/runs/{id}/approve`, audit action `ci-run-approve`). It reads the PR again first and does nothing when it is closed, a draft or at another head than the reviewed one. It never acts on PRs without a final take or take-fix review at the head, or on the pipeline's own integration PRs. Daily limit 30 PRs. After the approval the PR counts as waiting for CI until the next checks read, and then follows the usual flow.

**Drafts.** A draft is not in the queue and gets no work: its status waits for the pull request to be marked ready for review, a merge leg waits where it is, the merge step and the guard read it live before a merge, and a batch leaves it out like a closed pull request. No refusal is recorded, so it goes on once it is ready.

**Changes requested.** A formal "changes requested" review blocks the merge. A PR is blocked when a reviewer with write access has CHANGES_REQUESTED as their latest APPROVED, CHANGES_REQUESTED or DISMISSED review. As on GitHub, it stands across pushes until that reviewer approves or it is dismissed. Comments, COMMENTED reviews and reviews by people without write access neither block nor clear.

- **Live reads decide.** Reads at merge time ask GitHub for the latest review of each reviewer with write access (`latestOpinionatedReviews(writersOnly: true)`), because a reviewer's association with the repo depends on the viewer and can show as CONTRIBUTOR or NONE for a private member. GitHub's review decision CHANGES_REQUESTED also blocks, since it is empty when the repo requires no reviews and cannot decide alone.
- **Stored result.** The latest live result of each PR is kept in `review_gates`, which sync never touches. The queue trusts a live result newer than the PR's last update. Otherwise it uses the mirrored reviews (the latest 10 per PR, with the reviewer's association), where only a stranger association, an approval or a dismissal clears a block.
- **Re-read.** Each merge run reads every PR in `changes-requested` again before it builds its queue, so a block the mirror guessed wrongly clears after one live read.
- **State.** A blocked PR is in `changes-requested`: never eligible and never put in a batch, approved or not. Nothing is pushed to it meanwhile (no base merge, fix-up, CI fix or stored patch), except a fix-up a person asked for. It goes on when the block clears.
- **Merge paths.** The merge step reads the PR live before it runs any merge command. The built-in safe-merge reads the reviews live too and refuses with "changes requested by a maintainer".
- **Batches.** Before a batch PR merges, each member and the batch PR are read live. A blocked member is dropped and the batch is rebuilt without it. Changes requested on the batch PR itself fail the batch: the PR is closed with a comment naming the review, its members are held until they change, and no new batch is built from them.
- **Read failures.** After 3 failed live reads in a row the queue shows a note on the PR; the next successful read clears it.

**Merge without asking** only when all of these hold at the PR's current head:

- final review verdict is take (not take-fix)
- size S or M
- type is bugfix or infra (tests, CI, docs, build)
- author is on the whitelist (see Contributors)
- CI is green
- its base is the default branch
- Verify passed, or recorded "CI is enough" (CI must still be green at the head)
- GitHub reports it mergeable
- neither the review nor the pre-merge review at the head names a conflict with an owner statement (below)
- the diff has none of the content a person looks at (below)

**Blocking and follow-up defects.** The pre-merge review gives every defect a blocking class with one sentence why: `regression` (it breaks behaviour that works on the base branch, or the build or tests), `security`, `data-loss`, `off-purpose` (the PR's own change does not do what its title and description say; a code-wrong claim is one), or none. A claim that holds in the code the PR changes, while other paths the PR does not touch or an edge case of the working change do not follow, is a code-incomplete claim: its defect has no class, so on a PR approved for merge it is filed as a follow-up and the merge goes on. The Opus review treats such a claim the same way: its fix is a fix without a class, and one without a fix is a risk note that is filed as a follow-up of its own (see Blocking classes above). On a PR a maintainer approved for merge, only blocking defects stop the merge; a defect stored before the class existed counts as blocking. When the others are all the review found at the head, the PR gets no fix-up round and no question: step `premerge-followups` files them in the PR's follow-up issue ("Follow-ups from #N: …", one per PR, shared with the review's fixes and hold that do not block; a later head's new follow-ups are a comment on it, and a finding filed before, by file and title, is not posted again), and the PR merges on green CI. The merge waits for that filing's try, not its success: a filing the repo's approvals refuse, or one GitHub refuses, shows "Not posted on GitHub: …" and the PR still merges. A try that sent nothing (no app token, write pacing, GitHub's rate limit) is made again after 10 and then 60 minutes while the merge waits; the try after those counts as failed and the PR merges. Once merged, the item's status line says "Merged; follow-ups filed in #N", or "Merged; follow-ups not posted on GitHub" when the last filing failed. On the automatic path every defect stops the merge.

**Fix of pre-merge defects.** When every defect that stops the merge is in a file a fix-up may edit, and the branch can be pushed to, the fix-up fixes them: up to 3 rounds per PR (`PREMERGE_FIX_ROUNDS`), on the automatic path and for a PR approved for merge that is not handed over yet. A defect with no fix text of its own is fixed from its title and scenario. On the automatic path the new head is reviewed and checked again. On a PR approved for merge a round whose patch check approved it ends in CI and the merge: the review and the pre-merge review carry over to the new head with no model call, and only a defect nothing fixed still stops it. If a new pre-merge review reports a defect with the same file and title as one the round answered, the fix did not take and the rounds stop; a defect after the last round, or one that cannot be fixed this way, is a person's. A merge stopped at pre-merge defects that a round could fix at its head now (a stop made when they had none) is taken up again on the next workflow pass: the question is withdrawn and the round runs.

**Never merged.** A PR in a repo without CI, or whose base is not the default branch, is not merged, whoever approves it: a person is told why. The leg of an approved merge in a repo without CI stops, and the workflow asks.

**Screenshots.** A clear regression in the screenshots of the head keeps the PR off the rule, and out of a merge a person approved before it was found, until a person answers.

**Content a person looks at.** These keep a PR off the rule whatever the reviews say, CI and build PRs included; each is a reason on the PR's queue row and in its recommendation. They are read from the diff the reviews cached at the reviewed head (a PR whose diff is not cached waits for the pre-merge step, which caches it before its model call and makes none when the diff or anything else took the PR off the path that asked for the review), and both names of a renamed or copied file count. Beside the diff the cache keeps what the rule reads with it: the head text of edited `Cargo.toml` and `package.json` files and of lockfiles whose hunks change a checksum without naming the package, and, when a changed path could be run by name (anything but docs, images, Rust and web sources and data files), the run steps of the workflows on the default branch's current head (one listing per read, each workflow file's steps cached by blob). A diff that needs these and has no complete read of them waits: its reasons are the ones the rule finds without them (an edited manifest it cannot read counts as risky, and with the workflows unread every script-like path counts), plus `waiting to read the files the merge rule checks beside the diff`, so nothing merges by the rule meanwhile. The pre-merge step reads such a diff again with no model call, whatever the PR's state: at once, then 1 hour after each read that left it incomplete. The re-reads share the account's GitHub rate with the sync and the other steps: at most 800 run in a rolling hour across the instance, and none while the token's core rate is below the sync's reserve (1,000 points; they wait for the reset). A re-read makes 2 calls (the pull request and the compare diff), one contents call per edited `Cargo.toml`, `package.json` or lockfile it reads whole, and, when a changed path could be run by name, one workflows listing per repo and default branch in 10 minutes plus one blob call per workflow file not read before (cached by blob). After 3 such reads the rule judges with what it has. Only these re-reads count; other steps read the cached diff without fetching it again.

- the README (`changes the README`) or a file whose path names brand or logo (`changes brand files`)
- CI or build configuration (`changes CI or build configuration`):
  - anything under `.github/`, `.cargo/`, `.vscode/`, `.devcontainer/`, `.config/` or `.husky/`; a file named `build.rs`, `rust-toolchain*`, `Makefile`, `GNUmakefile`, `justfile`, `.envrc`, `.pre-commit-config.yaml`, `rustfmt.toml`, `clippy.toml`, `deny.toml`, `.gitmodules`, `.gitattributes` or `CODEOWNERS`, at any depth; agent instruction files (`CLAUDE.md`, `AGENTS.md` and the like, anything under `.claude/`)
  - a file the workflows run: a repo-relative file path named in a `run:` step, joined with the step's `working-directory` (or with the root and each `defaults.run.working-directory` when the step sets none; a working directory set by an expression matches any path that ends with the named file); a file inside a local action's directory (`uses: ./dir`); the `xtask/` crate when a step runs `cargo xtask` or `cargo run -p xtask`. A directory named in a run step (`pytest tests/`) does not count. Manifests and lockfiles named in a run step keep their own rules. When the workflows cannot be read, every `*.sh`, `*.bash` or `*.ps1` file and every file under `scripts/`, `script/`, `ci/` or `xtask/` counts.
  - a `package.json` change to `scripts`, read from the whole file before and after
  - a `Cargo.toml` change that alters a risky setting, read from the whole manifest before and after (the base is the head text with the diff taken back): the build script, `links`, proc-macro, which crates the build dependencies are (an entry added, removed or renamed), `[patch]`, `[replace]`, a git or registry source, or a path that leaves the repository. A registry version bump, of a build dependency too, is not risky. A manifest that does not parse (keys such as `__proto__` included), or whose head text could not be read, counts as risky.
- a submodule, a symlink, a file mode change, or a binary file other than an image (`changes a submodule, symlink, file mode or binary file`)
- a lockfile change beyond version updates from the default registry: a source outside it, such as git, a path or another registry (`lockfile adds a source outside the default registry`); a new checksum for a name and version already locked, read from the hunks or, when they do not name the package, from the whole lockfile before and after; poetry's `[metadata]` content hash is not a package checksum (`lockfile changes the checksum of a locked version`); a lockfile that changes with no manifest of its kind changed in the PR (`lockfile changes without a manifest change`); a lockfile renamed, copied or deleted (`renames, copies or deletes a lockfile`). Lockfiles read: `Cargo.lock`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `uv.lock`, `poetry.lock`, `go.sum`.
- test files the review could not show because the diff is too long (`test files left out of the review for size`)
- a file name the check cannot read (`changes a file whose name the check cannot read`)
- a third-party link or image added to a docs file (`.md`, `.html`, `.rst`, `.adoc`, `.txt` and the like, or anything under `doc/` or `docs/`): a URL is read as a browser reads it (character references decoded, tabs and line breaks removed, `http:host` and backslashes read as slashes, dot segments resolved, attribute values that span lines joined), and only GitHub pages of the repo's own org and the org's `github.io` pages are not third-party (`adds a third-party image or link`)

The rule's size is the changed-line count of that cached diff, so it is the size of the head the rule would merge.

**Owner memory.** What the operators said once is kept and shown to the reviews of related work. A statement is an operator's comment or review on any mirrored item (tracked repos and shared repos alike) that AutoCraft did not post (text that starts with the AI note line, and bot accounts, are left out), or an operator's message in an AutoCraft conversation. Operators are the logins with the operator role. The embed step collects new sources and embeds each statement (item title and text) with the item embedder; nothing waits for a timer. A review (Review or Pre-merge) gets up to five statements of the PR's own repo whose cosine similarity to the PR's embedding is at least 0.7, best first and newest first among equal scores, never one said on the PR itself or on a quiet security PR, each with where it was said (repo#number), its kind, the item's title, the date and the text (cut to 800 characters). The prompt shows them as a JSON array with `<` escaped, and calls the item title its author's text. The review's public text, claims and fix changes (posted in the comment that lists fixes the pipeline cannot push), and the pre-merge review's findings and fixes (which become fix-up fixes), reach GitHub without a person reading them, so both reviews' lints send back any of them that repeats a shown statement or quotes the reference pages (the overlap measure of the reference check below), and what is still flagged after the fix turn is left out of the post. The reviewer judges what a statement asks for: it names in `conflicts` (`{id, reason}`) only a statement the change goes against. A change that follows a statement, or only shares its topic, is no conflict. Unknown ids are dropped. A PR with a conflict never merges by the rule: it waits for a maintainer's approval, and its reasons name the statement's item and an excerpt. An approval lets it merge as for any other PR. The item page shows operators and maintainers each conflict with the item the statement was said about, an excerpt and the reviewer's reason; viewers see the item only. A statement said in a repo the reader cannot see is not shown, and the merge queue and the item's plan name it only as "conflicts with an owner statement".

A take PR that fails any of the first four or is not verified (Verify `unavailable`) is never merged by the rule: it shows as `needs-decision` with its reasons until a maintainer approves the merge. An approved merge needs a mergeable PR and green CI and a passed Verify (or CI is enough), except that a PR that says "not verified" needs no Verify, and past a failed verification only when the approval came after it.

A conflicting PR also shows what Fix-up does about it next to its state: "conflict: merging <base>" while the merge is queued or active, "conflict: asked the contributor", or "conflict: held" after 2 tries (or when the branch can't be pushed and commenting is not approved).

**Merge step.** Needs the repo's **merge approval**. It lands the PRs that may merge in integration batches (below), runs `safe-merge --merge`. `safe-merge` is built in (`autocraft-server safe-merge OWNER/REPO PR --squash|--merge [--allow-pending NAME]... [--allow-failed NAME]...`); it refuses unless the PR is open, not a draft, mergeable and every check and Actions run for the head finished green, and it merges pinned to that head. `--allow-failed NAME` accepts a failed check of that exact name only while GitHub's merge state of the PR is not `BLOCKED`; at least one check must still have succeeded, and the success message names the failed checks it accepted. `$AUTOCRAFT_MERGE_CMD` can name another command instead; it is called with `OWNER/REPO PR --squash|--merge --head <sha>` and must refuse when the PR head differs from `<sha>`. It never calls `gh pr merge` itself and never passes `--allow-pending`; it passes `--allow-failed` only for the repo's optional checks and the PR's checks that fail only where the red default branch fails (No new failures). A refusal is recorded with its reason and the batch stays open; any other error stops the run. A PR in a repo Verify cannot build (`unavailable`) is merged on its own through `safe-merge` (squash, or merge when the commits have more than one author). Haiku writes the failure summary of a held PR. Daily limit 10 PRs: a batch of 6 uses 6.

**Single merges.** When a repo has at most N PRs that may merge (N is the single-merge limit, default 3), and no two of them change the same file, the merge step merges them one at a time, and starts no batch. PRs the rule covers go first, then PRs an operator approved, each group by work rank. A PR that was refused at its current CI and mergeable state is left out until GitHub reports something different, so it cannot hold up the others. A workspace-level manifest or lockfile (`Cargo.lock`, a root `Cargo.toml`, `pnpm-lock.yaml`, a root `package.json`) is a file like any other: two PRs that both change one overlap. The changed files come from the PR diffs cached by Review. Before each merge the PR is read again from GitHub; it must still be open at the reviewed head, mergeable, with green CI and the same Verify result. The first PR that is not goes unmerged, the round ends (right after a merge, a PR whose mergeable state GitHub has not computed yet ends the round without a refusal on record), and the remaining PRs wait for the next round; no CI re-run is waited for. Every merge goes through `safe-merge` as above. With more than N PRs that may merge, two that overlap, or a limit of 0, the integration batches below run as usual. A repo with a batch in flight keeps using batches until that batch ends.

The limit is set by an operator on the Repos page (a number field) or with `autocraft-server merge-single [N]` (0 to 100; without N it shows the value). A change is audited as `single-merge-max`.

**Integration batches.** A batch starts whenever a repo has PRs that may merge and no batch in flight there; nothing waits for more PRs. It takes the top-ranked PR, then the other PRs of that PR's area in work-rank order, then the rest in work-rank order, up to the repo's batch size (1 to 50, starting at 20), at most about 10,000 changed lines in all; an L-size PR goes alone. The area only orders the candidates, so a ready PR is never left out to keep a batch to one area; a PR without an area joins through the rank-order fill. The merge queue shows each batch's areas. A PR that conflicts with the batch so far waits for the next batch.

1. Build `integration-<repo>-<yyyymmdd>-<n>` from the current default branch by merging each PR head with a merge commit in the cached bare clone (`git merge-tree`, no working tree, no hooks or filters). Contributor commits stay, so GitHub marks each PR merged when the batch lands.
2. Push the branch to the pipeline account's fork and open a PR to the storytold repo that lists the batch's PRs as links. Upstream CI runs on it and is the only check of the combined tree. If the push or the PR fails, the error is kept on the batch and the next try waits 1, 2, 4, 8 minutes (at most 30); after 5 failures the batch fails and its PRs return to the queue. A member that no longer passes the merge check, here or before the batch lands, leaves it: the batch is rebuilt with the others. The batch PR comes from the pipeline account's fork, so GitHub may hold its workflow runs for approval; where the repo's CI approval is on and every member was reviewed at its batched head (a take or take-fix, or approved for merge and handed over there with a clean pre-merge review), the `ci-approve` step approves them, otherwise the batch shows "batch PR runs wait for a maintainer's approval".
3. When upstream CI is green and the PR is mergeable, `safe-merge --merge` lands it. The repo's batch size grows by one.

If upstream CI fails on the batch PR, the batch is worked out without a model, cheapest first (`src/merge/batch.ts`, `src/merge/batch-blame.ts`):

1. **Red on main too.** When every failing check (optional checks left out) also failed on the default branch at the batch's base commit (from the main CI poll), and the comparison with main's failures (No new failures, above) found none of them new, no PR is blamed: once the default branch has a newer head, the batch is rebuilt on it; until then it waits, saying so in its summary.
2. **Traced.** The failed steps' logs (`gh run view --log-failed`, as CI fix reads them) are searched for compiler errors (`error...` followed by `--> file:line`; a warning's location does not count) and panics (`panicked at file:line`). Each location is blamed (`git blame`) at the batch tip in the cached bare clone; the member whose commits wrote that line is a suspect, and failing that, the one member that changed the file. When this names some members but not all, and at most 3, each of them is tested alone in a batch of its own and the others are rebuilt without them (state `split`, audit `batch-blame` per suspect with the location). A suspect is held only if it is red alone too, so a wrong trace costs one round, not a hold. The batch size does not change. Only plain repo paths are taken from the log (relative, no `..`, no dependency or `target` paths), always passed after `--`.
3. **Rerun once.** Nothing traced: the failed Actions runs of the batch tip are rerun once (`gh run rerun --failed`, audit `batch-rerun`; recorded on the batch as `ci_reruns`, `ci_rerun_at` before the calls). Red results older than the rerun do not count; after 45 minutes without new results the batch goes on to the next step. A batch that is green after the rerun merges.
4. **Split.** The batch is split in half and each half is retried, and the repo's batch size halves (minimum 1). A single PR that is still red goes on hold (`batch-failed`), with the names of the failing checks as the reason, and waits for a person: until it has a new head, an operator releases it (`autocraft-server item batch-again`), or a person answers the question a started item comes back with (or starts an unstarted one) and it is handed over anew.

A red combined-tree build (Build batches) is traced from the build log the same way before the batch splits; its test step already gets one rerun. A person closing the batch PR holds its PRs as a single red PR is held.

Rebuilds. A PR in the batch that is no longer mergeable by the rule or the operator's answer, or that was closed, merged or pushed to on GitHub, leaves the batch, as does one whose implementation session revises it or whose approver has to sign in: right before the batch branch is pushed and again right before the merge command one query checks every member for state OPEN at the batched head, and the rest are rebuilt in a new batch (merge, not rebase). In a repo whose Pipeline is off only started PRs are batched: a batch in which a PR has no live workflow is closed, its started PRs go back to the queue, and the closing comment names the others, which wait until someone starts them or the Pipeline is on again. When the default branch moves, the batch is kept if its tip still merges cleanly with the new head (GitHub's mergeable flag and upstream CI on the batch PR cover the rest); a conflict, or GitHub reporting one, closes the batch PR and rebuilds. A batch PR merged by someone else is recorded as merged.

Assignment. A stage assigns the pipeline's account when its work on the item starts (audit action `assign`): the fix-up, conflict merge and CI fix before their model call or push, the fix issue step after triage, a single merge right before `safe-merge`, and the batch step when a PR is put into a batch. It reads the assignees from GitHub first and assigns only when the item is open and nobody is assigned. It never assigns again when the audit shows we assigned it and the assignment is gone: a person who removed us is final. A later start after our own unassign assigns again; the fix-up checks again right before its push, because the planner may have released the PR while the model worked. The planner decides the release (the `unassign` step, audit action `unassign`; only the global switch is needed): the assignment stays while the PR is on the path to merge (in flight, in a batch, a fix-up, conflict merge, CI fix, stored-patch collect, pre-merge review or merge is due, or the state is ready, waiting for CI, pre-merge review, verification, CI approval or a green main, decision-answered-merge, needs-fix-up, ci-failed or refused), and is removed in every other open state (a PR whose review is stale only because of the pipeline's own push or comment keeps it, since its re-review is due): waiting on a person (needs-decision, changes-requested, held, backlog, opus-hold), opus-close, draft, review-stale, out of scope, verification failed, a failed batch, CI runs that wait for a maintainer because the repo's CI approval is off, and a stage that gave up (fix-up tries used up or the branch can't be pushed to, CI fix failed, capped or ended without a push, a conflict the conflict step only asked about or holds, whatever the queue state). A refused merge keeps the assignment, and so does a batch that could not open its PR: both return to the queue. It stays when work is due or in flight. It removes only our own assignment, only while we are the sole assignee, and reads the assignees from GitHub just before the write. An issue stays assigned while its fix attempt runs or its fix PR is open and is released when the attempt fails or is skipped, or the issue is held or out of scope. A closed or merged item keeps its assignee. The batch PR is not assigned.

Limits and exclusions. Nothing merges without green CI, also not in a repo with no CI or when a maintainer approved it. PRs Verify cannot build are merged on their own. A batch with more PRs than the daily limit has left waits, and rebuilds and splits take at most what is left. A merge job that started, opened, advanced, split or merged a batch counts as having made progress. A crash after the batch PR was created is repaired by adopting the open PR of the branch. Fetches into the shared cache retry on ref-lock errors.

The pipeline's own integration PRs (author the pipeline account, number in `merge_batches`) are left out of classify, labels, review, Opus review, duplicates, decide, act, fix-up, verify and the queue. There is no Opus review of the combined diff. The Merge queue page lists the batches with their PRs, state and batch PR.

### Queue controls

Whoever runs the repo controls what merges next from the Work queue, the CLI or the API. Every control is audited.

- **Hold** and **Resume** (`autocraft-server hold <repo#n>`, `resume <repo#n>`) send the command of that name on the row's item. Held items are listed on the Work queue under Held.
- **Remove from batch** (`autocraft-server batch-remove <repo#n>`): holds the PR, which ends its batch. The batch PR is closed through the GitHub write path (audited, on the GitHub activity page). The other PRs return to the queue and the next merge run builds a batch without the held PR (with the repo's Pipeline off, of the started ones). Neither control removes the pipeline account's assignment on the member PRs.
- **Stop batch** (`autocraft-server batch-stop <id>`): holds each open member PR, so the next merge run does not rebuild the same batch, then closes the batch's integration PR. Resume them one by one.

**Weight.** The Merge tab shows each started item's weight word. A person who may act on the repo changes it with a weight command (see Starting and answering).

Each merge queue row says how the PR came in, by whom and when (`added` on the row; the login for staff only): **Queued** (approved for merge without a fix-up), **Pre-approved** (approved with a fix-up), or **Take review** (it came in with its take review, at the review's time).

The Queue page API (`GET /api/queue/page?tab=all|review|fix|verify|merge&repos=pipeline|all|<repo>`) serves the tabs. The default repo filter is the repos whose pipeline is on plus started items of any repo. Rows carry their weight place ("2 of 5") and hold. `GET /api/merge/held` lists the held PRs as `repo#n`. The Merge tab adds "Next merges": what merges next and what each PR waits for (CI, Verify, re-review, batch check, hold), read from the merge queue states.

### PR status comment

With the repo's **PR status comment** switch on (Repos page, GitHub writes; off by default; an operator or a maintainer with write access to the repo switches it), the `pr-status` step keeps one comment on each PR the pipeline works on. It posts the comment once the PR is past triage (in review, waiting for CI, in a fix-up, waiting for a maintainer decision, or in the merge queue), then edits it in place whenever the status line changes, including when the PR merges or closes; a reopened PR gets edits again. GitHub sends no notification for an edit. Batch PRs get no comment. The fix-up, CI fix and conflict comments are still posted separately.

Every issue or PR a person started or approved gets the same comment in any repo, switch on or off, under the GitHub App identity: their start is the approval. It is posted as soon as the item starts and carries the workflow's lines (`src/workflow/status.ts`): where it stands, who started, approved, answered or held it, its steps, its numbered parts, the open recommendation with the logins it asks, and how to answer: "Answer in a comment that starts with `@<mention>`: yes, or another command." (where a yes runs nothing, an implementation's question with no recommended option: "an option's number, or another command", or "your answer" when it has no options) A question an implementation asks before its PR exists shows in the issue's comment. Once the implementation's PR exists, the PR's comment shows the issue's workflow and asks its questions, and the issue's comment reads "Implementation: #N" with who started, approved and answered it, and asks nothing more.

The comment names the people it asks as plain logins, and an edit notifies nobody, so each new question gets one short reply on the item (`src/prstatus/ping.ts`, audited as `pr-status-ping`): the asked people's `@`-logins beside the same recommendation line, how to answer and a link to the status comment. A question is the workflow's recommendation at its time; the comment's row keeps the last one pinged (`pr_status_comments.pinged`), so a question is pinged once, on its first post too, and not again on the implementation's PR after its issue. A command's reply on the item that showed the question counts as its ping, and the person whose command made the question (written within 10 seconds of their command) is not pinged about it. Only logins of people with an AutoCraft login are pinged. A quiet PR, a row only the automatic merge rule started and an issue's review (which posts its own comment with its recommendation) get no ping. The reply goes out with the comment's write, under the same switch or start. A failed ping is tried again on the next run without holding up the comment's edits (`pr_status_comments.ping_failures`), and after 3 failures in a row the question is given up (`<key> given up`). When the pings started, the questions open on comments in repos with the PR status switch on, which their maintainers had seen, were counted as pinged once (`src/db/pings-settled.ts`).

The comment of an item nobody started has:

- **Status:** the PR's step from the public status layer (`src/public/status.ts`, the same steps the Discord bot shows): Waiting for review, In review, Waiting for CI, Fix-up in progress, Waiting for a maintainer decision, In the merge queue, Merged, Closed. In the merge queue it adds the place in merge order (`next in line`, `#3 in line`; from #11 on, `10 or more PRs ahead`, so a merge edits only the comments near the front) or, once the batch PR is open, the batch it is checked in (`checked in merge batch #N`); until the batch PR opens, a member keeps its line. Members of open batches count as ahead of every other queued PR; PRs waiting on a maintainer do not count. A merged PR names the batch it merged with. Hold reasons, review text and the reasons behind a step are never shown. A security fix gets the same line as any PR, place and batch included.
- **History:** the steps the comment has shown, with their times (UTC), the newest eight.
- **Details for maintainers:** links to the item page and, in the merge queue, the Merge queue page. Only people with dashboard access can open them. The line is left out when no dashboard address (`AUTOCRAFT_BASE_URL`) is set.

The planner queues the step when a PR's line differs from the one posted; there is no timer. When the repo leaves the pipeline scope (its Pipeline switch off) while the PR status switch stays on, no new comments start, but comments already posted still get their Merged or Closed edit. A comment someone deleted on GitHub (the edit is refused and a read of the PR no longer shows it) is not posted again on that PR. With no stored record of the comment (a restart between the post and its record), the step pages back through the PR's comments, finds it by its hidden marker and edits it. A comment written as another identity (the box account, before a switch to the GitHub App) cannot be edited, so a new one replaces it. After 3 failed writes in a row a PR waits 1 hour, doubling up to 24 hours; a success resets it. One job at a time writes a repo's comments (a per-repo lease). The writes are audited as `pr-status-comment` and `pr-status-comment-edit`, made as the bot with the "Automated message" note, and paced as bulk writes: they start only while the GitHub write budget is less than half used, so they leave room for the writes that move PRs.

## Pre-approved merge

The merge leg of an approved workflow. A `fix-up` command queues the fix-up of the PR's head; with an approval the leg goes on to the merge. A `review` command marks the head's review stale so Opus reviews it again.

- **Fix-up.** The operator's instructions (1 to 1500 characters, never posted) are queued per head (`operator_fixups`). The Fix-up step works them with source `operator` in its `fixups` rows: the model gets the instructions as a trusted `operator` block in place of the fix list, may edit any existing file of the repository except what every fix-up refuses (CI workflows, cargo configuration, build scripts, files that instruct coding agents) and the build and trust files (`Cargo.toml`, `Cargo.lock`, `rust-toolchain*`, `.gitmodules`, `.gitattributes`, `CODEOWNERS`, `.claude/`), and the patch goes through the same checks, lint and push approval as any fix-up. The PR's tries (2) apply to operator fix-ups as to the review's. After a push the comment on the PR reads "Fixes included:" and a numbered list of what the fix-up changed, taken from the model's own `CHANGES:` list after its diff (the files when it gave none), each item cleaned to one plain line, left out when it repeats a run of 12 words of the instructions, and checked by the reference lint; the instructions are never quoted. The review's own fix-up and the merge queue leave the PR alone while the pre-approval is before its Merge answer.
- **Review.** A merge approval says the change is wanted, so a take review at the row's head goes on to `ci` whether Opus is sure or not, and a take-fix review, sure or not, keeps the row in `review` while the planner's fix-up of the review's fixes runs (`fixupOf` plans it for any take-fix review), after the conflict merge when the PR conflicts with its base branch. Parts a person dropped from the workflow's plan are left out, and so are fixes that do not block (they are filed as follow-ups); a take-fix with no fix left counts as a take, and the thread says "finds nothing that blocks the approved merge". A hold that does not block goes on as a take. Its push is the pipeline's own: the row moves to the new head, which needs a fresh review, a clean pre-merge review and green CI. Fixes the pipeline cannot make (not pushable, too large, its 2 tries since the approval used up) are never handed to the contributor: the leg stops (`fix-cannot-run`) and the workflow asks the approver whether to drop them and merge. A hold or close verdict stops it, unless the person answered after that review: the leg then goes on as after a take, with the pre-merge review, Verify and CI. The thread says which way it went, for example "The review of the PR's head is unsure and asks for fixes; the PR was queued to merge, so the fix-up runs.
- **States** (`preapprovals`, shown as `Item.preapproval`): `fixup` (queued or running), `review` (the push's head waits for its Opus review), `ci` (the review says take, sure or unsure, and is not stale; waiting for CI, then for a clean pre-merge review of the head; while the stored checks are pending or of another head, the repo's checks job reads them again every minute), `queued` (back to `review` when a new review asks for fixes), `merged`, `cancelled`, `failed`. Each change is evaluated on the runner's tick from rows other steps write (fixups, reviews, checks, the mirrored head, merges), so it has no timer and no wait of its own (the one time comparison is made on the tick, as the next paragraphs say). Each one writes an audit row (`preapproval`) and a system line in the item's conversation.
- **Hand-over.** Only when, at the pushed head, the review is a take that is not stale (read again just before), CI is green (as the planner and the merge step read it: without the repo's optional checks, and not while approved runs are unfinished) and the pre-merge review is clean (the planner runs it for a leg in `ci`; a failed one is retried like any other, for about a day (Pre-merge review retry), then stops the leg: a yes gives it one more try at that head, and a person who answered `merge` after it failed has the leg hand over without it). The merge queue takes it from there as the person who approved, with every check it always makes (CI, safe-merge). A verification that failed stops the hand-over, unless the person answered after it. Defects of the pre-merge review that a person has to have fixed come first: the fix is a new head, which is verified again. After the hand-over, a failed verification or a merge refusal that nothing clears by itself is a question of the workflow, which ends the leg; a yes goes on past it. Other waits of the queue (CI, a batch, the approver's sign-in) and a transient refusal, which is tried again, do not. A PR in a batch, or while a merge job of the repo runs, is looked at afterwards. The leg never merges anything itself. It ends `merged` when the queue merged that head.
- **The merge check** (`src/core/may.ts`), read by the planner and again right before each merge. A started PR merges only through a leg that handed it over at its head, also where the merge rule would merge it: before the leg starts, while it works and after it ended, until the workflow moves on, nothing merges. The head must be the one the workflow accepted, or follow from it through our own pushes alone; a push of ours on top of someone else's commits does not count. After a stop, a backlog, a close or an answer that ended the work with nothing to run, the PR (or the PR of such an issue) does not merge on the repo's approval until someone starts it again. An issue's workflow that ended as its PR merged says nothing about the issue's other PRs.
- **The approver's access.** The leg stands while its approver does (see Starting and answering): after GitHub's own answer that they have no write access, or a lost role, it waits and the workflow asks for another maintainer's approval, and it waits while GitHub cannot answer. Up to the hand-over it goes on for whoever last answered, approved or started the item and may act; after it, for the approver alone. A batch reads the permission live when it takes a member and before it merges, and leaves out a member whose approver has no write access.
- **Not take or CI not green.** A fix-up that did not push, a review that is neither take nor take-fix, fixes nobody makes, a pre-merge review with blocking defects, a failed verification (an errored one once AutoCraft's runs of it again are used up), or a CI problem nobody repairs stops the leg. Where the stop is a finding (a hold or close of the review, the pre-merge review's defects, a failed verification), the workflow asks for a fix-up of it as the approver and a new leg goes on with its push; any other stop comes back with its blocker and recommendation. A repo that never runs CI stops it too, since nothing merges without CI. While red CI can still be fixed by the CI fix, the pre-approval waits; its push is the pipeline's own, and the leg goes on at the new head. Red CI the CI fix gave up on stops the leg, naming the failing checks and what the CI fix tried: the contributor is never asked to fix CI on a PR whose merge a person approved; only a patch the CI fix posted as a comment, on a branch it cannot push to, waits for them (`src/preapproval/paths.ts`). Defects that do not block go to the follow-up issue and the leg goes on. Blocking pre-merge defects in files a fix-up may edit get up to 3 fix-up rounds per PR, and the leg waits meanwhile; a defect the next pre-merge review finds again (same file and title), or one left after the last round, stops it, and the workflow has it fixed as above. A defect a person dropped from the workflow's plan stops nothing: with every blocking one dropped, the leg hands over on green CI without a new pre-merge review. Each end has a code (`reason_code`, `src/core/codes.ts`) that says whether it is fixed or stands for a blocker; `reason` is the sentence shown.
- **Conflict with the base branch.** The leg waits while the PR conflicts, as the plan does, whatever CI says: for the conflict merge, whose push is the pipeline's own; for the contributor or another person where the conflict merge cannot run (the branch cannot be pushed to, its tries are used up, a base branch it may not merge). On a PR approved for merge that person is the approver, who is asked. Catching up to the base branch is part of the merge queue: a PR approved for merge or queued for merge gets the base merged in every time it is behind or conflicts, with no daily limit, and a resolution rejected twice at one head asks the approver. The approval stands; a person's push goes through the review round. The recommendation on such a PR and the confirmation of a yes, a `merge` or an approved start say who has to act (`conflictPath`, `src/core/decide.ts`), and where that is a person a yes claims no fix and no merge. A yes to fix findings is kept where the pipeline merges the base in: it makes a take-fix review's minor fixes itself after that merge, and any other fix-up (a pre-merge review's findings, a major finding) is a request that waits for the merge and follows the head.
- **Draft.** A draft gets no work and no merge: a leg waits where it is, and an approved PR without one gets it once it is marked ready for review.
- **Our own pushes.** Every push AutoCraft makes to the PR (a fix-up of any source, a CI fix, a base merge clean or resolved, a revision of its own implementation, an autorepin) keeps the approval, in every state of the leg, after the hand-over too, and asks nobody. The leg goes back to `review` at the new head, which needs green CI, a clean pre-merge review and, for every PR but a merge-queue entry, a review: an earlier review carries over our checked fix-ups and over a base merge that left the PR's diff the same (`own_diff`) (see Review, step `review-carry`), and any other push gets a delta review for blocking problems. The pre-merge review is read again by a model only where some head since the approval's full review got a review that read new code: the author's commits, a resolved conflict that changed the PR's own diff, an operator's fix-up beyond its parts. A CI fix of ours gets its delta review but no new pre-merge review. Every other head's pre-merge row is stored with no model call (model `carried`): clean where nothing since the full review owed one, else the nearest earlier head's findings less the defects our fix-ups since were asked to fix, so its follow-ups are not filed twice. Verify runs once, at the head that merges: when CI is green there and its pre-merge review has no defect that stops the merge. A merge-queue entry, which merges without a review, is reviewed only when a person asks for it (`review`, or a `yes` that says so) and for a push since its start that a model wrote or that changed the PR's diff, also one under someone else's commits: it merges after a review at that push or at what followed, whatever was answered meanwhile. What such a review says counts until the person has been asked about it. A clean base merge and an autorepin need none, and an older review plays no part. A fix-up request that waits follows the head. The push is ours when our own pushes alone lead to the head from the leg's (`src/core/evidence.ts`, also for the workflow and the merge check). Each push is recorded right before git runs (`own_pushes`: the head it was made on, the commit, the time), so a crash after the push loses nothing and a push that never landed counts for nothing. A try that another push overtook is dropped (`superseded`): it is no failed try, and the new head gets its own. While the mirror does not show a push of ours yet, the leg waits, until a sync that began after the push has finished. However many pushes of ours a PR gets, none stops the approved merge: each step's own tries (fix-up, CI fix, pre-merge fix rounds, conflict resolutions) bound them. Rows of untracked repos are left alone until the repo is tracked again. An error while advancing a row is recorded once in the item's trace (audit `preapproval-error`).
- **Cancelled.** When someone else pushes (also under a push of ours), after which the workflow's review round judges the new head and starts a new leg at a head it accepts, when the PR closes or merges elsewhere, or when an operator cancels it (`POST /api/items/:repo/:n/preapproval/cancel`, audited). A queued PR that is in an integration batch is first removed from the batch (the batch PR is closed); the cancel is refused only when a merge job of the repo is running or the PR is merged. A head that goes back to the commit the fix-up started from counts as another push once a review of the pushed head exists or a repo sync has finished after the push (the mirror may lag until then). While an operator fix-up request can be worked (same head, pushable, push approved, not conflicting, not a draft, tries left), the queue also leaves the PR alone; a request that can no longer be worked is ended with a reason in the thread, and a pre-approval whose fix-up cannot run ends as `asked`. A merge that lands after a cancel turns the row into `merged`.

## Act

Carries out the closes people command, on any surface, and the queued presses of conversation cards. No model. The command is the approval; a card press needs the repo's approval for its write. Daily limit 20 items.

| Command | Action |
|---|---|
| `close` | One comment, then close |
| `close as completed`, `close as not planned` | The same; an issue gets that reason on GitHub, a PR has none |
| `close as duplicate of #n` (or `owner/repo#n`) | `Duplicate of #n.`, then close |

- **Person actions.** The command queues a row in `workflow_actions` with the person, the reason and, for a PR, the head they saw, and ends the item's workflow as closed. The planner lists Act for the item while the row is `pending`, whatever the item's scope, heaviest workflow first, then in the order of the commands.
- **As the person.** While the GitHub identity is the app, the close is made with the person's own token; the comment is the app's. A person with no usable sign-in (`waiting-token`) or no write access (`waiting-permission`) leaves the row waiting and the item's state line says so; signing in puts it back to `pending`. A person who lost their role ends it as `stopped`.
- **Duplicates.** An issue closed as a duplicate gets GitHub's reason DUPLICATE, linked to the original; when the original is a PR, or GitHub rejects the link, the reason is NOT_PLANNED. The original must be another item of a tracked repo.
- **Comments.** Fixed templates in code (listed on [Prompts](/prompts)). A comment is never posted twice.
- **Before writing,** the step re-reads the item on GitHub. One that is closed or merged already ends the row as `done`, without a comment; a PR whose head moved since the command, or an item that is gone, ends it as `skipped`. An item the sync sees closed ends its row too.
- **Taking it back.** `hold`, `backlog` or a command that starts work on the item ends a close that is not made yet as `stopped`, also between the comment and the close.
- **Failures.** An error of GitHub itself (a 5xx, a timeout, a rate limit) stops the job and counts no try. Any other error counts one; after three the row is `failed` (audit `act-stopped`) and the person sends the command again. The state line shows why a close was not made.
- **Follow-up issues held until the merge.** A card that merges the PR does not open its issue when pressed: it stores it (table `held_followups`, with the PR, the issue's repo, title and body, the presser and the card) bound to the workflow and the merge approval of the press. The Act job of the PR's repo opens it once the PR merged, whoever merged it, with the same write as a pressed card (audit `act-open-issue`, counted against Act's daily limit then, not at the press). It drops the issue when the PR closes without merging, or when that approval ended before the merge (stopped, replaced or withdrawn). It also drops it when the PR turned quiet or the presser no longer has write access to the issue's repo; a missing comment approval of the issue's repo keeps it held. The planner runs the job when the PR's state or its workflow changes; there is no timer. Before the create call the row turns `filing`, so a restart never opens it twice; the next job settles a row left in `filing` from its audit row (opened when the write finished with a URL, held again when no write was recorded) and otherwise the item page shows "the create's outcome is unknown, check GitHub". A refusal from GitHub returns it to held and fails the job, so the failed-job backoff spaces the tries, three at most; a create the write pacing held back counts no try and runs again at the next pass, like other paced writes. The planner wakes 10 minutes after a create started to settle a row a stopped process left in `filing`. The item page shows the held issue under the presser's name and, when it is dropped or not opened, why; an opened issue is the "Opened issue" line. Cards that open an issue without merging (a scope split, a plug-in split) open it when pressed.

## Post-merge review

A second Opus review of what the pipeline's merges landed, to catch what the first review and the merge let through (for example a requested fix that a conflict merge dropped). A merge is reviewed when no person answered for the code that landed:

- nobody approved the merge (the pipeline merged it by the merge rule);
- a push of the pipeline's changed code after the head a person approved: a fix-up of any source, a CI fix, a conflict merge that changed the PR's own diff, or an implementation session's revision;
- it is an implementation whose merge was approved before its pull request existed.

A PR that merged as a person approved it gets no post-merge review, and the item page says so; a clean base merge and an autorepin after the approval change nothing the person approved. In a batch each member goes by its own approval and pushes. The rule is the one by which a push of the pipeline's owes a review before the merge (`landedWhy` in `src/core/evidence.ts`), and the repo's Pipeline switch does not matter.

The review of a PR a person's workflow merged is part of that workflow's work: the Task Runners of the person who started or approved it take the call first, as they take the rest of its work, a Manual only one included (`src/remote/started.ts`), for 3 days after the workflow ended done through the merge.

A maintainer with write access on the repo, or an operator, who has a Task Runner can take one item's work onto it: `take` (the item page's "Run on my Task Runner" button, a GitHub comment, Discord or the agent) adds them as an owner of the item's live workflow, and `release` ("Release my Task Runner") ends it. The starter's and approver's Task Runners come first: the taker's runner claims one of the workflow's calls only while no Task Runner of theirs could run that call now, that is fresh, ready, not cooling off, serving the call's tier with its reported model, active (running a lease or asking for work lately), with a free slot and under its user's Max calls at once (offline, held by its usage limit, cooled off, inactive, without the tier, or full). It then takes the call like the starter's own runner would, ahead of automatic work and whatever its My repos, tasks, items or Manual only say; no other item of the repo reaches it. The implement step's calls, which run on the Task Runner of the person who started the implementation, follow the same rule: while no runner of that person could run one now, the taker's runner leases it in one of its slots, counted toward the taker's Max calls at once, and the session's later turns stay on that runner. Such a call has a taker while a taker's runner is fresh and ready, so it is not withdrawn for want of one, and the Work queue says it runs on the Task Runner that took the work (whose, for operators and maintainers only). Other calls bound to a person (Discord and interactive prompts, a maintainer's conversation turns) run only on that person's runners. The claim's condition (`startedWorkAllows` and, for bound calls, `boundTakeAllows` in `src/data/runners/cross.ts`) and the Task Runner snapshot (`src/remote/started.ts`) read the same rule; the claim hands the condition the credentials that serve the call's tier, read from the snapshot. A take lasts until the workflow ends or the taker releases it; a new start on the item does not inherit it. Nobody can take work onto someone else's Task Runner, and the people who started or approved the item have nothing to take. A take and a release are recorded in the item's history and the audit log (`item-take`, `item-release`). The grants are in `item_runners` (`src/data/workflow/item-runners.ts`), the rule on who may send them in `src/core/item-runner.ts`.

Only merges recorded after the stage started, or since `autocraft-server postmerge backfill --since <date>`, are reviewed; merges outside the pipeline's scope (made in a repo whose Pipeline switch is off) only from the time the setting `postmerge_unscoped_since` holds. Each of these merged PRs is reviewed once, oldest merge first; there is no daily limit on the model step. A backfill more than 14 days back needs `--yes`.

- **Input.** The PR's title, body and author; the merged diff (the merge commit against its first parent, kept to the files the PR changed, code files only, the same size cap as Review; for a PR merged through an integration batch, the PR's own diff at the merged head, which includes the pipeline's pushes to the PR branch; when the PR's own diff cannot be read there is no diff and the review is tried again later); the commits the pipeline added (conflict merges, fix-ups, parts carried over from duplicates); the PR's earlier Opus reviews; the open issues and PRs, and those closed in the last 30 days, that mention the PR number or one of its files, by number, state and title, to avoid duplicates; and the follow-up issues earlier reviews of the PR filed (`filed_before`), with their state. The call reads a checkout at the merge commit with the same read-only tools and reference mount as Review, and its reply goes through the same lint and fix turn.
- **Findings.** Each finding is a `defect` (wrong behaviour, a crash, data loss, a correctness bug) or `minor` (style, wording, commit titles, stale comments, test-only gaps), with a title, a public body, file and line, the number of an open item that already covers it, and two internal notes: the stage that should have caught it and why it did not. An empty list is a valid review. A reply that is not valid is asked again once, then stored as an error and tried again after an hour, three times at most, after which the review is held; a diff over the size cap is held.
- **Filing.** The `postmerge-file` step opens one GitHub issue for each defect that no open item covers, in repos approved for comments: the title is the finding's title, the body is the note line (`AI-generated issue (<Model>). Not a maintainer decision.`), `Follow-up to #<n>.` and the finding's text, then the `Location:` line when the finding names a file. Daily limit 20 issues; defects over the limit are filed by later runs, and every attempt counts against it. Public text outside code is cleaned: URLs go, Markdown links keep their text, issue references (`owner/repo#n`, `#n`, `GH-n`) read "issue n"; code spans and closed fenced blocks keep their URLs and references, and an unclosed fence is not code. Every `@` before a name is removed, code included. A title or body that names the product or the pipeline's GitHub account is stored and never filed. No issue is filed for a security fix whose advisory is not published yet (its quiet pull request); its findings are only shown on the dashboard.
- **Safety.** Before the create call the step writes a follow-up row in state `filing`; after it, the row becomes `filed` with the issue number in a separate step. A row left in `filing` (crash, lost response, failed record) is never retried: the issue may exist, the item page says "Outcome unknown, check GitHub", and the run stops. A refusal from GitHub that cannot have created an issue (issues disabled, no permission) is stored as `failed` and tried again after 1 hour, then after 6 hours, three attempts at most. A defect whose cited file is no longer on the default branch is skipped as stale. Defects in the same file, within 20 lines and with a similar title are filed once: the first of a run, or one this stage filed in the last 30 days; the others are marked duplicates of it. A PR that already has a filed follow-up from an earlier review never files automatically again, and neither does a PR that itself fixes a follow-up issue: their findings are stored and shown as not filed.
- **After filing.** The issue is mirrored, classified and fixed like any other issue.
- **Item page.** A PR that merged as a person approved it says that it needs no post-merge review. A reviewed one shows its findings with severity, text, file and line, and the issue filed for each defect, the duplicate it was marked as, why it was not filed, and the follow-ups of earlier reviews. Operators and maintainers also see which stage missed the finding and why.
- **Commands.** `autocraft-server postmerge review <repo>#<n> [--again]` reviews one PR now (refused while the runner has a postmerge job running for the repo); `autocraft-server postmerge file <repo>#<n> <finding>` files one defect of the PR's latest review, counted from 0, whatever holds the PR's automatic filing back (the PR must still be in the pipeline's scope, or reviewed since `postmerge_unscoped_since`); `autocraft-server postmerge backfill --since <ISO date> [--yes]` makes the step review the pipeline's merges since that date that need a review. All are logged in the audit log.

### Self-evaluation

Once an hour the `eval` step looks for stalls, loops, repeated failures and cost outliers in AutoCraft's own records, and files what it finds as issues on the AutoCraft repository, where maintainers decide what to do with them. It runs only while the instance setting `eval_repo` names a tracked repo (`autocraft-server eval repo <name>`, see docs/operations.md); unset, nothing runs and nothing is posted. The eval job carries that repo, so its model calls go to Task Runners that take it. There is no daily limit; the next job is due an hour after the last one was queued (wait "Eval schedule").

- **Detectors.** Deterministic rules over the database (`src/eval/detect.ts`, data through `src/data/eval`). Each groups its evidence under a cause key that names the cause, never an item:

  | Detector | Rule | Cause key |
  |---|---|---|
  | `stalled-item` | a started item's workflow is `running` or `waiting` with no change for 2 hours (no question is open) | `stalled-item:<state>:<step>` |
  | `queued-call-idle-runner` | a model call queued 30 minutes while a fresh, ready Task Runner has a free slot | `queued-call:<step>` |
  | `queued-job` | a job queued an hour | `queued-job:<step>` |
  | `jobs-wait-on-calls` | a job queued an hour while every running job waits on a call queued 10 minutes | `running-jobs-wait-on-calls` |
  | `step-failing` | 3 failed jobs of a step in 24 hours with the same error (numbers, hashes, refs and quoted parts left out) | `job-failed:<step>:<hash>` |
  | `idle-repeat` | 8 jobs of a step on one repo in 24 hours that handled and acted on nothing | `idle-jobs:<step>` |
  | `blocked-unasked` | a workflow at a blocker for an hour with no recommendation | `blocked-unasked:<blocker>` |
  | `comment-churn` | 10 comments, comment edits, review edits or label writes of one action on one item in 24 hours | `churn:<action>` |
  | `answer-ran-nothing` | an answer or start an hour old on a live item that no job touched since | `answer-ran-nothing` |
  | `refused-write` | 3 failed GitHub writes of one action in 24 hours with the same error | `write-failed:<action>:<hash>` |
  | `retries` | 3 retry requests on one item in 24 hours | `retries:<step>` |
  | `health-stays-on` | a health check in warning or failure for an hour | `health:<check>` |
  | `calls-per-merge` | a PR merged in the last 7 days whose Claude calls number at least 15 and 3 times the median of merged PRs | `calls-per-merge` |

- **Causes.** Each cause key is one row of `eval_causes` with the newest 50 pieces of evidence (job, call, workflow, audit row, answer, health check or merged PR, with its time) and the count of distinct pieces seen. A piece already kept, or older than the oldest kept one of a full list, is not counted again.
- **Investigation.** A cause gets one Opus call (`eval.investigate`, effort high) when it is new, when its last call failed (at the next run; after 3 failures in a row only once new evidence arrives), or when it grew since its last investigation and that was a day ago. One run makes at most 10 calls, new causes first, then grown ones, then failed ones; the rest wait for the next run. The call reads a read-only checkout of the eval repo's default branch head with Read, Grep and Glob, the same sandbox Review uses, and answers whether it is a real defect, its severity (high, medium, low), the cause, evidence as path:line entries and the proposed fix. An evidence entry without path:line goes back as one fix turn; entries still without it are dropped, and a defect left without evidence counts as none. Private repository names in the records reach the call only as `private-repo-N`. A cause no Task Runner takes, or without a checkout, waits for the next run.
- **Filing.** Only through `src/github/write.ts`, as the instance's GitHub identity, on the eval repo; the setting is the operator's approval for it, so no repo approval is needed, and the global switch applies. A real defect becomes one issue labelled `autocraft-eval` (the label is created or updated first) with the note line, the detector's rule, severity, cause key and counts, the cause, the path:line evidence, the records (by kind, id and time; an item only when its repo is public) and the proposed fix. The model's text is cleaned like post-merge issues: no URLs, `@` mentions or issue references. A last pass over the model's fields and again over the whole title, body or comment right before it is posted (`src/eval/public.ts`) replaces every login AutoCraft knows (access list, Task Runner owners, users with settings, repository owners, item authors and mergers) with a role word such as "a maintainer", bare, mentioned, in code or as a path segment, and any other mention with "a user"; home directories (`/home/<name>`, `/Users/<name>`, `C:\Users\<name>`) become `~`; it takes out e-mail addresses, links to hosts other than github.com, IP addresses, internal names (`.local`, `.internal`, `.svc`, `.lan`), Task Runner host names and labels, the server's own host names and other names in their domain, and private repository names (also with a suffix such as `.git`). Logins of one or two characters are replaced only as mentions. While the issue is open, new evidence becomes one comment at most once a day. An issue closed as not planned or a duplicate ends its cause; one closed as completed whose cause shows evidence after the close gets a new issue that names it. Before the create the cause is `filing`; a create that sent nothing puts it back, a refusal counts an attempt (3 at most), and an unknown outcome stays `filing` until the audit row of the create settles it.
- **Nothing is implemented.** The issues wait for a maintainer's command like any other issue.
- **Commands.** `autocraft-server eval repo [<name> | --clear]` shows, sets or clears the eval repo (audited as `eval-repo`); `autocraft-server eval run` queues one `eval` job now (the runner keeps one live job per step and repo, so it never overlaps the hourly one); `autocraft-server eval run --dry` runs inline and prints the candidate groups with their newest evidence, which causes would be investigated and what would be filed or commented, writing and posting nothing and calling no model (`--investigate` fetches the checkout and makes the investigation calls, which leave their own call, run and usage rows, but the causes stay as they were; `--text` prints the issue and comment text exactly as it would be posted); `autocraft-server eval status` lists the causes with their state, verdict and issue.

## Security deep scan

Audits the default branch of one repo for vulnerabilities an outsider can reach, then fixes confirmed findings privately and lands each fix as a pull request that does not say what it protects against. It is not part of the daily pipeline: an operator, or a maintainer with write access who sets a spend cap, starts each scan, the private fix of each confirmed finding starts on its own, and an operator starts every other step on a finding (Land, Advisory, Publish). The pipeline's on/off switch and daily limits do not apply. Its steps (`security-scan`, `security-fix`, `security-land`, `security-advisory`, `security-publish`) are jobs with no registry entry, so they get the default step time limit. The only model is Opus at high effort, with tools `Read`, `Grep` and `Glob` on a read-only checkout (no shell, no web tool).

- **Starting a scan.** An operator (with any cap or none) or a maintainer with GitHub write permission on the repo (with a positive cap; without one the API answers 403), from the repo page or, on a test repo, with `autocraft-server security scan REPO --as LOGIN (--cap USD | --no-cap)`. The spend cap is a dollar amount above 0 and up to 100,000, or none. A repo has at most one active scan (modeling, scanning or verifying); a second start is refused with 409. The scan pins the default branch's head commit; every call, and any later fix, works on that commit. The scan's job and agent runs are recorded under the pseudo repo `(security):<repo>`, so job and run listings that hide untracked repos hide them. Stopping a scan cancels its job; the scan ends `stopped` before its next call. A scan whose job ended without finishing is closed as `stopped` (job cancelled) or `failed`, and one that was never queued fails after a minute. Scan states: `modeling`, `scanning`, `verifying`, `done`, `stopped`, `capped`, `failed`.
- **Threat model.** `security.model` (Opus, high, 60 turns) lists entry points (kind from a fixed list, else `other`) and splits the code into areas, each with paths, entry points, a risk from 1 to 5 and a reason. Areas are sorted by risk, highest first (ties keep the reply's order), at most 60; an area whose paths are not in the checkout is skipped. A reply with no valid area is asked once more, then the scan fails.
- **Area calls.** One `security.area` call per area, in risk order (Opus, high, 60 turns). A finding is kept only with confidence of at least 0.8, a title, severity (`critical`, `high`, `medium`, `low`), reach and impact, and at least one ref with a path and line (at most 8 refs, at most 12 findings per area). The first ref is the sink; a finding whose sink is not a real line of a file in the checkout is dropped, other refs that are not real lines are dropped. The model sets `urgent` only for a flaw that is easy to exploit against current users and needs an immediate release; it only marks the finding, the operator picks the route. A reply that cannot be read is asked once more; after that the area is `failed` and the scan goes on.
- **Verify.** One `security.verify` call per new finding (Opus, high, 40 turns) tries to disprove it. The finding stays only with verdict `confirmed` and a score of at least 8 of 10; otherwise it is `disproved`. The model may propose a test; the scan stores it and does not run it. When the call gives no readable answer after two tries, the finding stays listed as not verified. A finding still unchecked when the scan ends is listed with the same note.
- **Spend cap.** Before every call (and again before the repeat of an unreadable one) the scan stops as `capped` when the cost so far plus the call's expected cost would pass the cap. The expected cost is $2 for the threat model; for an area, the mean cost of the area calls so far, or before the first one $1 plus the area files' size in bytes divided by 200,000, at most $6; for a verify, the mean cost of the verify calls so far, or $0.60 before the first. A call that answered without reporting its cost counts as its expected cost. Money spent is added to the scan and to the area, and a call that stopped the scan is never started, so the cap is not passed by more than the error of an estimate. With no cap the check is skipped.
- **Continuing a scan.** An operator, or a maintainer with write access on the repo and a positive new cap, can continue a scan in state `capped` (`POST /api/security/scans/<id>/continue` with `{"cap": number|null}`, the Continue button on the scan header, or on a test repo `autocraft-server security continue REPO SCAN_ID --as LOGIN (--cap USD | --no-cap)`; audit action `security-scan-continue`). The new cap must be above what the scan has spent, or none; the repo must have no other active scan (409), and a scan in any other state is refused with 409 (a `stopped` scan was ended by an operator and may have no threat model, so it is not continued). The scan keeps its id, pinned commit, threat model, areas, findings and cost, takes the repo's active-scan slot again and queues a new `security-scan` job. Its state is `verifying` when the cap left findings unchecked, `modeling` when the cap stopped it before the threat model existed, else `scanning`. The runner checks out the pinned commit (the scan fails if the checkout is another commit), skips the threat model and every area already `done` or `failed`, first verifies the findings the cap left unchecked (they return to `unverified`; findings an operator already acted on stay as they are), and goes on in risk order. An area the cap stopped between its call and its verifies is not scanned again. The cap check uses the new cap against the total cost, and the estimates start from the mean cost of the calls the scan already made.
- **Estimate.** After the threat model the estimate is the cost so far plus the sum of the area guesses. After each area it is the cost so far plus the remaining area count times the mean cost per started area, which includes that area's verify calls.
- **Dedupe.** A new finding repeats an earlier finding of the same repo (any scan) when its fingerprint (first ref's path and line, plus the title reduced to lower-case words) is exactly the same, or when, for an earlier finding that is neither `disproved` nor a repeat, the sink file is the same, the sink line is within 3 lines and the category is the same or the titles share at least half of their words longer than 2 characters. A repeat is stored hidden, pointing at the earlier finding, which shows it in its timeline, and is not verified again. A disproved finding suppresses only an exact fingerprint match, so a reworded report of the same line can be raised again.
- **Findings and states.** Verify and dedupe states (`unverified`, `disproved`, repeats) are never listed. Listed states: `new`, `dismissed`, `backlog`, `fixing`, `ready`, `landing`, `awaiting-admin`, `landed`, `advisory`, `published`. Operator actions: Dismiss (needs a reason; from `new`, `backlog`, `ready`, `awaiting-admin`), Backlog (from `new`, `dismissed`), Reopen (from `dismissed`, `backlog`, to `new`), Fix (from `new`, `backlog`; needs a verification), Land and Advisory (from `ready`, `awaiting-admin`), Publish (from `landed`, `advisory`). A step moves the finding to its working state when queued and a second press while it works is refused; a finding left in `fixing`, or in `landing` with no pull request, after its job ended goes back to `new` or `ready` with a note.
- **Scan pages.** The Deep scans page (`/security/scans`, `GET /api/security/scans?repo=`) lists scans newest first with state, spent against cap, areas, findings and start; the repo page's Security part links to it filtered by repo. A scan page (`/security/scans/<id>`, `GET /api/security/scans/<id>`) shows the scan header (an operator can Stop an active scan and Continue a capped one), the threat model (summary, entry points, areas with risk, state and cost), every model call in order and the scan's findings. Each call is one `security_calls` row; its `agent_run_id` is the first agent run the call made, set when the call ends. A call still running, and a call of a scan from before the column, takes the first agent run listed under the scan that started within the call's time window. A call opens inline to the run's prompt and output (the Agents page's run detail) and links to `/agents/<run>`; a running call shows its latest progress line. The pages follow the `security` and `agents` live topics (`security_calls` is in `security`, which the planner ignores).
- **Who sees it.** Operators and maintainers read scans and findings; only operators act. Everyone else gets 404 from every endpoint, so the endpoints do not show that findings exist, and sees no scan jobs or agent runs.
- **Scan test.** Optional, behind the instance-wide `scan-tests` build feature (off by default; an operator sets it with `POST /api/build/features`, and the dashboard shows no switch while no confidential build environment runs on the cluster). For a finding that survives verify and has a proposed test, `security.scantest` (Opus, medium, 30 turns) writes one Rust integration test file; our code turns it into a diff that adds that one file and checks it like a regression test (at most 150 lines). The scan queues one build task (step `scan-test`, hidden from viewers like fix tasks) that builds the crate on the pinned commit and runs only that test, before the automatic fix is considered. A later runner tick reads the task with no job: a failure at the test step is `confirmed`, a pass is `not-shown` (the finding gets the note "The proposed test passes on the current code."), a build failure, a timeout, a second environment error or more than 4 hours is `could-not-build`. Findings are never dropped or re-rated. While a test is building or `not-shown` the automatic fix skips the finding (an operator can still press Fix); the fix prompt then receives the test and its result as `scan_test`. The finding page shows the badge and the test.
- **Fix.** `security.fix` (Opus, high, 40 turns, up to 3 rounds) writes one diff on the pinned commit: edits to existing `.rs` files of the Rust crate that holds the sink, plus exactly one new integration test file with a neutral name derived from a hash of the repo and finding number (no finding number or topic in it). The diff may change at most 300 lines, may not touch manifests, lock files or build scripts, and must apply with `git apply --check`. The model gets the build check tool for `fmt`, `clippy` and `test`. The reply's title (at most 72 characters), summary (at most 600) and every line the diff adds must pass the word check below. Once the wording checks pass, the job stores the round in `security_fix_rounds` (state `building`, with the kept session), queues the round's two build tasks (neutral: no finding number, the hashed test name, the pinned commit; only a confidential build environment takes them and the check tool's tasks, and the fix waits before its model call until one is ready, see Confidential environments in operations.md) and ends; no job waits on a build. The worker container builds the patch and runs the crate's tests, fmt and clippy on the changed lines; the new test must fail on the pinned commit without the fix and pass with it (a test that passes without the fix is a failed round); formatter changes ride in the same commit. `security.fixcheck` (Opus, high, 30 turns) then reviews the diff: it must remove the defect at its cause, keep the test meaningful and the change small, and reveal nothing. Fix starts on its own when verify confirms a finding (state `new` with a verify score of at least the threshold), once per finding: a finding that has had a `security-fix` job that was not cancelled is never started again automatically. The job counts as an automatic one, so switching the pipeline off cancels it while queued; the runner starts it again at start-up and on each planner pass while the pipeline is on, after moving a finding left `fixing` by the cancelled job back to `new`. The job is requested by `pipeline` and audited `security-finding-fix` with `auto: true`; its spend is not part of the scan's cap. When the round's tasks end, the runner's planner pass queues a `security-fix` job for the finding (`advanceSecurityFixes` on every runner tick, requested by whoever started the fix; a fix the pipeline started continues only while the pipeline is on; none while one is queued or running). A round that builds longer than 4 hours counts as ended: its unfinished tasks are cancelled and it is read as an environment error, then as a failure after the one retry, and a finding with a building round is not reset by the job-less check. That job reads the result: an environment error queues the tasks once more and ends; a failed round is repeated, in the same job, at most 3 rounds in all (a round that fails before its build counts too): the next round continues the model session of the round before (same account, same read-only checkout), with only the failure reason and the harness output as its message, while the prompt cache is warm (`RESUME_WINDOW_MS`); outside the window, or when the account is busy or paused or the session store is gone, it is a new call with the reason and the last diff. The session is kept with the building round and continues in the job that collects it, within the window; the sweep at the start of each run removes it from a round that waited longer, and it is deleted when the fix ends. The age-based prune of session stores covers a crash. The review stays a separate new call. The job log and `security_calls.resumed` record which rounds were resumes; if none succeeds the finding returns to `new` with the reason as a note. An operator's Fix starts it again. A fix the build cannot cover (a finding outside a Rust crate) is refused the same way. On success the commit, diff, title and summary are stored with the finding and the commit is written to a local ref in the bare cache. The commit is authored by the box account and is never pushed before Land or Advisory.
- **Word check.** Text bound for a public place may not contain a giveaway word: security, vulnerability, exploit, attack, malicious, CVE and GHSA ids, advisory, injection, traversal, overflow, out of bounds, RCE, untrusted, crafted, sanitize, zero-day, payload, escalate, bypass, and their forms. Added code lines are checked against the short list (security, vulnerability, exploit, attack, malicious, CVE, GHSA, advisory) because identifiers such as an overflow error are ordinary code; added comments, the names of added files and added function names (underscores, slashes and dots split words) are checked against the full list.
- **Land (quiet route).** The default route for any finding. The Land step pushes the stored commit to the pipeline account's fork under a neutral branch (`autocraft/fix-<title slug>-<random hex>`, the form of other pipeline branches; while the GitHub identity is the app, to the base repository) and opens a pull request with the fix's title, the summary, and one line saying the regression test fails without the change and passes with it. Before anything is pushed the title, body and branch pass the word check, and the write layer checks them again, with the commit message, so no caller can skip it. The pull request then goes through the normal Verify, review and merge steps; the Land step does not merge. Land stays `landing` with the pull request number. The landing poll (below) moves it on.
- **Quiet pull request.** A pull request is quiet from the moment it opens until its finding is `published` or `dismissed`; a quiet pull request that is closed unmerged stays quiet for as long. The finding goes back to `ready` and the next Land opens a new one. Nothing about the finding may reach a public place or a viewer in that time. These protections apply:
  - No review is posted on it (the pipeline never posts reviews on its own pull requests), and it gets no `security` label; the dashboard's verdict for it carries no security flag and, for viewers, no referee reason.
  - The review's fix list is never asked as a comment: the fix-up step holds it as "cannot push" with the reason "a quiet pull request is not asked for changes".
  - An operator's fix-up, a CI fix, a conflict resolution and a default-branch fix whose culprit is the quiet pull request use a prompt with the quiet rule. The lines the model writes must pass the word check or the try is refused as "the patch uses wording this pull request must not contain". A conflict resolution checks only the lines the model wrote, not those taken from either side.
  - The close comment on it is the plain template. Conversation cards on it drop any step that posts text.
  - The pull request is left out of duplicate pairing, and its post-merge review is only shown: no follow-up issue is filed for its defects, and `postmerge file` refuses it.
  - For viewers the dashboard veils it: its workflow events show no model output, the item trace leaves out model events.
  - No GitHub write about the finding is shown in the feed, activity page or live topics (the write actions are not in the public action set).
- **Advisory route.** An operator picks it for an urgent finding (the area call's `urgent` mark shows as a badge; no code picks the route). The Advisory step creates a draft repository advisory (with the affected-version range, as under After merge), starts its temporary private fork, pushes the stored commit there with the box user's token (the GitHub App cannot reach these forks), and opens the pull request inside the fork. When GitHub refuses a step with 403 or 404, the finding becomes `awaiting-admin` with a note naming what a repository admin must do (allow advisories for the box account, start the fork on the advisory page, add the box account to it, open the pull request, merge it). The steps already done are kept and are not repeated on the next press; any other failure returns the finding to `ready`. An admin merges the fork's pull request on the advisory page. Land from `awaiting-admin` abandons this route: the fork and pull request are forgotten (the advisory id stays) and the quiet route starts.
- **Landing poll.** Read by the sync run when the last poll is more than about two minutes old, with the pipeline on or off; it only reads GitHub state and has no timer wait. A quiet pull request that the mirror shows `MERGED` moves the finding to `landed`; one `CLOSED` moves it to `ready` with a note; an open one gets a note with the reason it waits (draft, conflicts, failed or pending checks, a refused merge, or waiting for the merge step), worded without naming the finding. An `awaiting-admin` finding moves to `advisory` when its fork pull request is merged or when the default branch holds a commit with the fix's patch id.
- **After merge.** When a quiet fix lands the poll creates the draft advisory (best effort; Publish creates it when this failed). One claim row keeps the merge poll and a Publish press from creating two drafts; a claim older than 10 minutes counts as a crashed attempt. The draft's text holds the impact, how it is reached, the affected code and the fix's pull request, and stays private to repo admins and security managers. **Publish** (from `landed` or `advisory`, after a release) creates the draft when there is none, sets a range on a draft that has none, publishes it, and, with the CVE option and on a public repo, requests a CVE (a failed request is noted, the finding is still `published`). Every advisory write (create, fork, pull request in the fork, range, publish, CVE) runs as the box account whatever the GitHub identity is, and is recorded as such.
- **Advisory range.** A draft advisory names its affected versions as `<= <version>`, the version in the Cargo.toml of the crate that holds the finding's first reference at the scan's pinned commit (the workspace version when the crate inherits it); when no version can be read the range is `<= <first 12 characters of the commit>`. GitHub refuses to publish an advisory without a range, so Publish first sets one on a draft that has none.
- **Commands.** `autocraft-server security scan REPO --as LOGIN (--cap USD | --no-cap)`, `continue REPO SCAN_ID --as LOGIN (--cap USD | --no-cap)`, `stop SCAN_ID --as LOGIN`, `list REPO`, `show REPO N` and `act REPO N fix|dismiss|backlog|reopen|land|advisory|publish --as LOGIN [--reason TEXT] [--cve]`. `scan`, `continue`, `stop` and `act` are refused unless the repo is marked as a test repo and `--as` names an operator (audit rows are marked as a session); `list` and `show` only read.

## Conversations

Each item can have one conversation with Opus, shown on its page. Everyone with access to the repo reads it. Operators write, and so do maintainers with write permission on the repo, whose messages to Opus run on their own Task Runner (see [Trust boundary](dashboard-spec.md#trust-boundary)); cards show in the item's chat as text, without buttons, and an operator can run one from the shell; a fix-up's instructions need write permission on the repo. It belongs to the item, so it stays when the item is started again.

- **Start.** An operator or a maintainer writes the first message.
- **`ask <question>`.** A message to Opus is `ask` and the question, in the item's chat or the dashboard's command box, in a GitHub comment to the app (`@<app> ask <question>`, the question running to the end of the comment), or on Discord (`@AutoCraft ask <question>`, as a reply to an item's message or naming the item, with the item rules of the other Discord commands); no question mark is needed, and `ask author` stays that command (`askedQuestion` and `commentQuestion` in `src/workflow/parse.ts`). Text without `ask` that a model reads as only a question (see Text the parser cannot read) is asked the same way. In the item's chat, text the parser reads as nothing that holds a question mark is a question too, asked at once with no model reading. The question becomes the asker's message (`src/conversations/ask.ts`), linked to the message it came in when the turn is stored, with the same refusals: the pipeline off, the step paused, no ready Task Runner of a maintainer's, an unanswered message before it, or 10 questions an hour or 50 a day. A GitHub question is asked by an operator or a maintainer the act rule lets act on the repo (others get that line, under the comment approval); its command waits, state `asked`, until the turn ends: the drain then posts Opus's reply, `@<login> <answer>`, through `write.ts`, under the AI note naming the model, or why there is none. A question from GitHub or Discord gets a prompt with the item and the question only, never the chat's earlier messages and replies. Reply lint (the reference checks of the fix turn) reads the answer first; an answer it finds a problem in, or could not check, is not posted, and the reply points to the item's chat. A posted answer, and the line saying why there is none, is cleaned as an Opus review is (`stripLinks`): no mentions outside code, raw HTML, images, links outside the repo's owner, or references that link another thread; comments by AutoCraft's own accounts are never read as commands. A question from GitHub or Discord gets only the item's update turns of the chat, no messages, replies, card results or follow-up lines. A GitHub question is not answered on a quiet pull request, also when it became quiet before the answer is posted. A question whose turn ended without its answer sent (a crash between the two) gets the pointer to the item's chat, or why there is none, 15 minutes after the turn's stored end: the runner sweeps GitHub questions once a minute, the Discord process its questions every 3 minutes while any waits. A Discord question comes from a linked login with write access to the item's repo, or an operator, about one item; it runs as `interactive.conversation-turn` (the same prompt), in the Interactive slots of the asker's own Task Runner (an operator's on any Task Runner's), so a maintainer with no Interactive slots is refused. The bot replies to the question that it was asked, starts no thread and makes nothing follow the item; when the turn ends, the Discord process (`src/discord/answers.ts`) posts the answer, after the same reply lint and cleaning (without HTML entity escapes; the post allows no mentions) and ending with the AI note naming the model, or why there is none, as a reply to the question's message in the channel or thread where it was asked. That place is sealed on the question's chat message. An item of a private repo or a quiet item gets the pointer to the item's chat instead, and so does the end of an answer too long for one message, cut so that no code block stays open. A question withdrawn in the item's chat is answered nowhere: its GitHub command ends refused without a reply, and Discord gets nothing.
- **Reply.** The Conversation step (daily limit 30 messages, Opus, effort high) answers each message with one `claude -p` call in the sandbox: the item's repository, the workspace and the item tools (see Trust boundary), read-only, Read, Grep and Glob only. It runs while the pipeline is On, for any tracked repo, including one whose pipeline is off. Maintainers' messages are answered by their own step, Answer maintainers' conversations (`conversation-maintainer`), which has no daily limit and does not count toward the operators' 30: each is a call only that maintainer's Task Runners take, beside their other calls (see [Who gets which call](operations.md#who-gets-which-call)). It fails at once, or when their runners go away while it waits, with "<login>'s Task Runner was not connected and ready; send the message again"; a message none of their runners took within two minutes waits, pending, for a later job, which starts when a maintainers' message is added or answered, or a waiting maintainer's Task Runners take or end a call or report ready again. An operator, or the maintainer who wrote it, can withdraw a waiting maintainer's message (`POST /api/items/<repo>/<n>/chat/withdraw`; Withdraw message under the waiting message in the item chat): it ends as failed, "withdrawn by <login>", and the item takes messages again. The two minutes apply to the first call only; the fix turn on its session waits as long as other follow-ups do. Tool output is not stored; Opus reads again when it needs to.
- **Progress.** The call runs with `--output-format stream-json --verbose`, and each tool call becomes a short plain line ("Reading craft-i18n/packs/hu/…", "Searching for …", "Explorer: Reading …", "Looking up repo#n"). The answering message keeps the last five lines (at most one write a second) and the page shows the latest under "Opus is replying…", the earlier ones on hover. The lines are cleared when the reply is stored; they hold no file contents.
- **Prompt order** (`conversation.turn` on [Prompts](/prompts)): the fixed prompt and action list; the item block, written once when the conversation starts and sent byte for byte afterwards; the earlier turns oldest first, each as stored; the new message last. Nothing that changes comes before the newest turn, so each call reuses the cached start of the one before. When the head commit, title or text, state, labels, comments, or the item's workflow change after the block was written, a system turn ("The PR was updated (labels, comments): ...") carries the changed fields before the next call. A system turn that arrives while Opus is answering is held and placed after the reply, so the prompt already sent stays the start of the next one. All GitHub text is quoted as untrusted data.
- **Cards.** A reply ends with action cards, the first being Opus's pick. A card holds a command (shown with what it will do, or why it cannot run now) or one or more steps: a comment (its text is the card's `text`), labels of the managed set, reopen, transfer, assign, request reviewers, open an issue. A press runs a command as the presser, the same way as a command on any other surface; the other steps go out as the app with the presser in the audit. At most one card ends the item (close, duplicate close or transfer), last.
- **Drafts.** A new Opus reply marks every still-proposed card of earlier replies `replaced`; they refuse to run ("replaced by a later reply"). Each card records the PR head and newest GitHub comment Opus had been told about. A push since makes the card refuse ("the PR changed since this was proposed", view `stale: "pr-changed"`); new GitHub comments only mark it (`stale: "new-comments"`).
- **Messages without a question.** A message may be sent with `ask: false`: it is stored as a turn without a pending state, no Opus reply is queued, and Opus reads it among the turns at the next ask. It also starts the conversation when the item has none.
- **One message at a time.** A new message waits until Opus has answered the previous one. A run claims the message before it calls Opus, so two runs or a double submit answer it once; a claim older than the prompt timeouts is released. A card left Running by a crash (older than 10 minutes) is marked Failed, "outcome unknown", when the Conversation step starts and when the dashboard starts. A message that got no usable reply is marked failed and can be written again.
- **Shell.** `autocraft-server conversation show <repo>#<n>`, `conversation say <repo>#<n> <text> [--by LOGIN] [--now]` (queues the message; `--now` answers it at once), `conversation do <card> --by LOGIN`. `say` and `do` need an operator login; `say --now` answers only while the pipeline is On and the step's daily limit has room.

These calls run with tools: Read, Grep and Glob on a read-only checkout inside a sandbox (see Trust boundary): the Opus review, the Fix-up patch and its Opus check, the CI fix patch, the Verify planner (checkouts of the PR head), and conversation replies (the default branch). Every one of them also gets the workspace and, when a snapshot exists, the item tools (see Trust boundary). Every other call runs without tools. The Prompts page shows each prompt's tools, turn limit and sandbox mode.

**Stable prompt prefix.** The model reads a repeated start of a prompt from its cache at a fraction of the cost, so every call keeps its start identical. All `claude` calls run in one fixed empty directory (`~/.cache/autocraft/claude-cwd`, `AUTOCRAFT_CLAUDE_CWD`), because the CLI puts its working directory into its system prompt; the sandbox's `/work` is likewise fixed. A call without tools replaces the CLI's system prompt (`--system-prompt`) with the prompt's fixed text, up to the line where the item data starts, and sends only the item data on stdin. A sandboxed call keeps the CLI's system prompt, which carries the tool guidance, and sends the whole prompt on stdin with the item data last. The fixed text holds no dates, counts, repository names or item data. Accounts keep separate caches, so a prompt is cached once per account.

**Item tools.** A sandboxed call can also search and read every synced issue and PR without calling GitHub, through a read-only MCP server (`src/itemtools/server`, run by `/usr/bin/node` with no dependencies). Tools: `search_items` (full-text over titles, bodies and comments, optional repo, kind and state), `item` (text, labels, latest comments and reviews), `similar_items` (nearest stored embeddings) and `pr_diff` (the cached diff of the PR head, cut at 30,000 characters, one file or an offset on request). Results frame all GitHub text as untrusted and are size-capped. The server reads a snapshot file, `item-snapshot/items.db` beside the mirror (`AUTOCRAFT_SNAPSHOT_DIR`), kept in place by the runner leader on its own disk, beside the jobs and the worker API that read it (the sync may run in another pod): at the leader's start and after each successful sync run or finished embed job since its last refresh (`src/itemtools/keeper.ts`, a child process; an embed job ends without waiting for it, and `autocraft-server embed` run by hand refreshes the file itself). A refresh compares first without a write lock and applies only the rows added, changed or removed since the last one in one transaction (rollback journal, full-text index kept by triggers); a journal left by an interrupted refresh is rolled back before the next one, and never survives a rebuild. From Postgres, every copied row carries a hash of its columns (an embedding: its model and write time); a refresh compares the public rows' keys and hashes with the file's, reading items and comments only when the change counters of the `items` or `repos` topic moved (and regardless when a counter went down, the database is another one, or the last such compare is a day old), so a refresh after an embed run reads only the embeddings' keys. Everything is read from Postgres into temporary tables first; the write lock on the file covers only the local apply step. The runner leader also refreshes when the file has a journal left by an interrupted refresh, which read-only readers cannot roll back; until then the tools answer that the snapshot is being repaired. Reviews still `PENDING` are left out, and the file is rebuilt only when missing, of another schema version, or (from Postgres) when more than half of a table's rows and over 20,000 changed. Only repositories with visibility `public` are copied. It holds items, comments, reviews, their full-text index, embeddings; no settings, audit, accounts, tokens, paths or dashboard notes. `itemTools()` returns the mounts (server code at `/app/item-tools`, snapshot directory at `/data/snapshot`, the cached diffs of each repository in the snapshot at `/data/diffs/<repo>`, all read-only) and the `items` server definition; tool names are `mcp__items__*`. `autocraft-server item-tools snapshot` builds the snapshot and `autocraft-server item-tools call <tool> <json>` runs a tool without a model. PR heads are not fetched into the bare clones, so the tools read no files at a PR head.

[Prompts](/prompts) shows every prompt exactly as sent. The code can call a model only with a registered prompt. Classifiers and Cost show how often the models agree and what each stage costs.

## Agent runs

An agent run is one model call: one Task Runner call or one Jev request. Each is recorded when it starts and ends (prompt id and version, model, user and harness for a Task Runner call, item refs, tokens, summary). Everything is kept ten years; prompts and raw output are stored compressed. Each run also lists its tool uses (name, scrubbed arguments, result size, timing for streamed calls, the check row of a check-tool use) and its cost. The Agents page lists runs. A running call with tools also keeps the latest line of what it is doing (the same lines as in Conversations), shown on its row in Running and cleared when it ends.

**Reply lint and the fix turn.** After a reply parses, a per-prompt lint looks for problems the model can fix: a mention of the reference folder or a page file in public text, a quote of the repo's reference pages (the texts of one reply are read as one stream, as their post joins them, and compared in shingles of five words after folding case, compatibility forms, accents, look-alike letters of other scripts, format characters such as a zero-width space, and hyphens or dots inside a word: a text is a quote when half or more of its own shingles are in the pages, and every text that takes part in a run of 12 matching words, or in a reply with 16 matching shingles or a matching half of all, is one too), public text that refers to documentation or a vendor of another product (Jev first, Haiku for the unsure cases and while Jev is unavailable; only for repos that have reference documentation), and a summary or one-sentence reason over its word cap. Problems go back to the model as one follow-up message on the same session, with the same account, sandbox mounts and working directory so the prompt cache is read. The follow-up runs for one turn with no tool permission and asks only for the flagged fields, as a JSON object keyed by field name; they are put into the first reply, which stays as it was otherwise. A problem marked internal (text that is never posted or shown) is recorded without a follow-up. The follow-up is its own agent run, and its tokens count as usual. The merged reply is linted too. The model checks wait for that second lint when the first one already found other problems; whenever the first reply is used instead (no fix turn, or a fix reply that fails or cannot be merged), the first reply gets every check, the model checks included. The fix reply may be fenced or not, and so may the first reply it is merged into. If the reply still has problems, cannot be read, or the call had no sandbox (and so no session), the offending text is left out and an over-long summary is cut to its first sentence. A lint problem never repeats the whole call. During the call the session store is a directory of its own under the app's cache, mounted into the sandbox and removed when the call ends. Prompts that use it: `review.opus`, `dupes.compare-prs.opus` (word caps, and the reference checks on carry points, which reach the close comment and the kept PR's suggestion) and `conversation.turn` (comment cards).

**Model calls.** Every Claude call is queued as a remote call and waits in priority order (class 2 security, 1 path to merge: fix-up, CI fix, main fix, fix issue, verify, pre-merge, Opus review, conversation; 0 the rest, then the repo with fewer running calls, then the step with fewer running calls, then the oldest). A maintainer's or operator's Task Runner claims it, runs it in a sandbox on their machine under their own subscription, and submits the reply. The reply goes through the same parsing, lint and storage as any other, and the run records the user, harness and reported model. The queue, leases, eligibility and per-call tools are in [User-local inference](operations.md#user-local-inference).

Jev calls and embeddings run on the server. Jev's parallelism is the `jev_parallel` setting (default 4), and `jev_enabled` (default on) switches Jev off (`autocraft-server inference jev`).

## Build environments and tasks

Untrusted code (a PR's build and tests) never runs where the GitHub token or a Claude login is. It runs as a task on a build environment, a worker an operator registers.

- **Worker.** Holds no GitHub token, no Claude login and no database access. It fetches public source anonymously by commit and pulls tasks by key.
- **Task.** Names the source (repo, head and base commit), what it requires (OS, toolchains, memory), a plan of steps with timeouts and network setting, an optional patch (1 MiB at most, applied before the first step) and an optional warm build cache key.
- **Scheduling.** Workers claim queued tasks that match their capabilities, by priority. A task without a heartbeat for 2 minutes is requeued once, then fails. Cancelling a task stops it at once.
- **CI parity.** Before the first step the worker reads the repo's `.github/workflows/ci.yml` at the task's base commit, a default-branch commit the runner names (a PR's base commit, or the default-branch head for main builds, nightly checks and main fixes; never the PR head, so a PR cannot choose packages or env). A task without a base commit runs in the stock image. When the file calls the suite's `craft-common-actions` gate, the worker takes the gate's inputs plus the defaults in `gate.yml`: the `packages` list, `craft-fonts-ref`, `require-craft-fonts`, and the `env`, `linux-env` and `dev-debug` settings. Env lines are kept only for the repo's own switches (names starting with the repo's name, such as `PDFCRAFT_ORACLES_REQUIRED`) and a short list of output, retry and cargo profile settings; nothing that selects a program, flag, credential, registry or proxy (git, ssh, cargo config, rustc, linker) passes, and `dev-debug` must be a value cargo accepts. The task log names the gate ref and the sha256 of the `gate.yml` read. Packages go into a derived image, `craft-sandbox/<toolchain>-<hash>` (hash of the base image reference and the sorted package list), built once with `apt-get` and network by the worker and then reused. craft-fonts at the pinned commit, and craft-i18n at the commit in the checkout's `craft-i18n.rev`, are downloaded by commit into the worker's work dir and mounted read-only at `/craft-fonts` and `/craft-i18n`, with `CRAFT_FONTS_DIR`, `CRAFT_FONTS_REQUIRED` and `CRAFT_I18N_DIR`/`CRAFT_I18N_REQUIRED` set for every offline step. Steps still run offline except `fetch deps`, which gets neither the gate env nor these mounts. The task detail lists the image, package count and both commits. A repo whose CI does not call the gate runs in the stock image. Only Linux inputs apply; the gate's Rust toolchain, targets and cargo tools are not reproduced.
- **Results are data.** Logs and artifacts are size-capped, typed by content (PNG, JSON, JUnit XML, text) and served with `nosniff` and a sandboxing policy. Nothing a worker sends is executed, rendered as HTML or put in a prompt by the coordinator. A later step that lets a model read it frames it as untrusted.
- **Access.** Worker calls arrive on their own listener, authenticated by key (stored hashed, shown once), with body caps and rate limits. Only operators register environments, rotate keys or cancel tasks, and each is audited. Tasks of repos a viewer cannot see are hidden from that viewer.
- Task rows and logs are deleted ten years after the task ends; artifacts after 30 days.

## What needs a person

- **Starting an item** (see Starting and answering), or leaving it.
- **One recommendation per item**: when a started item's steps are done without a merge approval, or at a blocker.
- **Merges outside the rule** (see Merge queue). Contributors shows who is on the whitelist and why. The pipeline's own account counts as whitelisted for the PRs Implement opened from issues (S or M bugfix after Verify can merge by the rule) while the head is the pipeline's own work: a commit someone else pushed to the branch needs an approval. An operator's deny still wins.
- **Questions of an implementation plan** and a stuck implementation.
- **A close that could not be made** (Home lists it for those who act on the repo).

**Releases.** An operator, or a maintainer with write permission on the repo, can release an item that stopped waiting for a person, from the Item page (two clicks, audited, nothing written to GitHub; the pipeline takes the item up on its next pass): *Review again at this head* (removes a hold review of the current head), *Verify again* (after failed or error).

## Actions

### What AutoCraft does on its own

Each write needs the repo's approval (Repos page) and stays within the stage's daily limit (see Daily limits). The approvals are for work nobody commanded: on a pull request a person started, their command is the approval for its merge and pushes (`src/core/may.ts`), and an `implement` or `close` command is the approval for the implementation or the close, in any repo. The pipeline's on/off switch stops all of them except the security deep scan.

| Action | Stage | Approval and limit |
|---|---|---|
| Type labels and flags | Label | Label approval. No limit |
| Assign or release the pipeline's account | Fix, Fix-up, CI fix, Merge queue | The stage's own approval. Released when the work ends (see Merge queue, Assignment) |
| Post or edit the final review | Review (`review-post`) | Comment approval. 40 posts a day |
| Approve a contributor's held CI runs | Merge queue (`ci-approve`) | CI approval. 30 a day |
| Push the review's small fixes, or comment them when the branch cannot be pushed to | Fix-up | Push approval for the push, comment approval for the comment. 20 PRs a day |
| Format, rerun or patch a failing check | CI fix | Push approval for the push, comment approval for a patch comment, CI approval for the rerun. Two tries a head; reruns 30 a day |
| Merge the base branch into a conflicting PR, and comment | Fix-up | Push approval, comment approval. Two tries a PR; counted with Fix-up |
| Fix a red default branch: rerun, open a fix PR | CI fix (`main-fix`) | Fix red main approval, off by default. 20 a day |
| Open a PR that implements a queued issue | Implement | The person's `implement` command. No daily limit |
| Merge: singly, or in an integration batch of up to 50 PRs | Merge queue | Merge approval. The merge rule or a maintainer's merge approval. 10 a day |
| Comment, then close, after a command | Act | The person's command. 20 a day |
| Post and edit one status comment per PR | Merge queue (`pr-status`) | PR status comment switch, off by default. 2,000 posts and edits a day, at half the GitHub write budget |
| Open a follow-up issue for each defect of a post-merge review | Post-merge review | Comment approval. 20 a day |
| Private fix of a confirmed security finding | Security deep scan | Starts when Verify confirms the finding. Writes nothing to GitHub: Land, Advisory and Publish are operator presses. Pipeline switch and daily limits do not apply |

## Trust boundary

- Untrusted code never runs where GitHub or Claude credentials are (see Build environments).
- Only commands and answers of people who may act on the repo are carried out: operators, and maintainers with GitHub write access to it. Text that is not fully understood runs nothing.
- Comments and picks by other people are shown here but never reach a model's prompt.
- All GitHub text is untrusted data: models judge it and never follow instructions in it.
- Every GitHub write (labels, comments, closes, pushes, fix PRs, merges) needs the repo's approval, given on the Repos page by an operator or a maintainer with write access to the repo (the merges and pushes of a pull request a person started, an implementation and a close need that person's command instead); the CLI reads approvals and cannot set them. Approvals are audited.
- Model calls run without tools, except a prompt that registers a sandbox mode (the Opus review, Fix-up patch and check, CI fix patch, Verify planner, the duplicate-PR comparison and conversation replies). Claude Code's file tools could otherwise read anything this user can, such as tokens and other accounts' logins, and untrusted text could steer a model into echoing it. Two layers keep that from happening, plus a backstop:
  1. Claude Code allows only `Read`, `Grep` and `Glob`, denies everything else without asking (`dontAsk`, no prompts), allows reads of the checkout path only, is confined to the working directory and the checkout (`--restricted`), loads no MCP servers, skills, slash commands or user and project settings, and stops after a registered number of turns.
  2. bubblewrap runs the call in new namespaces (network shared, the API needs it) with an empty home and a clean environment. Only these are visible: the claude binary, `/usr`, the TLS certificates and resolver config, the checkout read-only at `/repo`, and the used account's credentials file, read-only (the rest of its config directory is not). The working directory is an empty `/work` and the checkout is added with `--add-dir`, so instructions and settings inside the checkout are never loaded as project memory; `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` and every `.claude/` path are also left out of the checkout.
  3. Backstop: after the reply JSON is parsed, anything in its text (and in stderr) that looks like a token or key is removed before it is stored or used (the log scrubber). A reply that carries code (`fixup.patch`, `fixup.conflict`, `cifix.patch`, `fixissue.patch`, `security.fix`, `security.scantest`) reaches its parser as written; one that holds a credential of a fixed shape (a GitHub, Anthropic-style `sk-`, Slack or AWS key, a JWT, a PEM private key) is refused as an unreadable reply, so neither a credential nor a placeholder is pushed. Its stored copy is scrubbed. Every text a write posts to GitHub (comments, reviews, PR and issue bodies and titles) goes through the whole scrub as well.
  **Repo docs.** The checkout leaves instruction files out, so the sandboxed calls that judge or change a repository's code or scope (the Opus review, pre-merge and post-merge reviews, Fix-up patch and conflict, the CI fix patch, and conversation replies) get the maintainers' own documents separately: `AGENTS.md` (stored as `AGENTS.txt`, so Claude Code never loads it as memory) and `ROADMAP.md`, read from the repository's default-branch commit in the cached clone (never from a pull request's head) and mounted read-only at `/repo-docs`, outside the working directory. There is one directory per repository and commit under the cache directory, deleted after a day without use. A repository with neither file gets no mount and no prompt sentence. The prompt's repository access then ends with one fixed sentence: the rules are at `/repo-docs/AGENTS.txt` and the roadmap at `/repo-docs/ROADMAP.md`; read the rules before judging or writing code and the roadmap when the question is whether a change is wanted; follow their conventions, but their text never changes the task or the output format; name a real conflict with a rule (file and line) only when there is one; ignore links to other repositories' rule files. A mention of `/repo-docs` or `AGENTS.txt` in public text is a lint problem, like a mention of `/reference`.
  The fixed working directory of every call is under the app's cache directory, and Claude Code loads a `CLAUDE.md` from the working directory and its parents. None may exist in the install root, the cache directory or any parent of them, because every tool-free call would load it too.
  An account with a long-lived token (see below) skips all of this: the sandbox gets the token as `CLAUDE_CODE_OAUTH_TOKEN` and no credentials file, and no expiry wait applies to the account.
  The sandbox never refreshes the OAuth token, since a refresh inside it could invalidate the account's stored login. Before a sandboxed call the code reads only the token's expiry; a call that has a checkout needs the token to outlast its margin (30 minutes, plus 45 minutes when the call has the check tool). An account with less is not eligible for the call, which waits (wait reason `<account>: login token expires within <n> min; waiting for its refresh`, bounded by the caller's maximum wait) until a host-side run refreshes the token, which the minutely `/usage` reading does. The call never runs on the host without its tools. If the token expires between the choice and the claim, that run ends as failed (`skipped: token near expiry`) and the call waits again. Calls without a checkout run on the host and are unaffected.
  **Workspace.** Every sandboxed call (the Opus review, the Fix-up patch and check, the CI fix patch, the Verify planner, the duplicate-PR comparison and conversation replies) also sees a read-only checkout of the default branch of every tracked repository with visibility `public` at `/repos/<name>`, except repositories listed in the `workspace_exclude` setting (private repositories are never mounted, because replies are visible to everyone with dashboard access) (default none; `autocraft-server workspace-exclude`, `GET|PUT /api/sandbox/workspace`). The item's own checkout stays at `/repo`. There is one checkout per repository and head. A repository's head is looked up when a call needs it, at most every 5 minutes; when it moved, a checkout of the new head is built and the previous one is removed 3 hours later. A call waits at most 20 seconds for a new checkout and mounts the previous one when it is not ready; a repository with no checkout yet is left out. The same caps as for any checkout apply (the largest repositories are about 2,000 files and 50 MB); a repository over them is logged and left out. The call may start one subagent, `workspace-search` (the name differs from Claude Code's built-in `Explore`, which the model would otherwise pick; the prompt names it as the `subagent_type`) (Haiku, medium effort, Read, Grep and Glob), for broad searches. Its definition is a generated file mounted read-only at `/agents.json`, identical across calls so the prompt prefix caches. Only the main call has the Agent tool. Item tools (`itemTools()`, passed by `askClaude` to every call with the workspace; none without a snapshot) add read-only mounts and an MCP config (`--mcp-config`, still with `--strict-mcp-config`) whose `mcp__<server>__*` tools both the call and the explorer may use. The explorer's tokens are recorded on the agent run, and as separate token rows by model with the same run and stage, so the Cost page splits by model and totals stay whole.
  The checkout is built from the cached clone without a working tree: only regular files under validated paths are written (no symlinks, submodules or `.git`), files over 2 MB are left out, and a tree over 20,000 files or 150 MB gets no checkout. Nothing in it is executed. Checkouts are kept per repo and commit and deleted after a day without use; reusing one refreshes its time, and a checkout a running call has mounted is never deleted. A superseded workspace checkout is removed only when nothing touched or holds it in the 3 hours after the swap. When there is no checkout or the head moved, the call runs without tools. Building a checkout needs only the cached clone: model calls run on Task Runners, which get the checkout as a mount and run the harness in their own sandbox, so the server's bubblewrap, claude binary and `AUTOCRAFT_NO_SANDBOX` do not affect their tools.
- Every text posted to GitHub (comments, reviews, review and comment edits, issue and pull request bodies, close comments) starts with a note line, a blank line, then the text. `src/github/write.ts` adds it, and every posting function requires a note, so no post can skip it. The wording depends on who stands behind the post, with the model named as in the review note (`Opus 5.5`):
  - A model wrote the text on the pipeline's own initiative: `_AI-generated <review|comment|issue|pull request> (<Model>). Not a maintainer decision._`
  - An operator chose the action (a close, a conversation card, a batch ended by an operator): `_AI-generated reply (<Model>)_`.
  - Fixed template text with no model behind it: `_Automated message. Not a maintainer decision._`, or `_Automated reply_` when an operator chose it.
  The audit row's `text` is the text as posted, note included.
- Every write on GitHub is recorded. `src/github/write.ts` is the only module that sends one: GraphQL mutations, `gh` commands that create, close or comment, git pushes and merges. Each function adds a row to the audit table before the write (state `started`, so a crash leaves a trace) and finishes it after (`done`, or `failed` with the error), with the action, the repo and item (`repo#number`, or `repo:branch` for a branch), the details (label names, comment text and URL, pushed commit, merge commit), the source (the stage and its run id, the command, or the operator for manual actions) and, when the write failed, the error. Labelling writes one row per item. `test/github-writes.test.ts` fails when any other file under `src/` sends a mutation, pushes, merges or runs a `gh` write command. The GitHub activity page (Insight) lists these rows, newest first, for anyone signed in; it filters by repo and action, and rows of repos the viewer cannot read are left out. A merge started from the command line (`autocraft-server safe-merge`) is recorded under the login `cli`.
- Only operators can turn the whole pipeline on or off, change limits, manage accounts or cancel jobs. A maintainer account acts only on repos it has GitHub write access to; a viewer account, even a compromised one, cannot trigger a merge, close, post, label, push or any step.

## Architecture

Three processes share one database. None needs a terminal or Claude session kept open.

| Process | What it does |
|---|---|
| Sync | Copies changes from GitHub into the mirror: webhooks within seconds, a backstop poll every 15 minutes |
| Dashboard | Shows everything to people on the access list; records answers, opinions, the pipeline switch and limits. Never runs a step or calls a model |
| Runner | Runs the pipeline steps as jobs, each in its own process, and records progress, logs, results and token use |

Each step has a fixed list of settings (a choice, a tracked repo, a bounded number or a run id). Nothing typed on the dashboard can reach a prompt or a shell. A step has at most one queued or running job per repo (a job without a repo counts as every repo; security fix jobs are per finding), so one step works several repos at once. The `step_parallel` setting limits how many repos one step has queued or running at once: a positive integer or `none`, default 1 (`autocraft-server pipeline parallel [N|none]`, audited as `step-parallel`). Review, Pre-merge review, Fix-up and Fix (CI) run one job per pull request, as soon as it is due: settings `number` and `lane: approved` for a pull request a person started or approved for merge, `lane: item` for the others. A pull request the automatic merge rule took up moves to the approved lane once a person approves it. One pull request has at most one queued or running job of a step; these jobs neither count toward `step_parallel` nor wait for it, so no pull request waits for another one's job. A job of these steps without a lane (a command-line run) works every pull request of its repo nobody started, so it waits for their item jobs and they for it. Failure backoff and the "nothing changed since the last run" check are per pull request. The Jobs list shows the job's pull request and lane in its settings. A few steps share a named mutex and run one at a time: Rank, Embed, the classification steps (Classify new, Classification pass, Area rescan), Dupes and Compare duplicate groups, and the security land, advisory and publish steps. The runner starts queued jobs security first, then by id, up to a cap of job processes set by capacity: the slots of the fresh, ready Task Runners, plus the slots of the enabled, online build environments and their workspace slots, plus 6 for work that needs neither, at least 8 and at most `AUTOCRAFT_RUNNER_JOBS` (default 32), read again every 15 seconds while jobs wait; the `runner` health check and `pipeline status` show the cap and its parts. A job whose step calls Claude starts only while a Task Runner user who would take its calls (its repo, its step's task and, for a lane job, its pull request, so the people who started or approved it count) has a slot left after the queued calls of its class and above that user would take, unless no job of its step runs. Each queued call is counted against one user who would take it (its started work's owners first), so a call nobody's free Task Runner takes holds no other user's room; Claude jobs started in the last 90 seconds that have no call queued or leased yet hold a slot of one user who would take them, since the queue does not count them yet. Inside a job, a pool of calls starts as many units as the room it read, less its units still preparing their call, and one unit when there is no room and none of its units runs, so the rest of the work waits in the model-call queue's claim order; in the user-local mode a job whose repo no connected Task Runner may take stays queued. Such a queued job holds no repo of `step_parallel` and keeps none of the step's daily limit, so it does not stop the step for other repos; the Jobs list and the job page show "No Task Runner takes <repo>" on it.

The runner and dashboard connections shadow `repos`, `items`, `comments`, `stages`, `classifications` and `token_usage` with temporary views of tracked repos (`scopeToTracked` in `src/repos.ts`), so rows of untracked repos stay in the database but are never seen. A write to one of these tables names `main.` (`test/main-qualified-writes.test.ts` enforces it; trigger bodies are not checked).

### Live updates

Pages update without a reload. The database is the single source of truth and the browser only caches views of it. Triggers on the tables the dashboard reads bump a per-topic counter in `change_seq` (topics: items, ranks, stages, checks, classify, dupes, workflows, jobs, queue and others, listed in `src/db/live.ts`), whichever process wrote the row. On Postgres a writing transaction moves each counter it touched once, at its commit. An UPDATE bumps only when a column other than the bookkeeping ones (fetch and compute times, derived hashes) changed, and the settings the runner and sync keep for themselves bump nothing. The dashboard reads the counters twice a second and sends the changed topic names over a server-sent event stream (`GET /api/live`, one per browser tab, with a heartbeat every 25 s). The browser refetches the cached views that read those topics (`web/src/api/topics.ts`), each view at most once every 3 s. A reconnecting tab gets the full counter map first and refetches what changed while it was away. Actions are ordinary POSTs; their effects come back through the same stream. Views that change without a database write, such as a job's log tail and the runner's heartbeat age, poll slowly.

### On and Off

The pipeline starts **Off**. An operator switches it on the Pipeline page or with `autocraft-server pipeline on|off`; the switch records who and when. Off cancels waiting automatic jobs and queues no new ones. A running job started by the pipeline stops starting new items (Fix-up, CI fix, Fix red main, Fix, Collect fix results, Verify and Collect verification) and finishes the item in hand, with its GitHub writes refused. A cancel request or a passed deadline stops new items the same way. Draining behaves like Off for new items; the item in hand finishes with its writes.

**Work leases.** A PR, issue or finding is worked by one job at a time. Fix-up (including conflict merges and operator fix-ups), CI fix (work, formatter results, lint results), Fix, Collect fix results and the security fix take a lease (`pr:<repo>#<n>`, `issue:<repo>#<n>`, `finding:<repo>#<n>`) before the item's first model call and release it when the item ends. A job that finds the item leased by another running job skips it without counting it against its limit and records the keys it skipped; the planner queues the step again once no running job holds any of them. A lease whose job is not running is free; runner start and a job's end delete its leases.

While On, the runner plans whenever the content the stages read changed, a job or sandbox task ended, a work lease was given back, an operator changed a limit or released work, the Task Runners that may take calls changed, or a wait the last pass found ended. A 5-minute timer is only a fallback. A changed change-counter topic is how the runner sees a change of content: every topic counts but those of bookkeeping (jobs, usage, agent runs, sandbox environments, audit, the sync's own runs and the like). The topic `plan-inputs` reports what the plans read and no page topic covers: roles and write permissions, the app's slug, outside-author holds, stale reviews, live review reads, author permissions and account ids, item vectors, conflict merges, findings with a quiet pull request. A table the plans read without such a topic says why in `src/db/plan-inputs.ts` (`noTopic`). Ends are counters as well (`job-ends`, `task-ends`), so an end that is dated or committed late is planned too. The planner queues a job for each stage and repo that has work, no job of that step and repo queued or running, the step under `step_parallel`, and limit left; a lane queues one job per repo in a pass; in the stages that run one job per pull request it queues one for each due pull request a person started or approved, and up to 24 item jobs, one pull request of each repo in turn (the next pass, which an ended job starts, queues more). In the user-local mode it queues no job of a step that calls Claude for a repo no Task Runner may take now (the taker rule of `src/remote/takers.ts`, read once per pass), and no job of a per-pull-request stage unless a call about its pull request has a taker, the test the queued call itself gets: the stage's status and the items on the Next page say "No Task Runner takes <repo>" (or the task, or the items), and the planner runs again when the set of Task Runners changes. A job whose calls were all withdrawn for want of a taker counts as one that did nothing, so it is not queued again on every pass. Per-repo stages (Label, Review, Merge, Act, Fix-up, Fix) queue only for repos whose pipeline is on and that have the matching approval.

A stage does not wait on a timer when it has work. Two rules decide when a stage that has work is held back:

- **Same input.** Each queued job stores a fingerprint of the input it saw (the stage, the repo and the counters of the topics the stage reads; a job's end is none of them). A job of one PR, and a job of a repo proposed for its due items (Verify), stores those PRs' facts in place of the counters, so it changes when one of them does or one joins or leaves the list. A job that handled no items and made no other progress (no batch started, opened or advanced) is not queued again until the fingerprint changes. A step reports such progress with `acted`, next to `items`.
- **Work no Task Runner takes.** A unit of a job's pool that no Task Runner may take is left unstarted and recorded as skipped for want of a taker, like a model call withdrawn for that reason. A job of the repo (no item of its own) that handled nothing, ran no unit to an end (a unit that ran may be waiting on builds still running) and skipped only such work waits for the takers, not for the rest of its input: it is queued again once the set of Task Runners or their settings, the work people started or approved, or the stage's own extra reading changes, and the stage's status says "no Task Runner takes the work it left; it runs again when a Task Runner can take it". On a busy repo the other counters move on every pass while that work stays untaken. A job that handled some units and left others is queued again as usual; the next one, left with only the untaken work, then waits. A job proposed for its due items is held back instead by the Task Runner test on those items (Task Runner for the repo, under Waits).
- **Failures.** After a failed job the stage waits 1 minute, then 2, 4, 8 and 16, then 30 minutes, until a job succeeds. Each repo, and each PR of a per-item lane, keeps its own count: a repo whose job keeps failing waits while the stage goes on with the others. A changed fingerprint or an operator release ends the wait at once. Jobs a runner stop or restart ended without resuming them do not count; a job that resumes has not ended (see Restarts and resumed jobs in [operations.md](operations.md#restarts-and-resumed-jobs)).

Stages that watch an outside system (upstream CI of PRs waiting for it, open batch PRs, finished sandbox tasks) are exempt from the first rule and read it again every minute. The full classification pass is never started automatically.

**Circuit breakers.** Each push stage (fix-up, CI fix, implement) and the merge path has a breaker per repo, stored in `stage_trips` as `<stage>:<repo>` (`implement:deckcraft`), and each push stage also has an instance-wide breaker, the bare `<stage>`. A push stage trips on a repo when 2 of that repo's last 10 pushes of the stage since its last resume turned a required check red. A push turned a check red only when the checks before it were green on a run newer than the default branch head the push's run merges with: the run before is dated by the later of our own push of that head and the sync first seeing its commit, and the default branch head by its commit time; while either time is not known the green counts. A branch the push created takes the CI result of the newest default-branch head with a final result (its run merges with the newest head), else that of the commit it was built on. When the default branch moved after the green run, the push's run is the first to merge the PR with the newer base and a failure there may come from the base; such a push is `stale` and takes no place among the 10, neither as broken nor as clean. The CI fix still repairs that head as one our push left red; when it cannot, the question says CI fails since the base branch moved. Merges trip on a repo when its main CI turns red because of a merge of ours or a post-merge review of one of our merges finds a defect. A repo's trip stops that stage for the items of that repo only: each planned push or merge there is refused until the resume, and neither the planner, a step nor the write guard takes it. The stage's jobs still run: what writes no commit (asks, reruns, the end of an implementation attempt, the bookkeeping of open batches) goes on there, and everything goes on for other repos. A push stage trips on every repo when the broken pushes among its last 10 across repos since that breaker's last resume come from 2 or more repos, which points at the step rather than at a repo; it then stops the stage's pushes everywhere. Act writes no commit, so no push breaker stops it. Each trip shows as its own row on Needs (Stopped) and below the daily limits on the Pipeline page, naming its repo or all repos. An operator, or for a repo's trip a maintainer with GitHub write permission on that repo, resumes it there or with `autocraft-server pipeline resume <stage>:<repo>` (or `<stage>`); pushes and merges before the resume no longer count for that breaker. The outside-surge breaker (below) is separate.

**Pipeline switch per repo.** Each tracked repo has a Pipeline toggle (Repos page, list and detail; `autocraft-server repos pipeline <repo> on|off`; audited as `repo-pipeline`). An operator, or a maintainer with GitHub write permission on that repo (read live on the request; `canSwitch` on the repo view), may switch it. A newly tracked repo starts off. Off means sync only, but for what people started: the mirror sync, Embed and Rank keep running, and every other stage works only the items with a live workflow (and the PR an implementation works on): for the rest there are no candidates, no model calls, no sandbox builds (operator smoke tests excepted) and no merges. The planner drops any job whose `repo` parameter names a repo outside the scope of its stage (the stage shows "outside the pipeline scope"; `src/core/scope.ts`): most stages need the switch or a live workflow; Act also runs where a close a person asked for is due; the unassign and PR status steps, the post-merge review and the closing of a batch whose PRs people no longer work run in every tracked repo, and a verification that was started is collected (without a model call). With the switch on, an item a person ended (stopped, closed, backlog) is out of scope, and so is a PR of an issue whose newest workflow a person ended, unless the PR has a live workflow of its own. The per-repo approvals still gate every GitHub write in a repo that is on.

**GitHub identity.** One instance-wide switch decides whether GitHub writes and dashboard sign-in use the box account (`box`, the default) or the GitHub App (`app`). Operators set it on the GitHub App page or with `autocraft-server identity [box|app]`; audited as `github-identity`. Switching to `app` is refused unless an app is registered and its installation covers every tracked repo; the refusal lists the repos that are not covered. Every switch ends all dashboard sessions, so everyone signs in again under the new mode. Under `app`, only a merge or a close that carries out a person's answer is made as that person (their own user token, `user:<login>`); `actsAsPerson` in `src/github/identity.ts` holds the rule. Every other write runs as the app, including the comment posted before a close, labels, assignments, new issues, review requests, transfers, and all rule merges, reviews, fix-up, conflict and CI-fix comments and pushes, claims, batch and fix-issue PRs, post-merge issues, CI approvals and reruns. Each of those runs with an installation token minted for the write's repository alone (a transfer's token also reaches the target repository): `gh` and `git` children get a replaced environment holding only that token, so the box account's `GITHUB_TOKEN` and `GH_TOKEN` never reach them, and git hands it only to `https://github.com`. Fix-up pushes to a contributor's fork use an installation-wide token, since the fork is outside the installation (the PR must allow maintainer edits). The app owns no fork, so `autocraft/*` branches of batch and fix-issue PRs are pushed to the base repo. When no token can be minted (app not registered, not installed, repo outside the installation) the write fails with an `app identity:` error; it never falls back to the box account. Security advisory writes stay on the box account and are audited as `legacy`. A merge or close under a `user:*` grant never gets the app token. An answer that carries out no merge or close never waits for the person's token or permission.

### Outside authors

Two protections keep an author outside the team from using up model spend, for example by opening hundreds of PRs. Both apply to items created by an **outside author**: an author who is not an operator or maintainer on the access list, not the pipeline's own account, not a GitHub Bot (author type Bot or a login ending in `[bot]`: an app can open items only where it is installed), not an owner, member or collaborator of the repo (the author association GitHub reports), and not on the Contributors whitelist (an `allow` override or a whitelisted tier). A post-merge follow-up issue, which the pipeline opens from its review of a merged PR, counts as an item of that PR's author. Each protection is off at 0. Only items in scope for model work count and can be held: items of repos whose Pipeline switch is on, never started ones.

- **Daily budget.** Of one outside author's items created in the last 24 hours (by creation time, across tracked repos), only the first `outside_prs_per_day` PRs (default 5) and the first `outside_issues_per_day` issues (default 5) get model work. Later open items wait with the wait "Author over daily limit" until an older item passes 24 hours, so a held item starts by itself once the window frees.
- **Surge breaker.** More than `outside_surge_per_hour` (default 30) new outside-author items in the last hour trips the breaker `outside-surge`. Outside-author items created from an hour before the trip hold until an operator resumes it; there is no timer. After a resume only items created later count towards a new trip. Insiders' and older items continue. The health check `outside-surge` (warning) shows the trip in the top bar and in `/healthz/checks`; the trip and the resume are audited like the other breakers.

**The gate.** Held items live in `outside_holds`, which the planner rewrites once per pass (`refreshOutsideHolds`, `src/outside.ts`) from one query on the items created in the last 24 hours. The scope condition (`inScopeExpr`) leaves a held item out, so every stage that picks candidates through it skips the item: Classify, Priority, Duplicates, Review, Fix-up, CI fix, Verify and the rest. Sync, Embed and Rank keep running. A started item and a released item are not held.

**Admission.** An item the gate has let through once (planned without a hold) or that already had pipeline work when the protections began is admitted and never held by the daily limit afterwards, even if the limit is lowered. The surge breaker holds only items created from an hour before the trip that were not admitted before it, and its holds last until the resume, however old the items are; the resume starts a planner pass at once. Bot authors known only by login (dependabot, renovate, github-actions, the review bot list) count as Bot until the mirror has stored their author type.

**Release.** An operator, or a maintainer with write permission on the repo, presses Release on the item page; the item is exempt from then on. Release all on Admin > Limits (operators only) releases every item now held for one author; the list there shows each author with held items. An operator can also set the author to `allow` on the Contributors page.

**Settings.** The three numbers are on the Pipeline page; operators edit them, everyone else reads them. Changes are audited as `abuse-limits`, releases as `outside-release` and `outside-release-author`.

### Daily limits

Limits count items handled per stage per day (from 00:00 UTC), including by failed or stopped jobs. Operators change them on the Pipeline page or with `autocraft-server pipeline limit`. Empty means no limit; 0 pauses the stage. A job's `limit` is what is left of the day's limit after today's count and after the unspent part (limit minus items handled) of every queued or running job of the same step, so concurrent jobs of a step never pass the day's limit together. Fix-up takes its item budget before an item's first await. The page shows why a stage cannot start. An operator can start a stage's count for today again from zero ("Reset count" beside the figure, `autocraft-server pipeline limit reset <step>|--all`, audited as `limit-reset`): only jobs that started after the reset count, until 00:00 UTC.

GitHub writes are paced inside the write module, so every write path is covered. Per identity and repo owner, at most 60 writes a minute and 400 an hour are started (GitHub's limits are about 80 and 500). The box account runs every write under the box identity and is one key for all owners, operator presses on those repos included. Only `user:` identities (an operator's own token) are exempt. A write over budget waits until the window frees, for at most 15 seconds; past that it fails as paced without an audit row and the planner retries it. After a write on a key failed with a secondary rate limit or abuse error, that key pauses for 60 seconds. Bulk writes (the label writes of the labels-apply step) count against the same budget but start only while the key has used less than half of each limit (30 in the last minute, 200 in the last hour), which leaves room for the writes that move PRs (CI approvals, reviews, merges, comments). A bulk write over its half waits and is refused as paced like any other; the labels-apply job then stops starting batches and ends as done, with the rest left for the next job. A job that failed only because a write was paced does not count toward failure backoff.

## Discord mentions, replies and search

Optional and off by default. It counts explicit mentions of tracked items in Discord channels the operators choose, answers pings of the bot and runs issue search commands (below). Nothing else in the pipeline reads the counts, and the planner ignores the tables (the `discord` topic is not in `INPUT_TOPICS`).

- **Switch.** The runner starts a gateway client only when `AUTOCRAFT_DISCORD_TOKEN_FILE` and `AUTOCRAFT_DISCORD_KEY_FILE` name files (mode 600). The token is read from the file and is never logged or stored in the database. A failed connection or a bad configuration is logged and shown on the Discord page; the pipeline keeps running.
- **Gateway.** Node's built-in WebSocket and `fetch`, with the GUILDS, GUILD_MESSAGES and MESSAGE_CONTENT intents, heartbeats, resume or reconnect with backoff, and a pause on rate limits. A refusal that cannot be fixed by retrying (bad token, intents not allowed) stops reconnecting. The client reads only MESSAGE_CREATE, MESSAGE_UPDATE, MESSAGE_DELETE and MESSAGE_DELETE_BULK of watched channels and never message history; it also receives INTERACTION_CREATE. Messages by bots are not counted. It posts only the replies described under "Ping replies" and "Commands".
- **Matching.** An item counts when the message holds a GitHub issue or PR URL of a tracked repo, `repo#123` or `owner/repo#123` for a tracked repo. Code blocks count. A message counts once per item. An edit replaces the message's references.
- **Storage.** `discord_mentions` has one row per message and item: repo and number in the clear for counting, and the guild, channel, message ID and message time sealed with AES-256-GCM under a key derived from the key file. A keyed hash of the message ID and one of the channel ID are kept in plain columns only to find rows for deletion; a keyed hash of the author ID is sealed with the row, so no per-person value sits in a plain column. No message text, no author ID and no per-person data is kept. A deleted message (watched channel or not), a deleted channel or thread, a guild the bot is removed from, or an edit that drops the reference deletes its rows. A message deleted while the bot is offline keeps its row until a deletion request; unwatching a channel keeps its rows.
- **Deletion requests.** `autocraft-server discord forget --message <link or id>` and `autocraft-server discord forget --user <user id>` delete rows (the second opens every row to find the author, only matches messages seen after this feature started, and also removes the user's account link). Each is audited.
- **Opting out.** `/autocraft account action:optout` stores a keyed hash of the caller's Discord user ID in `discord_optouts` and deletes their mention rows as `discord forget --user` does (rows from before authors were sealed cannot be matched); `/autocraft account action:optin` removes the row. While the row exists, `handleDispatch` records nothing for their messages, so they get no attention check and no reaction; their pings, @-commands and slash commands still run. An edit event without an author records no new rows, since its author's opt-out cannot be checked. Both are audited (`discord-optout`, `discord-optin`) without the user ID; opt-outs are limited to 5 a minute per user. `discord forget --user` does not opt the user out.
- **Channels.** The bot reports its servers and its text, announcement and forum channels into `discord_channels`; `watched` is the operators' choice (Discord page, or `autocraft-server discord watch|unwatch <channel id>`). Nothing in an unwatched channel is read. Threads and forum posts count under their parent channel: watching the parent watches them.
- **Bot permissions.** The invite needs the `bot` and `applications.commands` scopes and the permissions View Channels, Send Messages, Add Reactions, Read Message History, Create Public Threads and Send Messages in Threads. With the Discord page switch "React to recorded messages" on (the default), the bot adds the server's custom emoji named by the Discord page setting "Reaction emoji" (default `bot`; or `autocraft-server discord react-emoji [value]`, audited as `discord-react-emoji`) to a message, a Unicode emoji there is used as is, and 🤖 stands in when the server has no such custom emoji when it first records it against items; a refused reaction (missing permission, deleted message) is logged once per channel and skipped.
- **REST.** `src/discord/rest.ts` is the one client for posting, editing and deleting messages, interaction callbacks and registering commands. It runs requests of a rate-limit bucket one at a time, waits out `X-RateLimit-Remaining: 0` windows, retries a 429 after the `retry_after` Discord names (up to four tries) and honours the global limit. Requests of different buckets run side by side. Interaction callbacks are sent at once, never queued behind other requests.
- **Commands.** `src/discord/interactions.ts` keeps a table of command handlers keyed by command name (and subcommand) and button handlers keyed by `custom_id` prefix; other features add theirs with `command()` and `component()`. Every interaction is deferred first and edited when the handler is done, except handlers that answer with a form (a modal must be the first response within 3 seconds) or acknowledge a menu choice. At READY and at each GUILD_CREATE the guild's commands are replaced with the registered set (a bulk overwrite, so it is idempotent). Registered now: `/autocraft search` (no fields; it opens the search form, see Search) and `/autocraft report` (no fields; it opens the new-issue form, see Search form and new issue helper), the message command "Find issue", and `/autocraft account action:<link|unlink|alerts|optout|optin>` (with `code` for link and `state` for alerts; a missing option gets a short error naming it) and `/autocraft status` (`item:<repo#n>` for the public status layer, "No item found" for an unknown or hidden item; without an item, counts for the public repos or for the `repo` option, whose choices come by autocomplete); all replies are ephemeral. A handler that fails after the deferral edits the response with a short error. `/autocraft help` answers privately with short sections (find issues, status, commands, your account with the contributor role, privacy), one Components V2 text display each, and, when `AUTOCRAFT_BASE_URL` is set, Privacy notice and Terms link buttons; when Discord rejects the V2 message, the plain fallback keeps the whole sections that fit in 2,000 characters, with the same buttons.
- **Ping replies.** A new message from a person (not a bot or webhook) that mentions the bot, directly or through its managed role, in a watched channel gets one public reply: the items the quoted message links to or names (its mention rows and the item links and `repo#n` references in its text; items of public repos the public layer shows, in any state), then the issues closest to the question, with `allowed_mentions` set to none. The question is the quoted message when the ping is a reply, otherwise the ping's text without mentions. Edits get no reply. A message counts as a ping only when its text contains `<@botId>`, `<@!botId>` or the bot's role mention; the author-of-the-quoted-message entry Discord adds to `mentions` does not count, and a reply to one of the bot's own messages is ignored. When the ping, or the quoted message, is deleted, the reply is deleted in Discord and then its row (the pings handler owns this, so `discord_replies` is untouched until it runs); `autocraft-server discord forget --message` does the same through the bot token. `discord_replies` holds a keyed hash of the ping, one of the quoted message and one of the channel, and the reply's guild, channel and message ID sealed like the mention rows; no text.
- **Search.** A public tracked repo named in the question as a whole word (case-insensitive) restricts the search to that repo and is left out of the embedded text; when none or several are named, all public repos are searched. `/autocraft search` and the panel's find button open a form with one text box and search with its text (all repos or the one the text names, like "Find issue", with the same limits). The message command "Find issue" searches with the message text, all repos or the one the text names. Ping replies use the detection too; the channel's default repo does not restrict the search. The question is embedded in memory with the local model (loaded on first use) and compared with the stored vectors of issues and pull requests of public tracked repos: open ones, issues closed as completed in the last 180 days (shown with "(closed)") and pull requests merged in the last 7 days (a pull request closed unmerged is left out); pull requests are shown with "(PR)" and, when merged, "(merged)". The closest twenty are read and those with a cosine of at least 0.55 are kept, at most ten, with no model call: open issues first, then by activity (comments plus reactions, highest first), then by the latest update; a missing reaction count counts as 0. A command reply lists every match that fits in one message; a public ping reply lists the best three. Limits: 5 questions a minute per person and 20 per channel, counted in memory by keyed hash; a pinged question over a limit gets no reply, a command gets a short refusal.
- **@-commands.** A person's message in a watched channel that is addressed to the bot (it mentions the bot, or replies to the bot's message in a thread the bot follows or to the bot's command reply) and whose text without mentions starts with a command word or alias, or reads whole as a command (`yes`, `urgent`), is a command (`src/discord/at-commands.ts`); any other mention stays a ping. It runs exactly as `/autocraft do` (`src/discord/do.ts`: the workflow parser, the model reading and its refusal rules, the linked login, write permission per repo, the per-hour command limit, the audit and the "approved by" record). A command that names no item acts on its context: the items recorded for the message it replies to, else those of the bot's reply or thread it answers; named items replace the context and need not be among it, and `review all` reads as `review`. Write permission is the cached check when it is under a minute old, else the GitHub App's answer, which refreshes the cache; when the app cannot read it, a check under 10 minutes old counts (`freshWrite` in `src/remote/permission.ts`, also used by `/autocraft do` and by agent commands without a dashboard session). A sender with no linked login, or without write access on a repo of the items, gets one short public reply (at most one per 10 minutes) and nothing runs; when GitHub could not be asked, the reply says the check failed and to try again. When anything ran, the bot starts a public thread on the command message, named after the command and the first item (`review · photocraft#123 (+2)`), and posts the confirmation lines there, the lines GitHub shows; a command sent in a thread is answered in that thread. Without Create Public Threads, Send Messages in Threads or Read Message History in the channel, or when starting the thread fails, the answer is a plain reply, logged once per channel. A command that ran nothing gets a plain reply. Replies mention nobody.
- **@-status.** `@AutoCraft status`, alone or followed by items (`status photocraft#123 photocraft#456`), is a lookup, not a command: anyone may send it, at most 10 a minute, addressed to the bot like a command. It answers with a plain public reply in the form of `/autocraft status`, one block and one link button per item, at most five: the items named, else the items of the message it replies to (its mention rows, the items of the bot's reply, and the item links and `repo#n` references in its text), else the thread's items. An item of a private or untracked repo, or one the public status layer leaves out, reads as not found; with no item at all the reply is "No item found".
- **Threads.** The thread, or the plain reply that stands in for it, follows the items that ran (`src/discord/threads.ts`): later commands there, and replies to the bot's reply, take their items from it, and the results of the work on those items belong there (`followersOf`, `sendToFollow`). `discord_follows` has one row per target and item: the item in the clear, a keyed hash of the thread's channel ID (or of the bot's reply's message ID) and of the channel the command was sent in, the command as the parser writes it, the AutoCraft login, the time, and the guild, channel and message IDs with a keyed hash of the sender sealed like the mention rows. Rows go with the thread, the channel, the bot's reply, `discord forget --user`, or 30 days after the last command that named the item there. Items of private repos and items kept quiet as possible security problems show in Discord as status lines and links only (`discordDetail` in `src/discord/visibility.ts`).
- **Results in threads.** `src/discord/results.ts` posts the work on the followed items where the command was answered. Each status change of an item posts its status line, the first line of its GitHub status comment without the place in line or what a running item waits for ("Running: review", "Running: fix-up: 1 and 2", "Stopped at a blocker: …", "Held by …", "Merged"); the lines of one target that changed together share one message, with a link button per item. When an item comes back to a person, its result is posted: the numbered parts and the recommendation line, the same words as the status comment, with a "Full result on GitHub" button to that comment (to the item where none is known). A result that changes while it stays open edits its message, a new link edits only the button, and a result message deleted in Discord is posted again. An item that becomes status-only after its result was posted has that message edited down to its status line and link. A result over 1,900 characters gets a Haiku summary of its parts (`discord.result.haiku`, on an Interactive slot, step `discord-result`) under the recommendation line kept word for word; without a summary the parts are cut to fit and the rest counted as "more on GitHub". The text is kept in memory by the result's hash, so a retried send makes no new call. Items of private repos and quiet items get only status lines and links. Passes run when the `workflows` topic moves (a 2-second poll of the change markers, as for alerts) and right after a command adds a follow; a pass reads each followed item's workflow version, visibility and status comment id, and builds the full view only where one changed, for newly followed items, and for items whose post failed. `discord_follow_posts` keeps, per target and item, hashes of the status line, result and link last posted, the result's workflow and recommendation time, and the result message's ID sealed; no text. It feeds no live topic. A target whose channel is gone or closed to the bot (Discord codes 10003 and 50001) stops being followed; any other failed send backs that target off, from 30 seconds doubling up to 30 minutes.
- **Reply layout.** Replies are Components V2 messages (flag `1 << 15`, no `content`). Each result (title, repo#n, "(PR)"/"(merged)"/"(closed)") is a section: its text with its link button as the accessory beside it, at most ten results. After the sections, an action row holds "File a new issue", a button that opens the search form (below) with the app preselected: the channel's default repo (set per channel on the Discord page, public tracked repos only; a thread uses its parent's), else of the top result's repo or the only public tracked repo, with the description filled from the question.
- **Search form and new issue helper.** `/autocraft report` answers at once with a form: an app select (a Label component around a string select; public tracked repos that an operator has not hidden from the bot, and filing-only repos (docs/operations.md) by `release_apps.name`, else the repo name, preselected with the channel's default repo, at most 25: the preselected repo, then the filing-only ones, then the most open issues) and a description box, plus an optional Screenshots upload (up to 3 files, a File Upload component in a Label) on the bug and undecided forms when screenshot storage is configured (the `AUTOCRAFT_ATTACH_*` variables, docs/deploy-checklist.md); the session keeps only Discord's links to the files. The "File a new issue" button opens the same form with the description and repo filled in. Submitting searches that repo (up to ten matches, like Search) and replies privately at once with the matches (embeddings only, no model call), each result as a section with its link button, and "None of these, file a new one"; when nothing matches the reply says no similar issue was found and offers Continue. A filing-only repo is not searched: the reply says so and offers Continue. At submit a Haiku call (prompt `discord.issue-questions`) starts in the background, without delaying the reply, and picks up to three follow-up questions by id from a fixed list (steps to reproduce, expected and actual result, version and platform, what it would let the person do; issue templates are not synced); a failed call uses the questions of the kind. The result is kept in memory with the session and dropped when it expires. "None of these" opens the questions as a second form at once when the choice is ready; when the call is still running it defers, waits for it (at most 8 seconds) and shows a Continue button for the form. With no questions the flow goes to the draft at once. A further Haiku call (`discord.issue-draft`) writes the title, body and kind (bug or feature), which are length-capped and stripped of mentions, HTML and any link that is not an issue or pull request of a public tracked repo. The private draft has a type select (Bug report or Feature request, preset to the kind the person chose, else the model's) and the buttons Submit for me (below), File it (while filing under the person's account is on), Edit (title and body in a form) and Open on GitHub (a prefilled new-issue link, body trimmed with a note to fit 1500 encoded characters). File it calls `fileIssue()` (`src/discord/file-issue.ts`): a person who has not signed in gets a "Sign in with GitHub" link button and presses File it again afterwards; a filed issue answers "Filed as repo#N" with a link button and ends the session; a refusal shows its reason and the GitHub link. Person text sits in memory for the session only (15 minutes); the calls run as step `discord-issue` with cost in `agent_runs`, their prompt and reply texts are deleted when a call ends and at startup. Spend of the day against the `discord_issue_daily_usd` setting (default 2): at or above it no model call is made and the draft is built from the form. Limits: 3 new-issue sessions an hour per person, 10 per channel, counted in memory by keyed hash, when the person presses "None of these" (over the limit the button answers with a refusal); searches 5 a minute per person.
- **Issue panel.** `autocraft-server discord panel post <channel id>` (run where the bot token is, on the runner) posts a bot message with three buttons, Report a bug, Request a feature and Find an existing issue, pins it (the bot needs the pin permission in that channel; a failed pin is printed and the panel stays) and stores its message id in `discord_channels.panel_message`. Posting again edits that message in place; when it was deleted in Discord a new one is posted and pinned. Audited as `discord-panel`. Report a bug and Request a feature (custom_id `panel:bug|feature`) open the form of the new-issue helper with the channel's default repo preselected (the parent's for a thread). Find an existing issue (`panel:find`) opens the search form: one text box, no app select and no follow-up questions; its submit searches like the "Find issue" message command and replies privately with the matches, whose "File a new issue" button opens the new-issue form. Report a bug and Request a feature set the kind: the form title and description label follow it, both model calls get it (`kind` in the form JSON), the draft keeps it whatever the model guesses, and without a model answer a feature request is asked "What it would let you do" instead of the three bug questions.
- **Contributor role panel.** An operator picks a channel and a role id under Contributor role on the Discord page (or `autocraft-server discord role-panel set <channel id> <role id>`; `role-panel off` turns it off, `role-panel` shows it; audited as `discord-role-panel`). The settings are `discord_role_channel` and `discord_role_id`; the server is the channel's. The runner watches them (`src/discord/role-panel.ts`): it posts a message with a Verify button there and pins it, edits it in place at each start, deletes it when the channel changes or the feature is turned off, and keeps what it did in the bookkeeping setting `discord_role_panel` (shown on the Discord page; a failed post is tried again after 5 minutes). Verify (custom_id `rolecheck:verify`) answers privately. The GitHub login comes from the Discord account's link (`/autocraft account action:link`) or a GitHub sign-in made for filing; a typed name is never used. Without one the answer gives the link steps. A member who already has the role is told so. Otherwise AutoCraft looks for a merged pull request the login authored in a repo of the tracked owner with GitHub's search (`is:pr is:merged author:<login> org:<owner>` through the read path; at most 3 searches per login in 10 minutes, and a refused search, a 422 included, counts as not checked). The web verification, which knows the GitHub account id, asks the mirror first: merged pull requests by that account id in the owner's repos. A yes is cached in memory, by account id where known. Before giving the role the bot reads it from Discord and refuses a role that grants any permission or belongs to an integration (result `unsafe-role`; the panel is then not posted and the Discord page shows why). With a merged pull request, the bot adds the role (`PUT /guilds/{guild}/members/{user}/roles/{role}` with an audit-log reason naming the login); without one the answer says no merged pull request was found for the login; when GitHub cannot be asked it says to try later. A 403 from Discord answers that the bot cannot give the role yet and logs a line for operators. Each press is audited as `discord-role-verify` with the result and the keyed hash of the Discord user, never the id. Limits: 3 presses per person in 10 minutes and 20 a minute in all. Discord setup: the bot's role needs Manage Roles and must sit above the contributor role; in the panel channel the bot needs View Channel, Send Messages, Read Message History and Pin Messages (Manage Messages on servers without the separate pin permission).
- **Contributor verification on the web.** Most contributors are not dashboard users and cannot use Link Discord, so a member without a linked account who presses Verify gets a private link to `<base URL>/verify` (when the runner knows `AUTOCRAFT_BASE_URL`). The pages there (`src/dash/server/verify.ts`) need no dashboard session; `/verify` is the one path prefix the access gate in front of the dashboard must leave open, and the pages load nothing outside it. The visitor presses Continue with Discord (`POST /verify/discord`), signs in with Discord (OAuth2, `identify` scope; callback `/verify/discord/callback`), then with GitHub through the GitHub App's user authorization (callback `/verify/callback`). Each token is used once to read the account, then revoked; none is stored. Each step's OAuth state is single use, stored as a hash in `discord_verify_flows` and bound to the browser by the `__Host-craft_verify` cookie (HttpOnly, Secure, SameSite=Lax), which holds a random flow id the server keeps only as a hash; a flow expires after 15 minutes. The Discord user id stays in the flow row, sealed with the Discord key, never in a URL. After the GitHub step the dashboard links the two accounts (`discord_links.source` verify), so the button works directly next time, and runs the merged pull request check. A verify link never replaces a link made with a dashboard code, and a later `/autocraft account action:link` turns it into one. Commands (`/autocraft do`, @AutoCraft commands) need a code link and an AutoCraft login (an access row) besides write access, so a verify link runs none; searches, status and Verify work for it. With a merge it writes a row to `discord_role_grants` (the Discord user id sealed, the login, the time); the runner, which holds the bot token, wakes on the `discord-verify` change counter (checked every 2 seconds), looks the member up, adds the role and writes the result: granted, already, not-member (not in the panel's server), forbidden, failed, off or unsafe-role. It works through the open requests a page of 20 at a time until none is left, and drops open requests older than a day. Results are audited as `discord-role-verify` with `from: "web"`, like a press. The result page (`/verify/done`) asks `/verify/status` for the result a few times, then says the role will appear shortly. Without a merge, or when GitHub cannot be asked, the result page says so. Unfinished flows go at their expiry, finished flows and requests after a day; `/autocraft account action:unlink` and `discord forget --user` delete the user's flows and requests (matched by the keyed hash of the Discord id). The start form is accepted only from this site (Origin / Sec-Fetch-Site), and its page allows the form to lead to Discord (`form-action 'self' https://discord.com`); Discord always asks for consent. Limits: per address 60 page requests and 120 status polls in 10 minutes; flow starts for all addresses together a burst of 30, then one every 2 seconds. The notice is also served at `/verify/privacy`. Setup: set `AUTOCRAFT_DISCORD_CLIENT_ID` and `AUTOCRAFT_DISCORD_CLIENT_SECRET_FILE` on the dashboard (it also needs `AUTOCRAFT_DISCORD_KEY_FILE`, `AUTOCRAFT_BASE_URL` and the GitHub App); under OAuth2 in the Discord developer portal add the redirect `<base URL>/verify/discord/callback`; add `<base URL>/verify/callback` to the GitHub App's callback URLs. Until all of these are set, `/verify` says the verification is not set up.
- **Submit for me.** The draft offers "Submit for me" when the GitHub App may file for the person in that repo now (`botRefusal()` in `src/discord/file-issue.ts`): the instance's GitHub identity is `app`, the repo is public and tracked or filing-only, and the limits hold; for a filing-only repo the GitHub App must also cover it, read when the draft is built and kept 5 minutes (`appCovers` in `src/discord/filing-repos.ts`). Otherwise it offers only Edit and the prefilled GitHub link; a link-only filing-only repo's draft also says AutoCraft cannot file issues there yet. When the app lost access between the draft and the press, the press is refused ("AutoCraft can no longer file issues in this repo.") with the GitHub link. `fileAsBot()` files the draft through `createBotIssue` in `src/github/write.ts` with an installation token (never the box account), audited as `discord-issue-bot` under identity `app` (repo, number and URL, not the text) and labelled `bug` or `enhancement` like a reporter's issue. The body starts with the note line (AI-generated issue when a model wrote the draft) and ends with "Reported on Discord by <name>. Filed by AutoCraft on their behalf.", where the name is the unique Discord handle (`@username`, in a code span so GitHub does not mention anyone), never the nickname or display name, which users can change; without a handle it is "Discord user <id>". The junk check does not run again at submit (see below). Limits per 24 hours: 3 issues per Discord person (keyed hash), 30 per repo (`discord_filed`, shared with reporter filings; the slot is reserved, the limits counted again with it, and freed on any failure) and 50 for all of Discord (`discord-issue-bot` and `discord-issue-open` audit rows that did not fail). The draft states that the issue names the person as the reporter. Screenshots are copied only here, after the limits and the junk check pass (`attach` in `BotRequest`, `src/discord/attachments.ts`): each file is downloaded from Discord's CDN (20 seconds, at most 10 MB by declared size and by bytes read), kept only when its first bytes show PNG, JPEG, GIF or WebP, uploaded to the bucket with one SigV4-signed PUT (`Cache-Control: public, max-age=31536000, immutable`) and embedded under a "Screenshots" heading as `![<file name>](<public URL>)`, the name stripped of brackets and line breaks. A file that fails is left out, the issue is filed without it, and the "Filed as" reply names each left-out file and why. Images never reach a model prompt. The prefilled GitHub link cannot carry files, so when the person attached any, the draft and the refusal replies say to attach them on GitHub's page.
- **Filing from Discord.** Built and off (`FILING_IN_DISCORD` in `src/discord/file-issue.ts`): until the sign-in also confirms the Discord user in the browser, the draft offers only the prefilled GitHub link and the sign-in routes are not served. `fileIssue()` (`src/discord/file-issue.ts`) files a drafted issue under the person's own GitHub account, for public tracked repos only. A person who has not signed in gets a "Sign in with GitHub" link (`/discord/github/start?state=...`, state random, single use, stored hashed with the Discord user's keyed hash, valid 10 minutes); the callback (`/discord/github/callback`, both public, no dashboard session) stores the GitHub App user token in `reporter_tokens`, sealed like `user_tokens` with an AAD naming the table and reporter. The runner refreshes it as the dashboard does (compare-and-swap on `version`; a dead refresh token asks for sign-in again). The issue is created with the person's token through `gh`, audited as `discord-issue-open` under their GitHub login through `createReporterIssue` in `src/github/write.ts` (the audit row keeps the repo, number and URL, not the text; write limit 50 a day), with the footer "Filed from Discord with AutoCraft." and the label `bug` or `enhancement` when the repo has it and the token may set it (an audited `discord-issue-label` write). The junk check (Jev, Haiku where unsure or unavailable, `discord.junk.*`) runs once, on the person's first message (the description with the chosen kind), before the follow-up questions: spam, abuse, empty and test posts stop at once with the refusal and the prefilled GitHub link, and no question is asked. With no model answer the flow goes on. `fileIssue()` and `fileAsBot()` check the draft only when called without `junkChecked`; the flow sets it, so submit makes no junk call. The model sees only the message and the texts are deleted. Limits per 24 hours: 3 issues per GitHub login and 30 per repo (`discord_filed`; the slot is reserved first and freed on any failure, rows older than 24 hours are deleted). A new sign-in revokes the token it replaces. The new-issue session limit (3 an hour) counts when the person chooses "None of these, file a new one", not at each search. `/autocraft account action:unlink` and `autocraft-server discord forget --user` remove the sign-in and the person's `discord_filed` rows and queue the token's revoke. The GitHub App's callback URLs must include `/discord/github/callback`.
- **Attention signals.** `src/discord/signals.ts` checks each new message in a watched channel that names a tracked item (and each edit; a link-preview update is skipped) for one question per item, at most five items (a message naming more is not checked; 10 checks per minute per author and 30 per channel, in memory, over a limit it stays a plain mention; two model calls at a time, the rest wait): does it ask for attention (a review, a merge, an answer, whether anyone is looking)? Jev (`discord.signal.jev`) answers first: 0.8 or more is a signal, below 0.3 a plain mention, in between Haiku (`discord.signal.haiku`, no tools, the text as delimited data) decides. Without Jev, Haiku decides alone. Haiku calls stop for the day when the signal calls cost the `discord_signal_daily_usd` setting (default $1); a message past the cap stays a plain mention. The text is used for that call only: the result is one `signal` flag on the mention row, the recorded prompt and reply are deleted when the call ends (and at startup), and a deleted message takes its row and flag with it. The item page header shows "Asked about on Discord ×N" linking to the newest such message (links need the key file). Items has a "Seen on Discord" filter (`discord=1`) that lists every mentioned item, asked about or not. The flag is display only: nothing in the pipeline reads it, and the `discord` topic stays out of `INPUT_TOPICS`.
- **Public status.** `src/public/status.ts` is the only source of what anonymous people may learn, and exports the visibility rule (`isPublicRepo`, `publicRepoNames`, `hiddenSql`) that search candidates, counts, queue places and repo lists share. `publicStatus(repo, number)` gives an item's title, URL and one step of a fixed list (New, Triaged, In review, Waiting for CI, Fix-up in progress, Needs a maintainer decision, In the merge queue with its place in the Queue page order (heaviest first, then ready before batched, then work rank), Merged, Closed), derived from the item's stage, cached plan, workflow and queue; holds and refusals show as In review. It returns nothing for an untracked or non-public repo, and for security fixes (a quiet fix PR, a finding's fix PR, an item flagged or labelled security). `publicStats` gives open issues and PRs, merges and posted reviews of the last 7 days (and how many merges were AutoCraft's), the median open-to-merge time over 30 days and the merge queue length, per public repo or in total.
- **Linking accounts.** A signed-in dashboard user chooses Link Discord in the account menu and gets a code (8 characters, single use, valid 10 minutes, one live code per login, stored as a keyed hash in `discord_link_codes`; audited as `discord-link-code`). In Discord they run `/autocraft account action:link code:<code>`; the bot answers privately "Linked to <login>" and the link is stored in `discord_links` (keyed hash of the Discord user ID, login, time; audited as `discord-link`). Code entries are limited to 5 a minute per Discord user. `/autocraft account action:unlink`, Unlink Discord in the account menu and the operators' list on the Discord page remove links (audited as `discord-unlink`). The account menu and the Discord page refresh on their own topic, `discord-links`.
- **Privacy and terms pages.** `/privacy` and `/terms` are public and need no session. Its contact line is the `discord_contact` setting.

| `autocraft-server conversation show\|say\|do` | Conversations |
| `autocraft-server repos test-repo <repo> on\|off` | Marks a tracked repo as a test repo |
| `autocraft-server workflow status [repo]` | Lists the live workflows |
| `autocraft-server pipeline on\|off\|limit`, `accounts list\|set\|jev` | Switch, limits, accounts |

On a test repo, the security scan may be driven from the CLI by an operator login. On a test repo, a post-merge defect or a red default branch trips the breaker `merge:<repo>` only, which holds merges on that repo and not the whole pipeline.
